# Design: OTel spans

## Decisions

**1. Один trace на задачу.**
`trace_id = sha256(task_id)[:32]`; `span_id = sha256(event_id)[:16]`. Это
детерминированно: один и тот же прогон можно сопоставить без хранения ID.

**2. Время из журнала.**
Начало span — `events.created_at`; конец — следующий event или +1 мс. Это не
измерение длительности операции, а интервал между переходами; так честнее, чем
выдумывать end time.

**3. Метрики и spans — разные OTLP payload.**
OTLP/HTTP принимает `resourceMetrics` на `/v1/metrics` и `resourceSpans` на
`/v1/traces`; смешивать их в одном запросе нельзя. Поэтому `--out`/`--endpoint`
относятся к метрикам, `--traces-out`/`--traces-endpoint` — к spans; без приёмника
spans команда отказывает.

**4. trace_id не пишется в журнал, а вычисляется.**
Problem «trace_id в журнале нет» закрыт детерминизмом: `trace_id(task_id)`
восстанавливается из журнала без миграции схемы. Запись ID в БД не нужна.

## Risks

- Длительность span — интервал до следующего события, а не CPU-время.
- Spans плоские: `parentSpanId` нет, все события — корни одного trace; иерархия
  переходов не выражена.
- `trace_id` детерминирован от task_id: все попытки одной задачи попадают в один
  trace, атрибута attempt у spans нет.
- Метки времени — wall-clock float; суб-микросекундная точность теряется.
- События без `result.ok` имеют UNSET, а не OK.
- Без `--traces-out/--traces-endpoint` команда отказывает; `--out` метрик к этому
  моменту может быть уже записан — частичный результат остаётся.
