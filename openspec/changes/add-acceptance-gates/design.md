# Design

## Context

`change-FSM` Этапа 1 знает состояния, но verify/release/accept/archive были
«социальными»: проверялись только состояние и (для verify) факт наличия задач.
Записей о прогонах, выпуске и приёмке не было, а архив не требовал evidence.

## Decisions

**1. Два прогона как объекты, а не как лог.**
`verification.json` хранит результаты baseline и candidate отдельно: команда, ref,
окружение, runner, tests_ran, failures, exit_code, длительность. Отчёт без обоих
прогонов не проходит. Baseline может идти в отдельном git-worktree на `--ref`;
candidate — в рабочем дереве.

**2. Diff по именам упавших тестов.**
Новые падения = candidate_failures − baseline_failures. Это ловит регресс даже когда
оба прогона «не зелёные», и не требует хранить полный лог. Парсер понимает unittest
(`FAIL/ERROR: name`) и pytest (`FAILED path::name`); нестандартный runner обязан
назвать число тестов, иначе отчёт честно не проходит.

**3. Записи — файлы рядом с change.**
`release.json`, `acceptance.json`, `closing.json` лежат в каталоге change, а не в БД:
их видит Git, их можно приложить к закрывающему PR. Связь с планом — `spec_ref`,
с проверкой — `services` (имя + полный SHA).

**4. Evidence — копии с sha256-манифестом.**
`write_evidence` копирует артефакты change и вердикты задач в
`evidence/change-<id>/`, пишет `manifest.json` с sha256 и размером. Пакет — это
воспроизводимая опись, а не «папка с файлами». Подпись/вывоз — следующий этап.

**5. L0 может принять без release, L2 — только человек.**
Для L0 выпуск не обязателен (нет поведения в проде), но проверка всё равно нужна.
Для L2 release и acceptance требуют `by_role=human`; агент/CI отклоняются. Это
декларация роли: доверенная идентификация — отдельный остаточный риск.

## Risks / Trade-offs

- **Записи подделываемы** — файлы в change; связь spec_ref и SHA сервисов снижает
  риск, но не заменяет подпись.
- **Парсер вывода зависит от runner** — честно: неизвестный формат не даёт «pass».
- **Baseline-worktree требует git и чистого ref** — при отсутствии ref baseline идёт
  в рабочем дереве с пометкой, а не молча выдаётся за принятую версию.
- **Evidence копирует файлы, а не вывозит их** — retention и подпись остаются
  Этапу 4.

## Migration Plan

- Новые поля/файлы опциональны: существующие change без verification просто не
  перейдут verify.
- `release/accept/close` — новые команды; старые `advance --event` для этих
  переходов теперь требуют записи (осознанное ужесточение).
