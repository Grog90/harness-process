# Design

## Context

Этапы 1–4 сделали change, роли, verification, приёмку и видимость в одном корне.
Сервисы уже фигурировали в release/acceptance как пары `name=SHA`, но change и
verification оставались односервисными.

## Decisions

**1. Сервисы — payload change, не новая таблица.**
`change.payload.services` — список `{name, path, base_commit}`. Это те же данные, что
видит Git и closing PR; отдельная таблица потребовала бы миграции без выгоды.

**2. Verification-ключи `service:mode`.**
Для совместимости сервис `repo` пишет старые ключи `baseline`/`candidate`. Остальные —
`api:baseline`. `check_report` группирует ключи и требует оба режима для каждого
объявленного сервиса; новые падения считаются по каждому сервису.

**3. Границы записи не расширяются молча.**
Guard и gateway остаются однокорневыми: change может читать и прогонять тесты сервиса
по `--cwd`, но писать в чужой репозиторий через guard нельзя. Мультикорневая запись —
следующий шаг; выдавать её за готовую нельзя.

**4. Приёмка уже мультисервисная.**
Release/acceptance принимают несколько `--service`; `evidence` копирует записи, поэтому
несколько SHA попадают в манифест без отдельного формата.

**5. Порядок объявления — merge order.**
`change.payload.services` упорядочен; release/acceptance обязаны сохранить этот порядок
(`merge_order`), иначе запись отклоняется. Это фиксирует порядок слияния в evidence,
даже если сам merge выполняет внешний инструмент.

**6. Запись в чужие корни не открыта сознательно.**
Guard/gateway остаются однокорневыми. Мультикорневой write требует отдельной модели
прав (какие пути сервиса разрешены роли, как считать snapshot и откат); включить его
«заодно» значило бы ослабить R-PROT-1 без тестов на побег. Поэтому v1 умеет читать,
прогонять тесты и собирать версии сервисов, но не писать в них.

## Risks / Trade-offs

- **Пути сервисов не проверяются на существование при приёмке** — verification-прогон
  проверяет cwd, а change хранит путь как метаданные.
- **Guard не пишет в сервисы** — это ограничение v1; для изменений в сервисе нужен
  отдельный worktree/сессия.
- **`spec_ref` остаётся одним SHA** (репозиторий спецификаций); версии сервисов живут
  в verification/release/acceptance.
- **Declared services и фактические прогоны сверяются по именам, не путям** — путь
  проверяется при `verification run --cwd`.
