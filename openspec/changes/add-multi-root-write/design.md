# Design

## Context

Guard/gateway знают один `root`; политика нормализует путь относительно него и
отклоняет `..`. Сервисы уже объявлены в change и брифе, но только для чтения и
verification. Нужен явный, узкий путь записи, не превращающий R-PROT-1 в «любой
абсолютный путь разрешён».

## Decisions

**1. Путь как ключ, а не как сырой абсолютный путь.**
Политика принимает `service:<name>/<relative>`. Абсолютный путь из инструмента
резолвится в этот ключ только если он лежит под объявленным сервисным корнем.
Так `allowed_files` остаётся списком глобов, а не списком произвольных путей.

**2. Два независимых разрешения.**
`service.write` (change открыл сервис) и `role.can_write_services` (worker вообще
имеет право писать сервисы). Нет любого — отказ. Verifier/analyst/QA не получают
флаг, поэтому даже открытый сервис для них read-only.

**3. Realpath на обоих концах.**
Gateway проверяет `realpath` цели и корня; guard делает `realpathSync` (с fallback
на родителя для ещё не созданного файла). Симлинк из сервиса наружу не проходит.

**4. Shell не расширяется.**
`>>`, `sed -i`, `cp` в сервисный путь остаются запрещены: эвристика shell не умеет
надёжно разбирать несколько корней. Писать в сервис — только `write_file`, который
проходит общий resolver.

**5. Snapshot/commit — отдельная граница.**
Gateway пишет файл, но `snapshot`/`commit`/`finalize` по-прежнему смотрят главный
корень. Коммит сервисного репозитория делает человек/CI отдельно. Это ограничение
v1 названо в docs, а не спрятано.

## Risks / Trade-offs

- **Незакоммиченные изменения сервиса** не попадут в evidence-манифест, пока их не
  добавят вручную; поэтому v1 требует явного `service-write` и отдельного коммита.
- **Guard и Python-политика — две реализации**; расхождение ловится parity-тестами,
  но только для матрицы случаев, а не для произвольных путей.
- **Пути сервисов в change — метаданные**: если путь изменится, verification/запись
  будут работать со старым каталогом, пока change не обновят.
- **Junction/symlink на Windows** проверяется realpath; остаточный риск — TOCTOU
  между проверкой и записью (как и в однокорневом режиме).
