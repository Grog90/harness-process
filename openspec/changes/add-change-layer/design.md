# Design

## Context

Мотивация — в `proposal.md`. Сейчас `harness/fsm.py` знает только задачу; `openspec/`
хранит change, но связь «задача ↔ изменение ↔ редакция плана» нигде не проверяется.
`specgate.py` принимает архивный change и не сверяет digest, `brief from-change`
теряет ID требований и сценариев.

## Goals / Non-Goals

**Goals:**
- Автомат изменения с явной таблицей переходов и guard'ами.
- Review-запись как объект: артефакт, хеш, редакция, автор, роль, критерии, вердикт.
- Trace-матрица `REQ → CASE → task` с устойчивыми ID и блокировкой разрывов.
- Полный `spec_ref` (40 hex) в брифе и в записи change; совпадение проверяется.
- Гейт диспетча по состоянию change; обратная совместимость брифов без change_id.

**Non-Goals:**
- Приёмка и архив как гейты с evidence — следующий этап.
- Baseline/candidate-прогоны, мультирепозиторность, UI.
- Автоматическое согласование: review остаётся решением роли, а не выводом модели.

## Decisions

**1. Состояние изменения — в SQLite, review-записи — файлами в change.**
`changes`, `change_events`, `change_reviews` живут рядом с задачами: один писатель,
транзакции, переживает перезапуск. Review-запись дополнительно пишется в
`openspec/changes/<id>/reviews/*.json`, чтобы её видел Git и можно было проверить
без БД. Альтернатива «только файлы» не даёт атомарности и запросов; «только БД»
теряет переносимость доказательства.

**2. Review валиден только для текущего хеша и редакции.**
Хеш файла — sha256 содержимого; хеш `specs`/`contracts` — sha256 по отсортированному
списку относительных путей и содержимому. Правка артефакта меняет хеш, и прежний
approve перестаёт учитываться. Альтернатива «хранить diff» избыточна для гейта.

**3. Ready-гейт вычисляется, а не хранится флагом.**
`ready_check()` каждый раз собирает отчёт: артефакты, review по ролям, trace, GAP,
spec_ref. Переход `ready` вызывает его и при отказе не меняет состояние. Это
исключает «однажды пройденный» Ready после правки плана.

**4. ID требований и сценариев детерминированы.**
Явные `REQ-…`/`CASE-…` в заголовках сохраняются; без них выдаются `REQ-<n>` и
`CASE-<req>-<n>`, стабильные при добавлении в конец. Это позволяет связать вердикт
и критерий с требованием без отдельного реестра.

**5. Привязка задач — по `change_id` в брифе, а не по имени каталога.**
`brief from-change` заполняет `change_id`; `fsm._guard_dispatch` вызывает
`changefsm.gate_dispatch`. Если change не зарегистрирован в состоянии — отказ:
нельзя «привязаться» к спеке, не объявив изменение. Брифы без `change_id`
работают как раньше — это осознанная обратная совместимость, а не дыра: новые
брифы из `brief from-change` всегда привязаны.

**6. `spec_ref` — формат плюс совпадение, но не проверка существования коммита.**
Гейт проверяет 40 hex и равенство `change.spec_ref`. Существование объекта в Git
не проверяется: план может быть ещё не слит, а работа уже идёт в ветке. Остаточный
риск фиксируется: SHA подтверждает договорённость, а не её содержимое.

**7. `specgate` принимает только живой change и сверяет digest.**
Архивный change — история, а не разрешение на новый код. Digest из
`spec_version` сравнивается с текущим digest `specs/**`; расхождение означает, что
бриф собран по старой редакции. Если в change нет `spec.md`, сверять нечего — это
явно пропускается, а не считается совпадением.

## Risks / Trade-offs

- **Подмена reviewer_id** → проверка «автор ≠ reviewer» опирается на идентификаторы,
  которые задаёт вызывающий; нужна доверенная идентификация (guard/сессия).
- **Формальный review** → критерии можно заполнить не читая артефакт; это измеряют
  evals и человек, а не хеш.
- **Trace проверяет наличие связи, не смысл** → сценарий может не проверять
  требование по существу; смысл остаётся за BA/QA.
- **`spec_ref` может указывать на несуществующий коммит** → формат и совпадение
  проверяются, существование — нет; это записано в residual рисках R-REF-1.
- **Локальная БД — не распределённое состояние** → обход harness не видит гейта;
  граница та же, что у остальных правил задачи.

## Migration Plan

- `SCHEMA_VERSION = 4`; новые таблицы создаются `CREATE TABLE IF NOT EXISTS`,
  `tasks.change_id` добавляется идемпотентным `ALTER TABLE`.
- Старые задачи и брифы без `change_id` сохраняют прежнее поведение.
- Откат: перестать вызывать `changefsm.gate_dispatch`; таблицы можно оставить —
  они не влияют на задачи. Колонку `change_id` SQLite не удаляет, но она безвредна.
