# Design

## Context

Мотивация — в `proposal.md`. Здесь только то, что определяет подход.

Сейчас `harness/lanes.py` создаёт worktree и ветку (`create`), сливает под мьютексом
(`merge_lock`, `merge`) и удаляет (`remove`). Ветка пишется в `tasks.lane` при
`task new`, то есть колонка уже занята именем ветки, а не ресурсами.

`harness/checks.py` собирает окружение проверок заново из белого списка (`SAFE_ENV` +
`PATH`/`HOME`/`TMPDIR`) и в docker-ветке `_execute` передаёт контейнеру только
`PYTHONUNBUFFERED`. Любая переменная, выставленная снаружи, до команд не доходит —
поэтому «просто экспортировать порт в шелле» не работает.

Состояние — SQLite с идемпотентными миграциями через `ALTER TABLE`; атомарное
резервирование в проекте уже применяется для бюджета попыток.

## Goals / Non-Goals

**Goals:**
- Детерминированный, воспроизводимый набор ресурсов на лейн, вычислимый из целого слота.
- Уникальность слота среди живых лейнов без ручной уборки.
- Доставка ресурсов в команды проверок в обоих режимах `checks run` (docker и copy-only).
- Отсутствие лейна = отсутствие переменных: обратная совместимость.

**Non-Goals:**
- Настоящая песочница (сеть, права процесса) — это `R-SANDBOX-1`, другой предмет.
- Поднятие реальной БД или брокера: harness выдаёт координаты, а не сервисы.
- Ресурсы, разделяемые между машинами: слот локален для рабочего дерева.
- Очередь интеграции и барьер волны — остаток `R-WAVE-1`, но не этот change.

## Decisions

**1. Слот — строка в таблице `lane_resources`, а не поле в `tasks`.**
Отдельная таблица с `PRIMARY KEY (slot)` и `UNIQUE (task_id)` даёт уникальность
средствами БД: выдача слота — один `INSERT`, коллизия — `IntegrityError`, а не
проверка-потом-запись с гонкой. Альтернатива (колонка в `tasks`) требует сканирования
всех задач при каждом создании и допускает окно гонки между чтением и записью.

**2. Ресурсы вычисляются из слота формулой, а не хранятся произвольным конфигом.**
`resources_for(root, slot)`: база портов `18000 + slot * 10`, БД
`.harness/lanes/<slot>/test.db`, временный каталог `.harness/lanes/<slot>/tmp`,
индекс `slot`. Формула — часть контракта: значения можно пересчитать и объяснить,
а не «где-то записаны». Альтернатива (конфиг в `policy.json`) отвергнута: проектное
правило тогда начинает зависеть от локального файла, а слот перестаёт быть числом.

**3. Проверки получают ресурсы параметром, а не через `os.environ`.**
`checks.run(..., lane_resources=None)` добавляет переменные поверх `SAFE_ENV` внутри
`_env()`. Если бы harness выставлял их в своём процессе, пришлось бы расширять белый
список — то есть чинить изоляцию дырой в изоляции. Docker-ветка получает по `-e` на
каждую переменную: иначе требование выполнялось бы только при `copy-only`.

**4. Освобождение — явное плюс ленивая очистка.**
`lane remove`/`lane release` удаляют строку. Слот, чей worktree исчез (каталог
отсутствует и ветка не числится в `git worktree list`), считается свободным при
следующем выделении: отдельный сборщик мусора не нужен, а забытые лейны не копятся.

**5. Занятый извне порт — повод взять следующий слот, а не падать.**
При выдаче harness проверяет доступность базы портов (`bind` на `127.0.0.1`); занятая
база означает, что рядом чужой процесс, и слот пропускается. Исчерпание диапазона —
отказ `R-WAVE-1` с явной причиной.

## Risks / Trade-offs

- **Порт занят процессом, который не слушает `127.0.0.1`** → проверка `bind` ловит
  только локальный конфликт; риск принимается, команда проверки всё равно увидит
  ошибку и вернёт `INCONCLUSIVE`, а не ложный PASS.
- **Слот утёк после падения между `INSERT` и созданием worktree** → ленивая очистка
  по отсутствию worktree возвращает слот; строка без worktree живёт до следующего
  `lane create`.
- **Длинные пути на Windows** (`worktree` + `.harness/lanes/<n>/tmp` легко упирается в
  260 символов) → временный каталог держим в `.harness/lanes/`, но в отчёте и в
  `HARNESS_LANE_TMP` отдаём абсолютный путь, а тесты проверяют длину.
- **Две задачи в одном лейне** → `UNIQUE (task_id)` не спасает; принимаем, что лейн —
  на задачу (это уже так в `lane create`), а повторный `create` для той же задачи
  отказывает, как и сейчас.
- **Расширение `checks.run` меняет сигнатуру** → параметр со значением по умолчанию,
  вызовы без лейна не трогаем; паритет с плагином проверяется `tests/test_parity.py`.

## Migration Plan

- Миграция схемы идемпотентная (`CREATE TABLE IF NOT EXISTS`), старые базы
  открываются без действий.
- Задачи, созданные до изменения, имеют `lane='main'` и не получают переменных —
  поведение прежнее.
- Откат: удалить таблицу и вызовы `resources_for`; состояние задач не затрагивается,
  потому что слот живёт отдельно от `tasks`.

## Open Questions

- Нужен ли таймаут жизни слота (например, сутки) помимо очистки по worktree — можно
  решить после первых реальных прогонов, на спецификации это не влияет.
- Стоит ли отдавать базу портов в `policy.json` как настройку — вопрос вкуса, пока
  константа в коде и одна точка изменения.
