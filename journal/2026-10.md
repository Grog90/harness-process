## L-20261026-08 · schtasks-interactive-window

- **Дата:** 2026-10-26
- **Тип:** среда
- **Триггер:** Создание периодической задачи планировщика через schtasks /Create /TR с pwsh или powershell
- **Симптом:** Каждые N минут в интерактивной сессии вспыхивает консольное окно PowerShell
- **Причина:** schtasks регистрирует задачу в интерактивной сессии пользователя (LogonType Interactive) и без скрытия окна; сам процесс pwsh создаёт консоль в этой сессии

- **Область:** Windows Task Scheduler
- **Проверка:** Get-ScheduledTask -TaskName <имя> | Select-Object -ExpandProperty Settings | Select-Object Hidden

## L-20261029-01 · dropbear-client-openssh-key

- **Дата:** 2026-10-29
- **Тип:** среда
- **Триггер:** Обратный SSH-туннель с Keenetic: `dbclient -i <ключ, созданный ssh-keygen>` — падает сразу, до аутентификации
- **Симптом:** `dbclient: Exited: String too long`, при этом без `-i` доходит до «Host key accepted unconditionally»; OpenSSH с того же ключа с ПК к тому же серверу ходит нормально
- **Причина:** Клиент на роутере — это dropbear (`/opt/bin/ssh` → dropbear), он не переваривает приватный ключ в формате OPENSSH PRIVATE KEY. Второй слой: `ssh-keygen -N '""'` записал парольную фразу из двух кавычек, а не пустую
- **Правило:** Для dropbear генерировать ключ на самом роутере через `dropbearkey -t ed25519 -f <файл>`, а публичную часть снимать `dropbearkey -y -f <файл>`. Ключи из `ssh-keygen` для dbclient не использовать
- **Область:** Keenetic, Entware, dropbear 2025.89
- **Проверка:** `dbclient -N -T -y -i /opt/var/monitoring/tunnel_key_db -R 127.0.0.1:9115:127.0.0.1:9115 tunnel@<vps>` и `ss -ltn | grep 9115` на VPS

## L-20261029-02 · awgm-upload-limit

- **Дата:** 2026-10-29
- **Тип:** среда
- **Триггер:** Заливка 20 МБ бинарника на роутер через `POST /api/system/files/upload`
- **Симптом:** `Error while copying content to a stream … Удалённый хост принудительно разорвал подключение`
- **Причина:** Крупный multipart-аплоад через API панели не проходит. Заодно выяснилось: `path` у upload — это **каталог**, а не файл (иначе `target is not a directory`), а имя берётся из имени файла
- **Правило:** Крупные файлы на роутер не заливать аплоадом: писать скрипт через `/system/files/write` (в `.sh` он сам ставит исполняемый бит) и запускать его `/system/files/script-action`, а скачивание делать `curl` на самом роутере
- **Область:** AWG Manager 2.19.22, `/opt/var`
- **Проверка:** `script-action` возвращает `output` и `ok:true`; файл на месте по `/system/files/list`
## L-20261029-03 · keenetic-no-pkill

- **Дата:** 2026-10-29
- **Тип:** среда
- **Триггер:** `S99monitoring restart` на роутере «перезапускает» сервис, но конфиг не подхватывается
- **Симптом:** `restart` рапортует `running`, PID не меняется, blackbox продолжает отвечать `HTTP 400` на модуль, который в конфиге уже есть
- **Причина:** В busybox на Keenetic нет `pkill`; в скрипте стояло `pkill -f ... 2>/dev/null`, ошибка глушилась, процесс не убивался, а `start` видел «уже запущено» и ничего не делал
- **Правило:** Не рассчитывать на `pkill`/`pgrep` в Entware-скриптах: убивать через `ps | grep ... | while read pid rest; do kill "$pid"; done`, а после `restart` проверять, что PID сменился
- **Область:** Keenetic, busybox, `/opt/etc/init.d/S99monitoring`
- **Проверка:** `ps | grep "[b]lackbox_exporter --config"` до и после restart — PID должен отличаться; `/probe?module=<новый>` отдаёт 200, а не 400
## L-20261029-04 · ntopng-kills-keenetic

- **Дата:** 2026-10-29
- **Тип:** среда
- **Триггер:** ntopng 6.6 из Entware с захватом на `br0` на Keenetic Giga KN-1012
- **Симптом:** интернет и ping работают, но API AWG Manager и веб-интерфейс Keenetic не отвечают; запросы висят до таймаута, через 30-60 с некоторые всё же проходят
- **Причина:** захват пакетов на двухъядерном MT7981 с GRO/TSO съедает CPU; демонам управления не остаётся времени. Место на флешке при этом было (6,8 ГБ) — дело не в диске
- **Правило:** На этом роутере не запускать packet-capture сервисы (ntopng, tcpdump-конвейеры). Для «кто куда ходил» использовать снимок `/api/connections` + журналы. Если служба всё же уложила роутер — пробиваться к API с таймаутом 120-150 с (он отвечает, но медленно), а не считать его мёртвым
- **Область:** Keenetic KN-1012, Entware, ntopng, AWG Manager
- **Проверка:** `ps | grep "[n]topng"` пусто, `/api/connections` отвечает < 2 с, веб Keenetic открывается
## L-20261029-05 · instagram-slow-is-rtt

- **Дата:** 2026-10-29
- **Тип:** диагностика
- **Триггер:** «Instagram долго обновляется, видео плохо грузятся» через Hysteria на новом сервере
- **Симптом:** субъективно медленно, но объективных провалов нет
- **Причина:** замеры показали RTT роутер→VPS 76 мс (bufferbloat нет, под нагрузкой те же 76), скорость через туннель 74 Мбит/с, VPS→Instagram 21–30 мс и 0% потерь, 40 запросов к API — p50 0,21 / p95 0,27 с, ошибок Hysteria к Instagram 0, утечек напрямую 0. Медленно потому, что каждый круг стоит ~100 мс против 20–30 мс напрямую, плюс видео в общей сессии поднимает p95 до 0,46 с, плюс периодические 429 от Instagram
- **Правило:** при жалобе «медленно» сначала мерить RTT и реальный поток, а не искать потери. Не менять настройки туннеля, пока не доказано, что дело в них: здесь всё было исправно, а лечится близким сервером
- **Область:** Keenetic, hysteria2, Instagram
- **Проверка:** таблица замеров в `.dsh/skills/vpn-router/reference.md` §12; повтор — `curl` через 1081 + ping до VPS под нагрузкой
