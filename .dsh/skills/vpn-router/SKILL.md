# Обход блокировок на Keenetic

Домашняя сеть ходит в интернет через **Keenetic Giga (KN-1012)**, прошивка 5.1.8.
На роутере два независимых механизма обхода:

| Механизм | Что делает | Когда применять |
|---|---|---|
| **Hysteria 2 → `Proxy0`** (AWG Manager) | заворачивает домены в туннель на VPS `91.103.253.94`; вход по домену `knt-gw-7731.duckdns.org`, obfs salamander, без `insecure` | сервис заблокирован по IP или нужен зарубежный адрес |
| **nfqws2 (zapret2)** | ломает DPI локально, без туннеля | блокировка по SNI/протоколу: YouTube, Discord |

Рабочий пример: YouTube и Discord идут через **nfqws2**, Telegram / Instagram /
GitHub / Spotify / AI — через **Hysteria (`Proxy0`)**.

Старый VPS `177.177.230.47` **мёртв** (не отвечает с 29.10.2026); его туннель и
туннель на IP `91.103.253.94` удалены 30.10.2026 — сервер перешёл на домен и ACME,
и клиент со старым `sni=de-vps.local` получить сертификат уже не может.
Мониторинг: **http://91.103.253.94:8080** (см. раздел «Мониторинг»).

Подробный инвентарь (файлы, порты, списки, туннели, история тупиков) —
в `reference.md` рядом с этим файлом.

## Жёсткие правила

1. **Не откатывать самому.** Не сработало — стоп, показать данные, предложить
   варианты, ждать «да». Подробнее: `AGENT_RULES.md` в корне воркспейса.
2. **Любое изменение маршрутизации, списков, режимов, пакетов — только после
   явного «да».** Чтение (`curl` GET, `/api/...` GET, `iptables -S`, логи) —
   свободно.
3. **Списки не удалять.** Выключить = `set-enabled false`; удаление необратимо.
4. **`remove_dns_route` / `remove_static_route` необратимы** — только по прямой
   просьбе «удали навсегда».
5. **Не привязывать устройства к политикам Keenetic.** У политик нет маршрута
   по умолчанию — устройство теряет интернет. Проверено, не повторять.
6. **`MODE_ALL` в nfqws2 не включать.** Он трогает весь трафик; нужен `MODE_LIST`.
7. **Не ставить на роутер сервисы с захватом пакетов** (ntopng, tcpdump-конвейеры).
   Проверено 29.10.2026: ntopng 6.6 кладёт роутер — AWG Manager и веб Keenetic
   перестают отвечать, интернет при этом жив. Восстановление: убить ntopng и redis.
8. **Мониторинг — страница, а не Grafana.** Владелец её читает глазами с телефона;
   графов он не понимает. Новые дашборды не строить без просьбы.

## Как обращаться к роутеру

| Канал | Когда |
|---|---|
| MCP `awgm` (`mcp__awgm__*`) | удобно, но **отваливается** после перезапуска AWG Manager; тогда падает «unknown tool» |
| HTTP API `http://192.168.1.1:2222/api/...` | всегда; ключ в `~/.dsh/secrets/awgm.env`, заголовок `Authorization: Bearer` |
| SSH `plink -batch -ssh -pw ... admin@192.168.1.1` | только через `exec sh -c "..."`; CLI Keenetic без `storage`, `known host` |
| Chrome `chrome_*` (MCP browser) | проверка «что видно в браузере» — единственный честный способ |

Полезные эндпоинты AWGM:

```
GET  /api/routing/dns-routes            — списки и их цели
POST /api/dns-routes/update?id=list_N   — сменить цель: {"routes":[{"tunnelId":"system:Proxy1"}]}
                                            или {"tunnelId":"wan:ppp0"} для «напрямую»
POST /api/dns-routes/create             — новый список
POST /api/dns-routes/set-enabled?id=…   — вкл/выкл
GET  /api/singbox/tunnels               — туннели sing-box
POST /api/singbox/tunnels               — добавить из share-ссылки {"links":"hy2://…"}
GET  /api/singbox/router/status         — профили, orphan-правила, проблемы
```

## Рецепт: сервис через туннель (Hysteria)

1. `GET /api/routing/dns-routes` — найти список сервиса (`list_N`).
2. `POST /api/dns-routes/update?id=list_N` с
   `{"routes":[{"tunnelId":"system:Proxy1"}]}`.
3. Проверка: `chrome_net` на домен сервиса — 0 проблем; либо
   `GET /api/singbox/tunnels/test/ip?tag=<tag>` — `ipChanged: true`.

## Рецепт: сервис через nfqws2 (локальный обход)

1. Домен дописать в `/opt/etc/nfqws2/lists/list-general.list` (мягкий профиль,
   TLS не ломает) или в `list-google.list` (YouTube/Google).
2. `POST /api/dns-routes/update?id=list_N` с `{"routes":[{"tunnelId":"wan:ppp0"}]}`
   — домены должны идти **напрямую**, иначе nfqws2 их не увидит (он висит на `ppp0`).
3. `/opt/etc/init.d/S51nfqws2 restart`.
4. Проверка: `chrome_net` — 0 ошибок TLS; для видео — `chrome_eval` с
   `video.currentTime`.

## Перенос стратегии zapret v1 (Windows) → nfqws2 (роутер)

Это главная ловушка: **имена параметров совпадают, смысл — нет**.

| zapret v1 (`winws.exe`, `.bat`) | nfqws2 (`--lua-desync=…`) | Комментарий |
|---|---|---|
| `--dpi-desync=fake` | `fake` | базовая функция |
| `--dpi-desync-fake-tls-mod=rnd,dupsid,sni=X` | `tls_mod=rnd,dupsid,sni=X` | одинаково |
| `--dpi-desync-hostfakesplit` | `hostfakesplit` | |
| `--dpi-desync-hostfakesplit-mod=host=X` | `host=X` | **в обеих версиях это шаблон суффикса**: генерируется `случайное.X` |
| `--dpi-desync-hostfakesplit-mod=altorder=1` | **`disorder_after=-1`** | v1: реальный хост отдельным сегментом после; v2: задаётся точкой разреза |
| `--dpi-desync-fooling=ts` | **`tcp_ts=-600000`** | v1 смещает TSval на -600000. **`tcp_ts_up` — другая операция**, не путать |
| `--dpi-desync-fooling=badseq` | `tcp_seq=-10000` | дефолтный инкремент v1 |
| `--dpi-desync-fooling=badsum` | `badsum` | |
| `--dpi-desync-fooling=md5sig` | `tcp_md5` | |
| `--ip-id=zero` | **`ip_id=zero` внутри инстанса** | глобального `--ip-id` в nfqws2 нет |
| `--dpi-desync-repeats=N` | `repeats=N` | |
| `--dpi-desync-split-pos=1` | `multisplit:pos=1` | |
| `--dpi-desync-split-seqovl=N` | `multisplit:seqovl=N` | |

Ловушки запуска:

- `--new` **запрещён** внутри `NFQWS_ARGS`, `NFQWS_ARGS_QUIC`, `NFQWS_ARGS_UDP`,
  `NFQWS_EXTRA_ARGS` — init-скрипт ругается. Несколько профилей — только через
  `NFQWS_ARGS_CUSTOM` (он единственный, после которого скрипт сам ставит `--new`).
- Порядок профилей = порядок в командной строке, побеждает **первый совпавший**.
  Фактическая сборка: `BASE` → `CUSTOM` → `UDP` → `QUIC` → `ARGS + EXTRA`.
- `--dry-run` требует `--qnum` и работает только на inline-аргументах:
  `@файл` с комментариями и пустыми строками парсится неправильно.
  Проверять так: `. /opt/etc/nfqws2/nfqws2.conf` и собрать args как
  `_startup_args` в `S51nfqws2`.
- `hostfakesplit` без `disorder_after` даёт другой порядок сегментов — на живом
  трафике это ломает рукопожатие (проверено: YouTube `000`, `ERR_SSL_PROTOCOL_ERROR`).

## Мониторинг: что смотреть, чтобы понять жалобу

**http://91.103.253.94:8080** — единственная панель (без пароля, ~30 МБ, сервис
`netmon` на VPS). Показывает:

- плитки проб: Telegram и Google через VPN, Google напрямую — с кодом ответа и
  временем. **Instagram не пробится намеренно**: синтетика раз в 30 с = 2880
  запросов в сутки с IP VPS, то есть `429` и бан адреса. Здоровье Instagram
  читается только пассивно, по соединениям и ошибкам Hysteria;
- **ошибки**: соединения, не установившиеся за 15 с (`SYN_SENT`), ошибки Hysteria
  из журнала (`dial timeout`, `stream canceled`, `client disconnected`) и
  предупреждения AWGM — со счётчиком повторов `×N`;
- живые соединения: устройство, адресат, сервис по подсети, протокол, состояние,
  байты, через какой туннель;
- локальный шум (например, устройство `192.168.1.93`, долбящее в
  `10.10.10.1:11224`) — вынесен отдельно, к интернету отношения не имеет.

Быстрая проверка руками (с VPS, через проброшенный туннель):

```
curl 127.0.0.1:8080/data                      # JSON со всем снимком
curl 127.0.0.1:2222/api/connections?limit=500 # сырые соединения роутера
sudo journalctl -u hysteria-server --since -1h | grep error
```

Панель не видит URL и коды ответов твоих собственных запросов — трафик зашифрован
TLS. **Имена сайтов при этом видно**: SNI в TLS ClientHello идёт открытым текстом,
проверено дампом на `br0` (`example.com`, `www.iana.org`). Прежнее утверждение про
«только DNS-лог» неверно. Для QUIC SNI так не достать — Initial шифрован, нужен
диссектор вроде `tshark` (на роутере и на ПК его нет).

**Порядок, когда жалуются на тормоза** (не гадать, а идти по шагам):

1. Панель: есть ли ошибки `connect`/`hysteria` и к какому сервису.
2. Живые соединения: идёт ли трафик сервиса через туннель, а не напрямую.
3. Instagram: код не спросишь — смотреть байты на соединениях к `157.240/16`,
   `57.144/16`, `31.13/16`, `179.60/22`: идут ли, каким протоколом, не завис ли
   `SYN_SENT`. Пусто в соединениях при живой сети — приложение не стучится.
4. Разовый захват (ниже) — когда снимка панели не хватает: паузы внутри потока
   панель не показывает, а именно они и есть «крутится».
5. Замеры с VPS: RTT до сервиса, потери, скорость через туннель.
6. Только потом гипотезы. Проверено: ~100 мс задержки сами по себе объясняют
   «медленно», без всякой поломки.

### Разовый захват Instagram: `/opt/etc/ig-capture.sh`

```sh
/opt/etc/ig-capture.sh 45 192.168.1.64   # 45 с, телефон владельца; без IP — весь LAN
```

Снимает `br0`, а не `ppp0`: Instagram уходит в туннель, на WAN его уже нет.
**Никаких запросов в Instagram не делает** — только слушает идущий трафик.
Отчёт печатается сразу (дамп не уезжает по сети): по каждому потоку пакеты и
байты в обе стороны, максимальная пауза, число пауз > 1 с, неотвеченные потоки,
RST, TCP-рукопожатия.

| Что видно | Как читать |
|---|---|
| пауза > 2 с при живом потоке | поток встал — это и есть «крутится» |
| `pk_in = 0` при `pk_out > 0` | телефон отправил, ответа нет: туннель или блокировка |
| паузы на всех потоках сразу | канал/туннель, а не Instagram |
| один CDN-поток встал, другой тянет | конкретная точка присутствия Instagram |
| `pr = udp` у видео | QUIC; при паузах сравнить с TCP (A/B ниже) |

Параллельно с VPS (второй конец цепочки): `ss -tin state established '( dport = :443 )'`
— `rtt`, `minrtt`, `retrans` по TCP-сокетам к Instagram; для QUIC там пусто, что
честно: транспорт QUIC по потокам снаружи не виден.

Замерено 30.10.2026: 9 пауз > 1 с за 30 с на потоке `57.144.222.192` (видео,
1 МБ пришло) при 0 пауз на `57.145.4.192` в ту же минуту — то есть виноват не
канал целиком, а отдельная точка.

**Устройства в сети** (имена как в роутере): `Грига` (192.168.1.64) — телефон
владельца, основной потребитель Instagram; `iPhone` (192.168.2.45); `PC`
(192.168.1.72); `192.168.1.93` — ТВ-приставка (AltoBeam), бесконечно стучится в
`10.10.10.1:11224` — это шум, к интернету отношения не имеет.

## Почему Instagram «медленный» (замерено 29.10.2026)

Туннель при этом здоров — не ищи потерь, их нет:

| Замер | Значение |
|---|---|
| RTT роутер → VPS | 76 мс, 0% потерь, bufferbloat нет (под нагрузкой те же 76 мс) |
| Скорость через туннель | 74 Мбит/с (напрямую 78) |
| VPS → Instagram | 21–30 мс, 0% потерь |
| 40 запросов к `i.instagram.com` через туннель | p50 0,21 с · p95 0,27 с, все 200 |
| Ошибки Hysteria к Instagram за 2 ч | 0 |

Причина ощущения — **задержка, а не поломка**: каждый круг запроса стоит ~100 мс
(76 до VPS + 25 до Instagram) против 20–30 мс напрямую; лента делает несколько
кругов. Плюс множители: видео в общей сессии поднимает p95, а Instagram
периодически отвечает `429` на адрес VPS.

## Instagram принудительно на TCP (с 30.10.2026)

QUIC внутри UDP-туннеля Hysteria даёт длинный хвост: p95 ресурсов страницы
**2,2–3,9 с** против **0,9–1,1 с** по TCP, загрузка 4,9–8,7 с против 2,7–3,0 с.
Захват подтвердил предметно: 9 пауз > 1 с за 30 с на QUIC-потоке CDN при нуле
пауз на соседнем CDN в ту же минуту. После включения TCP страница грузится за
**1,5 с**, все 45 ресурсов по `h2`, ни одного `h3`.

Механика: `/opt/etc/init.d/S98instagram-tcp` держит цепочку `IG_TCP` в `mangle`
(блок UDP/443 к подсетям Instagram), хук
`/opt/etc/ndm/netfilter.d/102-instagram-tcp.sh` восстанавливает её после
пересборки файрвола. Копии — `tools/S98instagram-tcp.sh`, `tools/102-instagram-tcp.sh`.

| Действие | Команда |
|---|---|
| выключить и вернуть QUIC | `/opt/etc/init.d/S98instagram-tcp stop` |
| включить обратно | `/opt/etc/init.d/S98instagram-tcp start` |
| посмотреть правила и счётчики | `iptables -t mangle -L IG_TCP -v -n` |

**Не включать QUIC обратно без замера.** Подсети `31.13.0.0/16` и `129.134.0.0/16`
намеренно не блокируются — там WhatsApp; если захват покажет QUIC-поток к ним,
добавлять точечно, а не целиком.

Порядок проверки после любой правки: `ig-capture.sh 45 <ip>` → нет пауз > 2 с,
`ss -tin` на VPS → `retrans 0`.

## Проверка, что «работает»

Не докладывать «готово» без данных:

1. **Браузер** — `chrome_net <url>`: `problems_count: 0`, статусы 200;
   `chrome_open` — скриншот, глазами.
2. **Видео** — `chrome_eval`: `video.currentTime` растёт, `buffered > 0`,
   `error: null`.
3. **Туннель** — `GET /api/singbox/tunnels/test/ip?tag=…` → `ipChanged: true`.
4. **Приложение** — `Get-Process` → `MainWindowTitle` не пустой; логи
   `%APPDATA%\discord\logs\renderer_js.log` — heartbeat/ACK без ошибок.
5. **moli не использовать для визуальной проверки** — кэширует скриншоты
   (одинаковый `sha256`) и не грузит ленивые картинки.

## Диагностика «не открывается»

1. `curl -o NUL -w "%{http_code} %{size_download}"` с ПК — есть ли ответ.
2. `chrome_net` — какие запросы падают и с какой ошибкой:
   - `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` / `ERR_SSL_PROTOCOL_ERROR` — desync
     ломает рукопожатие: стратегия не та или домен не должен быть в nfqws2;
   - `ERR_CERT_VERIFIER_CHANGED` — гонка маршрутов после смены цели списка,
     повторить заход;
   - `net::ERR_ABORTED` — обычно норма (отменённые запросы).
3. `GET /api/singbox/router/status` — нет ли `orphan-rule` (правило ссылается на
   несуществующий outbound).
4. `iptables -t mangle -S nfqws_pre | grep -c NFQUEUE` — 5 правил = сервис жив.
5. Если домен в списке туннеля, а nfqws2 должен его обрабатывать — трафик уйдёт
   в `Proxy1` и мимо `ppp0`, то есть мимо nfqws2.

## Чего не делать (проверено, тупики)

- **Режим `tproxy` в sing-box-роутере AWGM**: требуются привязанные к политике
  устройства, политика без default route убивает интернет, правила перехвата не
  создаются. Не включать.
- **Outbound через слот `config/user`**: AWGM его не видит, правила становятся
  orphan. Только `POST /api/singbox/tunnels` с share-ссылкой.
- **Заворачивать в туннель `ggpht.com` / картинки Google** — изображения ломаются.
- **`MODE_AUTO`** — трогает весь трафик, ломает посторонние сервисы.
- **Привязка устройств к `Policy2`/`Hwave`** — у политики нет маршрута по
  умолчанию (см. п. 5 правил).
