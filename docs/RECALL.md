# Recall по прошлым сессиям

Локальный поиск по тому, что уже обсуждалось в DSH: без сервера, без ключей, без сети.
Заменяет «агент не помнит прошлые чаты» на «агент может спросить и получить 2–3 точных фрагмента».

## Зачем

Память нужна не для всего, а для вопроса «мы это уже делали?». Такой вопрос решается
поиском по прошлым разговорам, а не загрузкой их в контекст. Индекс строится один раз
и обновляется по mtime.

## Команды

```powershell
python tools/recall.py index            # первый раз ~0.5 с на 20 сессий
python tools/recall.py search "хук deny политика"
python tools/recall.py search "сборка релиза" --exact    # все слова в одном сообщении
python tools/recall.py search "gortex" --limit 3 --json   # для агента
python tools/recall.py stats             # сколько проиндексировано
python tools/recall.py forget            # удалить индекс
```

Вывод — карточки: дата, роль, заголовок сессии, фрагмент с подсветкой `‹…›`, id сессии.

```
[2 дн. назад] assistant · Внедрение практик из учебника по агентным п
  …два контура управления (инструкция / ‹хук›), ограниченная автономия…
  сессия: session-2d2a4538-86d7-4d30-8666-4a46a286d470
```

`--json` отдаёт те же поля машиночитаемо — это то, что стоит отдавать агенту через
инструмент, а не весь вывод целиком.

## Где лежат данные

```
~/.dsh/sessions/<воркспейс>/<session-id>/session.v4.jsonl.zstd
```

Имя воркспейса кодирует путь: кириллица превращается в `~0414~043E…`, поэтому искать
по имени каталога бессмысленно — только по содержимому.

## Что важно знать про формат

Два подводных камня, на которых легко потерять данные молча:

1. **zstd в несколько кадров.** Файл дописывается кадрами; `ZstdDecompressor().decompress()`
   читает только первый и возвращает 263 байта вместо 15 МБ. Нужен `stream_reader(read_across_frames=True)`.
2. **Разная форма событий.** У `assistant/message` контент в `data.message.content`,
   у `user/message` — прямо в `data.content`. Если читать единообразно, пользовательские
   сообщения пропадут целиком (и поиск будет «находить» только ответы агента).

Индексируются: сообщения пользователя, текстовые ответы агента и `compaction/summary`
(сжатые выжимки сессий — самый плотный источник фактов). Результаты инструментов не
индексируются: шум и секреты.

## Экономика токенов

Один поиск — 3 сессии × 2 фрагмента × ~28 слов ≈ 300–400 токенов. Против 15 МБ
транскриптов в контексте это не «экономия», а разница между возможно и невозможно.
Индекс на 20 сессий — около 1 МБ.

## Чего здесь нет

- **Семантики.** Поиск лексический (FTS5 + bm25). Синонимы не находит: «конфиг» ≠ «настройки».
  Морфология компенсируется префиксами (`тест*` → «тесты», «тестировали»), но не всегда.
- **Консолидации.** Нет «наблюдений» и переписывания фактов: что записано, то и найдётся,
  включая устаревшее. Противоречия не разрешаются автоматически.
- **Кросс-машинности.** Индекс локальный; на другом компьютере нужен свой (или скопировать
  `.recall/index.db`).
- **Автозаписи.** Ничего не пишется само: индексируются только уже существующие сессии.

## Чем отличается от Hindsight

| | recall.py | Hindsight |
|---|---|---|
| Инфраструктура | нет | Postgres/pgvector или облако |
| Запись | бесплатно | LLM-вызов на каждый `retain` |
| Поиск | лексический, bm25 | семантика + граф + время + реранк |
| Консолидация | нет | наблюдения, ментальные модели |
| Данные | только у вас | self-host или вендор |
| Прозрачность | видно, что проиндексировано | внутри банка |
| Формулировки | «вот фрагменты» | «я помню, что…» |

Hindsight отвечает на «что мы знаем», recall — на «где это было сказано». Второе дешевле и
проверяемее, первое мощнее. Их можно держать вместе: recall для точных цитат и решений,
Hindsight — для выжимок.

## Ограничения по безопасности

В индекс попадает всё, что было в чатах, включая пути и случайные секреты. `.recall/`
в `.gitignore`; синхронизировать этот каталог в общий доступ не надо. `forget` удаляет
индекс, но не транскрипты — за них отвечает DSH.
