# Браузер для агента: moli

Проверено 26.10.2026 на moli 1.1.19 (Windows x64). Здесь: зачем браузер, почему
moli, как он подключён, где его границы и когда переключаться на Chrome.

## 1. Зачем

`web_fetch` в DSH — это HTTP-запрос. Для страниц, которые собираются
JavaScript'ом, он отдаёт оболочку. Показательный случай: `trendshift.io` через
`web_fetch` вернул навигацию и футер без единого репозитория, а через moli —
полный список из 25 позиций за 2.1 с. То же с любой SPA, лендингом на Next.js
и документацией с клиентским поиском.

Нужен браузер, который: исполняет JS, отдаёт результат **текстом** (а не
скриншотом), умеет снимать PNG, не требует ставить Chromium и не тянет
Node-зависимости в проект.

## 2. Почему moli

| Критерий | Что даёт moli |
|---|---|
| Установка | один бинарник 102 МБ, без зависимостей и без браузера в системе |
| Вывод | `--dump markdown / html / semantic_tree_text / json / screenshot / pdf` |
| JS | свой движок: V8 + Servo/Stylo + Taffy, не обёртка над Chromium |
| Автоматизация | CDP, WebDriver Classic и BiDi из того же бинарника (`moli serve`) |
| Лицензия | Apache-2.0 / MIT |
| Память | по заявлению авторов ~92 МиБ на задачу против ~697 МиБ у Chrome |

Замеры на этой машине: `trendshift.io` — 2.1 с на markdown, страница истории
репозиториев — 11.4 с на semantic tree (139 КБ текста), скриншот `example.com`
— 80 КБ PNG.

Важно: moli **не отдаёт MCP сам**. У него есть только CLI и CDP, поэтому MCP-слой
наш — `tools/browser_mcp.py`.

## 3. Как подключено

```
.tools/moli/pkg/moli-v1.1.19-x86_64-pc-windows-msvc/moli.exe   бинарник (.gitignore)
tools/browser_mcp.py                                           MCP-обёртка
tools/mcp_stdio.py                                             общий stdio-протокол
tests/test_browser_mcp.py                                      47 проверок
```

Бинарник скачан из релиза и сверен с `sha256` из GitHub API
(`708b9353…8525`), а не установлен через `irm … | iex`. Это единственное
отличие от официального сценария и оно осознанное: скрипт-в-пайп сложно
проверить, а хеш — можно.

Инструменты у модели (после перезапуска приложения):

| Инструмент | Что делает |
|---|---|
| `mcp__browser__fetch_page` | страница → markdown / html / semantic / json; `eval` — действие до снятия; `fresh` — мимо кэша |
| `mcp__browser__page_screenshot` | PNG в `.browser/`, картинка приходит вложениями; `engine` — `auto`/`moli`/`chrome` |
| `mcp__browser__page_eval` | одно JS-выражение на живой странице |
| `mcp__browser__session_start` | постоянный CDP-эндпоинт `moli serve` для Playwright/Puppeteer |
| `mcp__browser__session_status` / `session_stop` | жив ли эндпоинт, погасить |

Поведение по умолчанию:

1. `moli fetch --wait done`;
2. если ответ короче 1200 символов и селектор не задан — повтор с `--wait networkidle`;
3. если и это оболочка — **fallback на headless Chrome**: `--dump-dom`, затем
   HTML→текст своим парсером (ссылки сохраняются как markdown, скрипты и стили
   выбрасываются). В ответе появляется пометка `> источник: Chrome`.

Скриншоты: viewport по умолчанию снимает Chrome (у moli нет CJK-шрифтов, китайский
текст превращается в квадраты), полную страницу — moli (`full: true`; Chrome так не
умеет без CDP). `engine` позволяет выбрать движок руками; при отказе одного
срабатывает второй.

Кэш: одна и та же страница с теми же параметрами не качается повторно в течение
10 минут (до 64 записей в памяти процесса). `fresh: true` — принудительно заново.

Выбор движка для скриншота (`engine: auto`):

* **moli** — обычные страницы: он рисует кадр целиком, без пойманных анимаций
  появления (`--delay-ms 300`);
* **Chrome** — если в тексте страницы есть иероглифы (CJK): у moli нет для них
  шрифтов. Проверка стоит одного дополнительного чтения страницы и кладёт его
  в кэш, так что следующий `fetch_page` с теми же параметрами уже бесплатен;
* **moli** — всегда для `full: true`: Chrome без CDP снимает только viewport.

Размер viewport (`width`/`height`) понимает только Chrome: у moli такого флага
нет, он снимает своим. И у moli, и у Chrome встречаются страницы, которые в
headless остаются пустыми: тяжёлый WebGL/канвас-герой рисует только настоящий
браузер (проверено на `linear.app` — оба движка отдают тёмный кадр). Это предел
headless, а не дефект обёртки; для таких страниц нужен CDP-путь.

Chrome-путь не соблюдает `--block-private-networks` (это флаг moli), поэтому
локальные и приватные адреса в него не уходят: обёртка проверяет хост сама и
пропускает fallback, если `allow_private` не выставлен явно.

Профиль Chrome — в `%TEMP%\dsh-chrome-profile`, а не в рабочей папке: она может
лежать в OneDrive, где запись профиля стоит секунды. `--virtual-time-budget`
не используется: на живой странице с опросами он превращает 1 с в 23 с.

### Интерактивная сессия

`session_start` поднимает `moli serve --layout` на `127.0.0.1:9222` (запуск ~0.4 с,
CDP отвечает как `Chrome/145`) и возвращает адрес. Дальше нужен внешний клиент —
Playwright по `connectOverCDP`, Puppeteer или свой скрипт. Это отдельный путь,
потому что говорить по CDP — это WebSocket, а тянуть клиент в Python-обёртку
значит нарушить правило «только стандартная библиотека».

Для одиночного «кликнуть и прочитать» сессия не нужна: `fetch_page` с `eval`
выполняет выражение после готовности страницы и снимает результат одним запуском:

```json
{"url": "https://example.com/app", "eval": "document.querySelector('.more').click()"}
```

```powershell
# проверить руками, без DSH
python tools/browser_mcp.py            # ждёт JSON-RPC в stdin
```

## 4. Проверка на живых страницах

Задача: `trendshift.io/topics` — клиентская страница, которую не берут ни
`web_fetch`, ни наш RSC-парсер (в HTML нет `initialData`).

| Движок | Время | Результат |
|---|---|---|
| `moli --wait done` | 2.1 с | 5962 символа, 64 ссылки на темы |
| `moli --wait networkidle` | 2.5 с | 6694 символа, 79 ссылок (полный каталог) |
| Chrome `--dump-dom` (прогретый профиль) | 1.0 с | 131 КБ HTML, 64 ссылки; markdown не умеет |
| `web_fetch` | — | оболочка без тем |

Срабатывание fallback проверено на `excalidraw.com`: moli отдал 390 символов,
Chrome — полноценный текст, весь путь 8.8 с. На `linear.app` moli справился сам
(3101 символ, fallback не понадобился).

Скриншоты того же `trendshift.io`: оба движка рисуют вёрстку, но у moli
**не хватает шрифтов для CJK** — китайские описания репозиториев превращаются
в квадраты. Для текста это неважно (извлекается сам текст), для картинки — важно.
Поэтому viewport теперь по умолчанию снимает Chrome, а полную страницу — moli.

Отсюда два вывода: (1) moli нужен правильный `wait` — `done` не всегда ждёт
догрузку; (2) Chrome точнее в пикселях и стартует быстрее прогретым профилем,
но отдаёт HTML, а не готовый текст.

## 5. Границы и риски

* **Проект молодой.** Репозиторий создан 10.08.2026, 453 открытых issue,
  версия 1.1.19. Заявления «production-ready» — от авторов, не от нас.
* **Свой бенчмарк против него же.** На Lexbench (их корпус) moli проходит
  81.9% задач против 99.8% у Chrome. На смешанном крауле по 192 сайтам —
  53.6% полезных страниц против 52.6% у Chrome. То есть «лучше Chrome» — только
  в памяти и цене, не в полноте.
* **Нет подписи кода.** Windows SmartScreen может ругаться на первый запуск.
* **Неполный CDP.** Часть протокола возвращает явные ошибки — для интерактивных
  сценариев (клики, формы) это надо проверять отдельно, `fetch` их не покрывает.
* **Контент — недоверенный.** Moli исполняет JS страницы; инструкции из текста
  страницы модель выполнять не должна. Это записано в `instructions` сервера.
* **Нет MCP из коробки.** При обновлении moli меняется CLI — обёртка может
  отстать; ломается громко (`ToolError`), а не молча.

## 6. Когда переключаться на Chrome

Для текста и viewport-скриншотов переключение автоматическое. Руками Chrome
остаётся нужен для интерактивных сценариев через CDP (логин, клики, загрузка
файла): `session_start` + Playwright, либо Chrome DevTools MCP как альтернатива
с более полным протоколом.

Практическое правило: `fetch_page` первым; если он вернул пометку
`> источник: Chrome` — значит moli не справился, и для этой страницы дальше
надо сразу просить `wait: "networkidle"` или селектор.

## 7. Что осталось

* **Замена `web_fetch` целиком — сознательно не делается.** Это встроенный
  инструмент DSH, а не наш код: выключать его — решение владельца профиля, а не
  побочный эффект задачи. Сейчас модель выбирает между двумя путями сама.
* Кэш живёт в памяти процесса: после перезапуска MCP-сервера он пуст.
* Скриншот full-page через Chrome (без moli) требует CDP, а не `--screenshot`.
