# Процесс агентской разработки: анализ источников и целевая архитектура

Дата: 15.11.2026. Статус: **проектный документ**, ничего не реализует и не меняет поведение
системы. Источники: презентация «OpenSpec в работе команды» (26 слайдов, OpenSpec 1.15.0)
и учебник «Агентные пайплайны. Практический учебник» (издание 1 от 12.09.2026, 34 стр.).
Оба разобраны по пунктам; затем сведены в одну архитектуру и план внедрения.

Документ опирается на уже существующий в этом репозитории контрольный слой (`harness/`,
`docs/ARCHITECTURE.md`, `docs/ANALYSIS.md`, `docs/ROADMAP.md`, `docs/PLUGINS.md`) и не
переписывает его замысел: он добавляет недостающий **продуктовый уровень изменения** и
соединяет его с уровнем задачи.

---

## 0. Кратко: что получилось и что с этим делать

1. **Два источника — это два разных слоя, а не два конкурирующих процесса.**
   OpenSpec отвечает на вопрос «что и зачем строим, кто и как это согласовал»;
   учебник — «как агент выполняет задачу и почему ему нельзя верить на слово».
   Их надо соединить, а не выбирать между ними.
2. **Главный недостающий элемент — уровень изменения (change), а не роли.**
   `harness` управляет задачей (бриф → воркер → вердикт → коммит), OpenSpec описывает
   изменение (proposal → specs → design → tasks → release → archive). В целевом процессе
   это **два вложенных автомата**: состояние изменения и состояние задачи.
3. **Договорённость между ролями — это версионированный артефакт + запись review + SHA,
   а не чат.** Передача «на словах» не воспроизводима; OpenSpec это уже требует, harness
   умеет привязывать решение к версии — это надо распространить на все артефакты.
4. **Трассировка должна быть машинно проверяемой:** бизнес-цель → `REQ` → `CASE` →
   критерий приёмки (`AC`) → задача → вердикт → коммит → приёмка. Иначе «связано со
   спекой» — это утверждение, а не свойство.
5. **Права распределяются по артефактам, а не по людям:** BA/SA пишут только
   `product-specs`, DEV — только свой сервис, QA — кейсы и тесты, оркестратор — никогда
   продукт, верификатор — только `evidence/`, политику меняет только человек.
6. **Управление двухконтурное:** инструкция — рекомендация, детерминированный хук —
   ограждение. Но хук — не песочница, а review — не доказательство; каждое «защищено»
   должно называть, чем именно и что остаётся открытым.
7. **Автономия ограничена:** три попытки, бюджеты, таймауты, порог GAP, эскалация с
   пакетом «проблема → влияние → доказательства → варианты». Человек — на необратимых
   решениях: бизнес-правила, приёмка, политика, исключения.
8. **DSH даёт готовые кирпичи:** пресеты ролей, `ctx.tools.guard()`, approvals/`ask`,
   Agent Teams, workflow, worktree, forge/webhook, OTel, поиск по сессиям, skills.
   Писать надо процессное ядро и тонкий слой над ним, а не ещё один фреймворк.
9. **Главные риски** — не «агент напишет плохой код», а: два источника истины,
   дрейф `spec_ref`, перформативный review, человек как узкое место, prompt injection
   через требования и стоимость церемонии. Лечатся классами риска, метриками и аудитом.
10. **Порядок внедрения:** пилот одного изменения → change-FSM и Ready-гейт → роли-пресеты,
    скиллы и guard → QA baseline/candidate и приёмка → UI/CI и наблюдаемость → параллелизм.
    Сначала необратимое (выпуск непроверенного), параллелизм — последним.

### Допущения анализа

* **A1.** Роль — это контракт прав и артефактов; её может исполнять человек или агент.
  Бизнес-решения, приёмку и изменение политики принимает человек (агент готовит черновик).
* **A2.** `product-specs` — отдельный Git-репозиторий; каждый сервис — свой репозиторий
  со своими ветками, сборками и PR (модель презентации).
* **A3.** Доступны Git/PR и CI; OpenSpec 1.15.0 используется как инструмент планирования,
  а не как источник истины о процессе.
* **A4.** `harness` остаётся управляющим процессом на Python 3.10+ (stdlib), DSH — среда
  агентов; связь между ними — стабильный протокол, а не импорт внутренностей.
* **A5.** Цель — не максимальная бюрократия, а воспроизводимый маршрут с доказательствами
  и **разными уровнями строгости** для разных классов риска.
* **A6.** Всё, что требует семантического суждения (полнота требований, осмысленность
  теста, качество дизайна), не выдаётся за машинную гарантию; для этого есть review,
  evals и человек.

## 1. Источник A: «OpenSpec в работе команды»

### 1.1. Что это за документ

Презентация для команды большого проекта, которая переводит требования, технические
решения и тестовые кейсы из wiki в общий Git-репозиторий `product-specs` и договаривается,
как роли BA / SA / DEV / QA работают с одной версией изменения. Основа — общий регламент
и четыре ролевые инструкции; используется OpenSpec 1.15.0. Цель встречи сформулирована
честно: показать, **где теперь живёт изменение** и что делает каждая роль; профессиональные
обязанности не меняются, меняются артефакты, способ согласования и связь с реализацией.

Важно, что это **не описание автоматизации**. Инструмент хранит файлы и проверяет их
структуру; согласование, приёмка и дисциплина остаются за командой. Это одновременно
сильная сторона документа (он не врёт о возможностях инструмента) и его главный пробел
(ничто не мешает агенту или человеку обойти договорённость).

### 1.2. Целевая модель (слайды 2–6)

1. Модель рассчитана на большой проект: требования, технические решения и кейсы — в
   общем `product-specs`; код — в репозиториях сервисов. Ролевые правила и порядок
   согласований команда утверждает отдельно.
2. **Было → стало:** BA держал требования в wiki → требования в общем репозитории;
   SA — технические документы в wiki → дизайн и контракты рядом с требованиями;
   DEV — код в репозитории сервиса → код по **утверждённой версии плана**;
   QA — автотесты на Reqnroll → сценарии рядом с требованиями.
   Содержание работы ролей не меняется; меняется носитель договорённости.
3. Ключевое изменение: обсуждение заканчивается **правкой общего файла и review**, а не
   сообщением в чате. Ссылка на конкретную версию позволяет понять, что именно должна
   реализовать команда сервиса.
4. Пилот начинается с одной области; подтверждённые правила переносятся из wiki, после
   чего wiki может ссылаться на репозиторий или публикуемое из него представление.
5. **Устройство репозиториев:** `openspec/specs/` — действующие требования;
   `openspec/changes/` — планируемые изменения и решения; `cases/` и `contracts/` —
   сценарии и интерфейсы. Общий репозиторий **не** делает проект монорепозиторием кода:
   у сервисов остаются независимые ветки, сборки и PR.
6. **`spec_ref` — полный Git SHA согласованного плана.** Ветки `main` недостаточно:
   она меняется. В сервисном PR указывают полный SHA плана, а в отчёте отдельно
   сохраняют SHA каждого сервиса. Для пилота достаточно обычного checkout; beta-механизм
   `stores` можно рассматривать позже — он не распределяет задачи между сервисами и не
   синхронизирует Git автоматически.

### 1.3. Словарь и четыре артефакта изменения (слайды 7–8)

1. `proposal.md` — зачем меняем продукт и что входит в объём.
2. `specs/` — какое поведение требуется и какие примеры его объясняют.
3. `design.md` — как сервисы реализуют поведение и взаимодействуют между собой.
4. `tasks.md` — кто и в каком репозитории работает и чем подтвердит результат.

Термины: **change** — папка одного изменения (`chg-142-cancel-order`); **артефакт** —
обычный файл в Git, который обсуждают через review; **capability** — долговременная
возможность (например, отмена заказа). Внутри активного изменения `specs` содержит
**дельту** к действующим требованиям: только новые, изменённые и удалённые правила.
Для реализации читают оба текста. Связи артефактов и порядок — стандартная схема
spec-driven; назначение владельцев BA/SA, распределение по репозиториям и требование
review — договорённость команды, а не свойство инструмента.

### 1.4. Запуск и карта команд (слайды 9–13)

1. Первый запуск: терминал и чат агента в `product-specs`; `openspec init`,
   `openspec config profile`, `openspec update`; выбрать AI-инструмент; включить
   расширенные `new`, `continue`, `verify` вместе с `explore`, `apply`, `update`,
   `archive`, затем применить `openspec update`. `profile` меняет настройки на машине
   участника.
2. Действия в чате: `/opsx:explore Отмена заказа`, `/opsx:new chg-142-cancel-order`,
   `/opsx:continue ...`. Синтаксис зависит от инструмента (Claude Code `/opsx:`,
   Cursor `/opsx-`, Codex `$openspec-`); примеры переключаются в нижней панели.
   Команды без слэша выполняются в терминале; `/opsx` — в чате AI-инструмента.
3. **Карта действий:** `explore` — разобраться и задать вопросы; `new` — создать папку
   изменения; `continue` — создать следующий артефакт; `apply` — выполнить выбранные
   задачи; `verify` — найти расхождения плана и кода; `update` — согласовать правки в
   плане; `archive` — архивировать принятое изменение. `propose` и `ff` собирают план
   целиком; для передачи работы между ролями используют `new` и `continue` с review
   каждого результата.
4. **Чего нет:** отдельной команды `extract`. Если под извлечением имеется в виду разбор
   wiki, это обычный запрос в `explore` («извлеки правила, примеры и вопросы, сохранив
   ссылки на источники»), а не встроенная команда.
5. `continue` создаёт **один следующий готовый артефакт**, а не исправляет существующий;
   для правок — `update`. Стандартный путь: proposal → specs → design → tasks. Если
   готовы несколько, агент берёт первый готовый по схеме.
6. `propose` создаёт планирующие артефакты в один проход — удобно для согласованного
   простого изменения, но не заменяет решения BA/SA. `sync` обновляет действующие specs
   без архивирования; в этой модели его нельзя использовать для ранней публикации
   будущего поведения — продвижение выполняется при закрытии после приёмки.
7. Перед работой агента надо открыть `product-specs` и **дать доступ только к нужным
   источникам**. Ссылки на wiki недостаточно, если агент не может её прочитать: нужен
   коннектор или экспорт с указанием версии.

### 1.5. Маршрут изменения и BA (слайды 14–18)

1. Путь одного изменения: **01 Проблема** (BA описывает цель и бизнес-правила) →
   **02 Общий план** (SA, DEV и QA уточняют решение) → **03 Реализация** (каждый сервис
   получает свой PR) → **04 Проверка** (QA проверяет точные версии) →
   **05 Приёмка** (BA принимает бизнес-результат).
2. Это карта взаимодействия, а не жёсткий конвейер: на этапе общего плана разработчик
   проверяет реализуемость, QA — проверяемость, SA — контракты и технические риски.
   Один владелец изменения собирает планирующий PR; BA, SA, QA и владельцы затронутых
   сервисов подтверждают свою часть; после merge фиксируется точная версия плана.
   Реализация и автоматизация могут идти параллельно; новое правило возвращает команду
   к файлам требований и кейсов, но обсуждение должно сохранять связь с актуальной
   редакцией плана.
3. **BA:** определяет, что пользователь должен получить. Артефакты — `proposal.md`,
   `specs/`. Шаги: изучить текущее поведение (действующие правила и кейсы) → описать
   цель и границы → сформулировать правила (права, условия, ошибки, результат) →
   разобрать примеры вместе с QA (успех, отказ, граничные случаи) → согласовать итоговый
   текст и передать план SA. Результат — однозначные критерии приёмки.
4. Хорошее правило содержит **наблюдаемый результат**. «Удобно отменить заказ» не
   позволяет определить готовность; нужны допустимое состояние заказа, права покупателя
   и результат операции. QA помогает выбрать примеры **до** разработки. SA получает
   согласованный бизнес-смысл. Если технические уточнения меняют обещанный результат,
   BA снова проверяет итоговый diff. После выпуска BA принимает результат в выбранной
   опорной среде.
5. **Роль AI:** может подготовить черновик и список вопросов; решение о бизнес-правилах
   остаётся у BA и владельца продукта. В диалоге `explore` агенту явно запрещают менять
   файлы и писать код; ожидаемый результат — правила со ссылками на источники, отделение
   фактов от предположений и вопросы, от которых зависит приёмка. Проверки BA: правила
   соответствуют источникам; неизвестные условия отмечены вопросами; бизнес-решения
   подтверждает BA.
6. Сохранение согласованного: `new` создаёт папку изменения и останавливается; каждый
   `continue` выполняется отдельно и останавливается на review; после `proposal.md` BA
   проверяет цель и объём; после `specs` — правила и примеры. Передача SA идёт через
   сохранённые артефакты и планирующий PR; **SA не нужна история чата BA** — после merge
   у него есть цель и правила из файлов.

### 1.6. SA (слайды 19–21)

1. SA определяет, как сервисы обеспечат нужное поведение. Артефакты — `design.md`,
   `contracts/`, `tasks.md`. Шаги: проверить текущую архитектуру (владельцы данных,
   затронутые сервисы) → уточнить системное поведение (права, повторы, гонки, сбои) →
   согласовать дизайн и контракты (API, события, совместимость) → разбить работу по
   сервисам (repo, зависимости, способ проверки каждой задачи) → определить выпуск и
   восстановление. Результат — выполнимый план без скрытых решений.
2. Фактическую архитектуру надо **проверять по коду**, а не восстанавливать по старым
   документам. Внешне наблюдаемые ограничения входят в требования; внутренний способ
   реализации — в `design.md`. Контракты должны пройти review **владельцев производителя
   и потребителя**. В `tasks.md` каждая задача получает репозиторий, зависимость и способ
   доказать выполнение; тесты сервиса входят в его группу задач; в конце — интеграционные
   проверки всего изменения.
3. **Вопросы, способные изменить требования, архитектуру или объём, блокируют Ready.**
   Наличие заполненных файлов само по себе эти вопросы не решает.
4. В диалоге агент читает код сервисов по указанным checkout и версиям, сравнивает
   варианты передачи отмены, сбои и повторы, показывает вопросы к BA и владельцам
   сервисов; файлы не меняет и код не реализует. Доступный workspace и точные версии
   источников задаёт человек; в запросе нужны абсолютные пути и SHA, а не «по указанным
   версиям» без значений. Если нужного кода нет в workspace или агент не имеет доступа,
   он **обязан назвать отсутствующий источник**, а не выдавать предположение за
   изученную архитектуру. Обсуждение с агентом не является согласованием команды.
5. Оформление: `continue` создаёт `design.md`; SA и владельцы сервисов делают review;
   отдельным запросом сохраняют согласованный API в `contracts/` **внутри change**, не
   меняя действующий корневой `contracts/`; следующий `continue` создаёт `tasks.md`
   с задачами DEV и QA. Проверка дизайна предшествует генерации задач, чтобы агент не
   закрепил невыбранный вариант.
6. Отдельные файлы OpenAPI, Gherkin и traceability **не являются самостоятельными
   артефактами стандартной схемы** — их создают обычным запросом или через custom schema.
   Нельзя вызывать `continue contracts`, ожидая встроенную команду. Для реального
   контракта указывают полный путь, согласованную структуру, версию и инструменты проверки.

### 1.7. Гейт Ready (слайды 22–23)

1. Ready — предлагаемое командой состояние «план готов к реализации»: команда согласовала
   одну редакцию изменения. Подтверждают четыре части: BA — бизнес-правила и границы;
   SA — дизайн и контракты; QA — проверяемые сценарии; DEV — реализуемость по сервисам.
2. **OpenSpec не подтверждает одобрение BA или SA.** Его команды показывают состояние
   артефактов и проверяют структуру. Зелёный `openspec validate` полезен, но не доказывает
   полноту бизнес-правил или работоспособность системы. Review ролей и проверки CI
   дополняют друг друга.
3. После review владелец изменения сливает планирующий PR и сообщает полный SHA.
   `spec_ref` записывается последующим PR в файл учёта, чтобы не пытаться ссылаться на
   commit самого этого файла.

### 1.8. DEV (слайды 24–26)

1. Вход: `change-id` и `spec_ref`, задачи своего сервиса. Шаги: получить точную версию
   плана (checkout `product-specs` по Git SHA) → прочитать весь контракт поведения
   (действующие specs, дельту, дизайн, кейсы, API) → реализовать свою часть, ограничив
   работу выбранными repo и задачами → проверить и открыть PR с тестами и ссылками на
   план и требования → передать QA фактическую сборку (итоговый commit и условия запуска).
2. Разработчик **не копирует требования** в новую редактируемую папку своего сервиса:
   он читает утверждённую версию общего репозитория и реализует только назначенную часть.
3. В сервисном PR должны быть `change-id`, `spec_ref`, номера задач, связанные требования,
   контракт и результаты проверок. Итоговый SHA после merge может отличаться от SHA
   рабочей ветки (например, squash merge). Слияние PR не означает развертывание или общую
   приёмку изменения.
4. **Ограничение области — критическое место.** `apply` не распределяет центральный
   `tasks.md` по репозиториям; агенту нужны точные пути и номера задач, а область правок
   ограничивается запросом, настройками доступа и review команды, **а не встроенным
   multi-repo маршрутизатором**. Если центральный checkout доступен только для чтения,
   используется обычный запрос на реализацию по точным спецификациям, а прогресс
   обновляется отдельным PR. Нельзя запускать `apply` из сервиса без корректно
   выбранного корня и нельзя создавать второй набор требований как побочный эффект.
5. Схема одной сессии: `product-specs` (change на согласованном `spec_ref`, рабочая ветка
   для отметок задач) + checkout сервиса (ветка реализации). Агент может обновлять
   **только отметки разрешённых задач** в `tasks.md`; требования и дизайн сохраняют
   согласованное содержание. Эти отметки передаются отдельным PR общего репозитория.
6. После ответа агента человек читает diff, проверяет результаты и оформляет сервисный
   PR со `spec_ref`. Если задача включает проверку после merge или развертывания, она
   остаётся незавершённой до этой проверки. При неясном правиле агент останавливается и
   передаёт вопрос SA и BA.

### 1.9. QA (слайды 27–31)

1. QA готовит примеры заранее и доказывает результат. Артефакты — `.feature` и bindings,
   `verification.md`. Шаги: проверить тестируемость правил (состояние, действие,
   результат) → связать требования с кейсами (каждому `REQ` — проверка и `CASE`) →
   согласовать Gherkin с BA (будущие сценарии — внутри изменения) → добавить bindings и
   выполнить тесты на выбранных версиях сервисов → передать доказательства приёмки
   (версии, `CASE`, отчёт).
2. QA участвует в анализе: если expected result неизвестен, тест нельзя корректно
   написать; если результат нельзя наблюдать, QA и SA **заранее** определяют способ
   проверки и уровень теста. Не все комбинации нужно проверять через end-to-end: unit,
   integration, контрактные и приёмочные проверки имеют разные задачи, но связь с
   обязательным правилом должна сохраняться.
3. Отчёт содержит версию требований, версию runner и bindings, версии сервисов, среду и
   результаты обязательных `CASE`. Новый тестовый код может проверять прежний контракт —
   тогда требования и runner берут из отдельных checkout и фиксируют оба SHA.
4. В диалоге сначала обсуждаются `REQ`→`CASE` и кандидатные сценарии; BA подтверждает
   смысл каждого сценария; затем явный запрос сохранить согласованные `.feature`
   (русский Gherkin, сохранить незатронутые сценарии, не придумывать expected result,
   не писать bindings). Проверки QA: BA согласовал смысл; все обязательные `REQ` имеют
   проверку; текущий регресс не заменён будущим набором.
5. `apply` по QA-задаче добавляет bindings в тестовый проект и выполняет проверки, не
   меняя правила и код сервисов. `verify` сопоставляет specs, design, tasks и
   доказательства; всё, что недоступно (код второго сервиса, результаты CI), помечается
   **«не проверено»**. Отчёт агента дополняет code review и CI, но **не подтверждает
   приёмку за BA**; `verify` не заменяет фактический прогон и не создаёт отсутствующий
   отчёт CI; `openspec validate` не является тестированием продукта.
6. **Два режима тестов.** Baseline — принятое поведение: текущие сценарии на принятой
   версии системы. Candidate — выбранное изменение: будущие версии затронутых кейсов и
   регресс остальных возможностей; запускается на версиях сервисов, реализующих
   изменение. Принятые сценарии — в `cases/current`; будущая полная версия затронутого
   `.feature` — в `changes/<id>/cases`. При сборке candidate изменённый файл заменяется,
   новые добавляются, удалённые учитываются явно, незатронутые сохраняются. Нельзя
   оставлять устаревший сгенерированный тестовый код; discovery и фактический отчёт
   должны подтверждать ожидаемые `CASE`; **успешный запуск нуля тестов не считается
   проверкой**.

### 1.10. Изменения, update и закрытие (слайды 32–35)

1. Два разных случая: **изменилось бизнес-правило** → BA обновляет правило, SA и QA
   проверяют, команда согласует новую редакцию, разработчики переходят на новый
   `spec_ref`; **код нарушает уже согласованное правило** → DEV исправляет код, QA
   повторяет проверку, принятое правило остаётся основанием проверки. Нельзя незаметно
   менять expected result под текущий код и нельзя продолжать реализацию по старому SHA
   после изменения договора без проверки влияния.
2. Если меняется только внутренняя реализация при сохранении внешнего поведения,
   достаточно согласовать техническое решение и при необходимости обновить `design`;
   выдуманное бизнес-требование не нужно.
3. `update` — для пересмотра существующего плана: найти противоречия в specs, design,
   tasks; предлагать правки по одному артефакту; после подтверждения внести
   согласованные изменения; код не менять. Проверки: правка отражает решение BA;
   затронутые SA и QA повторили review; DEV получил новый `spec_ref`. `update` не
   реализует код и не создаёт отсутствующий артефакт; для первого создания — `continue`.
   Если меняется сама цель или объём становится независимым — рассматривается новое
   изменение.
4. **Закрытие:** 01 выпуск (все нужные сервисы доступны в опорной среде) → 02 проверка
   (QA сохраняет версии и результаты `CASE`) → 03 приёмка (BA подтверждает бизнес-
   результат) → 04 закрывающий PR (действующие specs, контракты и кейсы обновляются;
   `openspec archive` архивирует изменение и обновляет specs; продвижение кейсов и
   контрактов команда выполняет отдельно).
5. Опорная среда в регламенте — production с включённой для целевой аудитории функцией;
   команда может выбрать другую, но обязана использовать её последовательно. Слияние
   сервисного PR само по себе не закрывает изменение нескольких сервисов: если один
   сервис не выпущен, change остаётся активным или объём заранее разбивается на
   независимо принимаемые изменения.
6. После общей приёмки владелец создаёт закрывающий PR: кандидатные кейсы и контракты
   продвигаются в действующие каталоги, `openspec archive` обновляет `openspec/specs` и
   переносит change в архив; BA, SA и QA проверяют итоговый diff. `archive` может
   предупредить о неполных задачах, но не заменяет обязательные условия команды: сначала
   проверяются отчёты и все чекбоксы; `sync` при необходимости обновляет действующие
   specs, затем change переносится в архив. Дополнительные кейсы и контракты стандартным
   `archive` не продвигаются — команда готовит их отдельно в том же PR.

### 1.11. Пилот (слайды 36–37)

1. Первое изменение: одна возможность, один владелец, один-два сервиса, назначенные
   обязательные reviewers и опорная среда. Роли: BA — правила и приёмка, SA — решение и
   контракты, DEV — реализация и проверки, QA — сценарии и доказательства.
2. Признак успешного пилота: **любой участник может найти согласованное правило, версию
   реализации и проверку результата, не восстанавливая переписку**. Команда проходит
   весь цикл, включая выпуск и продвижение действующих артефактов.
3. После пилота обсуждают, какие согласования помогли, где возникли очереди и какие
   проверки стоит автоматизировать; затем расширяют процесс. Переносить всю wiki до
   первого изменения не требуется.

### 1.12. Что этот источник даёт и чего в нём нет

**Сильное:** артефактная передача работы (SA не нужен чат BA); `spec_ref` как полный SHA
(воспроизводимость); разделение planning PR и сервисных PR; явные роли и четыре
подтверждения Ready; QA участвует до разработки; два режима тестов; честные оговорки о
том, что validate не доказывает полноту; жизненный цикл до архива; пилот с критерием
успеха.

**Ограничения (важно не принять за гарантии):**

* ограничение области правок в `apply` обеспечивается **запросом, настройками доступа и
  review**, а не маршрутизатором; следовательно, агент с полными правами может выйти за
  область, и это ловится только review/CI;
* нет ограничения автономии: числа попыток, бюджета, таймаута, эскалации;
* нет контракта вердикта и привязки «PASS» к версии результата; `verify` — это отчёт,
  а не объект с доказательствами;
* `Ready` — социальное состояние; «review прошли» нигде не записано как объект;
* трассировка `REQ`→`CASE` описана, но не проверяется машинно; `tasks.md` не связан с
  критериями приёмки формально;
* нет измерений качества review/QA (что пропускают), нет стоимости и наблюдаемости;
* нет безопасности: prompt injection через требования/тикеты, доступ агента к лишним
  источникам, секреты, утечки;
* предполагаются доступные люди во всех ролях и дисциплина, которой ничто не мешает;
* команды/пути зависят от версии инструмента и конкретного AI-клиента.

## 2. Источник B: учебник «Агентные пайплайны. Практический учебник»

### 2.0. Устройство книги

Издание 1 от 12.09.2026, 34 страницы, 7 глав и приложение. Основной текст — Антон;
комментарии, пояснения терминов, учебные примеры, этапы реализации и разбор — Астра
(ИИ-ассистент); ссылки [1]–[12] — проверенные первоисточники. Главы 1–6 начинаются
авторским текстом, затем идут пояснения и план внедрения; глава 7 целиком написана
Астрой; в приложении — шаблоны артефактов и контрольные вопросы. Книга честно оговаривает,
что приведённые количества правил/хуков не являются аудитом, а предложения по реализации —
рекомендации, а не результаты испытаний.

### 2.1. Глава 1. Основной цикл

1. **Роли.** Главный агент (оркестратор) не пишет код — ни одной правки, включая
   «мелочи». Он формулирует задачи, запускает исполнителей, собирает вердикты и
   коммитит. Код и тесты пишут воркеры-сабагенты; проверяют отдельные read-only
   верификаторы. Автор никогда не проверяет сам себя.
2. **Цикл: бриф → воркеры → верификация → loop.** Бриф — самодостаточный пакет:
   объём, список файлов, выдержки из спеки, правила, критерии приёмки, а при генерации
   кода — предопределённый контракт имён (testid, API, i18n-ключи, пропсы). Воркер
   получает всё в промпте, а не ищет по репозиторию.
3. **Воркеры.** Для нового модуля — два агента параллельно: тест-агент пишет
   поведенческие тесты из брифа, не видя кода; код-агент пишет реализацию, не видя
   тестов. Тесты — исполняемая спецификация; тест-агент не заражён реализацией,
   реализация не подгоняется под собственные тесты. Расхождение имён предотвращает
   контракт из брифа; остаток ловит верификатор. При багфиксе — TDD-последовательность:
   падающий тест → отдельный фикс-агент → верификатор.
4. **Верификаторы.** Каждый вывод проверяют read-only агенты параллельно:
   спек-верификатор сверяет дифф с брифом и спекой (точность, полнота 1:1, отсутствие
   выдуманного, регрессии; итог — замечания + PASS/FAIL); адверсальный подключается,
   когда дифф касается денег/платежей/безопасности, и обязан предъявить конкретный
   сценарий поломки («что реально произойдёт с балансом при этом payload»), а не
   перечитать спеку. Пройти без сценария нельзя.
5. **Loop.** FAIL → новый воркер, которому верификатор передал замечания **через файл**;
   оркестратор руками ничего не пересылает. Бюджет — максимум 3 итерации, дальше
   эскалация к человеку с сохранённым диффом. Бесконечных циклов нет.
6. **Правила, которые держат систему:** оркестратор не кодит; нет брифа — нет диспетча;
   нет неверифицированного вывода; модель по роли (сильная — брифам и верификаторам,
   дешёвая — коду; вручную не выбирают); каждая находка маршрутизируется (свой дифф —
   фикс, чужой/старый код — эскалация владельцу списком, «третьего ящика» нет); гейт на
   неоднозначность (неполная спека → вопрос человеку до запуска, а не молчаливый стаб);
   ключевые правила дублируются детерминированными shell-хуками; правило без хука
   считается незащищённым.
7. **Параллельная запись.** Read-only агенты работают параллельно всегда. Мутации — в
   трёх формах: пара «тест + код» в одном дереве (с запретом читать друг друга);
   независимые модули — изолированные worktree-цепочки бриф → воркер → верификатор →
   merge (merge + typecheck как мьютекс, волна закрывается одним коммитом); всё
   остальное — строго последовательно.
8. **Пояснения/этапы Астры.** Пайплайн — последовательность работ с условиями перехода;
   LLM — модель, агент — модель + инструменты + контекст + правила; разделение ролей
   распределяет права и информацию, но не доказывает независимость ошибок. Уточнения:
   независимая приёмка совместима с локальной самопроверкой исполнителя (право принять —
   у другого); контракт имён устраняет только расхождения в названиях, нужны типы,
   обязательные поля, коды ошибок, единицы, границы; бриф должен ссылаться на конкретную
   версию проекта и уметь запрашивать недостающий контекст; верификатору нужен доступ к
   исходной спецификации; запрет читать работу соседа в одном дереве — условность, пока
   среда технически разрешает чтение (для строгого «вслепую» — отдельные снимки и
   доверенный сборщик); адверсальный сценарий не обязан найти дефект, но обязан
   предъявить попытку, инвариант и наблюдаемый результат. Этапы: зафиксировать
   полномочия ролей; ввести единый формат брифа; запустить одну задачу последовательно;
   привязать приёмку к версии результата; проверить отказ и исчерпание бюджета; добавить
   параллелизм после устойчивого прохода.

### 2.2. Глава 2. Матрица хуков

1. **Принцип.** Каждое LLM-правило сопоставлено хуку — детерминированному скрипту на
   событие до/после вызова инструмента или при коммите. Матрица `RULE → HOOK →
   ENFORCEMENT`: ~60 правил, ~53 хука; правило без хука — видимая строка `coverage gap`,
   а не молчаливый пропуск.
2. **Три класса:** blocking (~40%) — deny, действие запрещено физически (оркестратору
   нельзя писать в `src/**`/`tests/**`, включая `sed -i`, redirect, tee; сабагенту нельзя
   мутации git и диспетчи; нельзя sleep; не прошли typecheck/eslint/секреты/ссылки —
   коммит заблокирован; диспетчеру 60 минут); soft (~30%) — разрешено, но предупреждение
   в контекст (наблюдения после воркера, GAP-эскалация, бюджет, дубли тестов, дрейф
   дерева); n/a (~30%) — детерминированной проверки нет, правило держится на инструкции,
   и это фиксируется открыто. Ключевое правило честности: advisory — не гейт;
   останавливает только deny; предупреждение взвешивается против бюджета, и тот, кто его
   перебивает, обязан назвать, какой бюджет управляет.
3. **Накрытые классы правил:** роли и границы; цепочка верификации (воркер без
   верификатора не пройдёт; вердикт записывается детерминированно; объём на одного
   верификатора ограничен); процессные гейты (план обязан содержать шаги пайплайна; GAP
   до запуска; из возврата агента извлекаются наблюдения); гигиена Bash (деструктивные
   команды, запрет sleep, ломалка циклов чтения, git-мутации называют дерево, работа
   сохраняется до revert); коммитные гейты (typecheck, ESLint, секреты в логах,
   pipeline-log, резолв ссылок, эфемерные ссылки); волны и worktree.
4. **Честность про дыры.** Часть правил без хука по осознанному решению (параллельные
   мутации вне worktree, обязательная обёртка тестов в timeout); под асинхронными
   dispatch часть post-хуков слепа; хуки ловят ошибки по привычке, а не намеренное
   уклонение — это названный residual. **Обслуживание:** хук, добавленный в сессии, не
   активен в ней же; изменение хука само проходит верификацию отдельным агентом;
   захардкоженный проектный литерал обязан попасть в чек-лист форка. **Зачем матрица:**
   без неё накапливаются три дефекта — правило расширилось, а хук проверяет старую
   формулировку; два хука с общей эвристикой разъехались; новое правило появилось без
   проверки.
5. **Пояснения Астры:** хук — обработчик события; детерминированность означает
   воспроизводимое правило вычисления, а не безошибочность и не полноту. Нельзя читать
   «40% blocking» как «40% безопасности»: одна незакрытая критическая операция важнее
   десятков закрытых мелочей. Надо разделять «неприменимо» и «проверка не реализована».
   В описании есть процессное противоречие: GAP и бюджет названы жёсткими, но попали в
   Soft — его нужно разрешить в конфигурации. PreToolUse может запретить вызов,
   PostToolUse выполняется после — последующая проверка не отменяет уже совершённую
   запись; поведение хуков зависит от версии среды. Перехват знакомых команд не равен
   изоляции прав: запись возможна через интерпретатор, дочерний процесс, библиотеку;
   надёжнее лишить роль ненужных возможностей на уровне среды, а хуками проверять
   бизнес-правила и порядок работ. Предлагаемый контракт строки матрицы: правило,
   проверка, решение, положительный тест, отрицательный тест, остаточный риск.
6. **Этапы:** реестр критических правил (полномочия записи, запрет запуска без брифа,
   актуальность вердикта, бюджет, сохранение работы); контроль вне изменяемого агентом
   контура; проверка входа/выхода каждого обработчика (схема события, таймаут,
   однозначный результат; отсутствие обработчика/сбой/некорректный ответ — закрывать
   переход); испытания в разрешённых и запрещённых случаях; финальный гейт отдельной
   точкой контроля; связь изменения политики с проверкой матрицы (общая запись причины,
   сначала проверка на известной разрешённой и запрещённой операции).

### 2.3. Глава 3. Принципы контроля

1. **Инициатор ≠ контролёр.** Воркер никогда не верифицирует свой вывод; оркестратор
   никогда не пишет код. Это four-eyes и разделение обязанностей, применённые к агентам:
   самоодобрение запрещено структурно, а не уговорами.
2. **Спецификация как эталон.** Вердикт выносится относительно формального артефакта
   (бриф, спека, §-ссылки), а не «выглядит нормально».
3. **Двухконтурное управление.** Поведение задаётся инструкцией (слабый контур), контроль —
   детерминированными хуками (сильный). «Инструкция — рекомендация, хук — ограждение».
4. **Ограниченная автономия.** Бюджет итераций (3), бюджет диспетчей, таймаут; система
   останавливает счёт и передаёт решение человеку.
5. **Полнота маршрутизации находок.** Каждый дефект — в один из двух треков (свой дифф —
   фикс, чужой код — батч-эскалация); «третьего ящика» нет.
6. **Внешний контур на границах.** Неоднозначность (GAP), edge case, исчерпание бюджета —
   точки выхода к человеку, а не к догадке агента. Автономия локальна, ответственность
   глобальна.
7. **Пояснения Астры:** независимость ролей — организационное свойство, независимость
   ошибок — эмпирический вопрос (общая модель, неверная спека, один бриф); её надо
   оценивать по реальным пропускам. Требования тоже нуждаются в проверке: нужен список
   доменных инвариантов, согласованный владельцем, и проверка противоречий с задачей.
   «Эскалировано» должно означать не только «записано», но и «назначен ответственный,
   известен статус»; нужны состояния находки (новая, подтверждена, назначена,
   исправлена, закрыта/принят остаточный риск). Старый дефект, делающий поставку
   небезопасной, может остановить работу в соответствующей части; возраст определяет
   исполнителя, но не влияние на выпуск. Не каждую неопределённость полезно отправлять
   человеку: обязательный вопрос — деньги, доступ, необратимые эффекты, противоречия
   критериев; обратимые технические детали внутри согласованных границ выбирает
   исполнитель и записывает. Порог надо утвердить заранее.
8. **Этапы:** описать защищаемые инварианты (повтор события не создаёт новую операцию;
   роль не расширяется из запроса; принятый результат соответствует версии требований);
   развести создание и утверждение (разные идентификаторы автора и принимающего;
   диагностические проверки исполнителю можно, самостоятельный выпуск — нет);
   реестр находок (finding_id, задача, серьёзность, доказательство, версия, владелец,
   статус, связь с исправлением; удаление без причины не допускается); порог эскалации
   (проблема, влияние, доказательства, варианты); испытать полноту обратной связи
   (неверный бриф, спорный FAIL, дефект вне диффа, превышение бюджета).

### 2.4. Глава 4. Перекличка с теорией надёжности

1. **Аналогии:** recovery blocks (верификатор — acceptance test, FAIL запускает alternate
   с сохранением состояния; бюджет 3 — ограничение попыток); N-version programming
   (пара «тест-агент вслепую к коду / код-агент вслепую к тестам» как проектная
   диверсификация каналов; общий контракт имён — общий спецификационный интерфейс);
   fault → error → failure (дефект ловится на стадии fault до коммита; эшелоны
   «инструкция → хук → верификатор → коммитные гейты» — defence in depth); common-cause
   failures (одинаковые агенты слепы одинаково; разделение моделей по роли и каналов
   снижает корреляцию, но требует измерения); watchdog (таймаут диспетча; смерть
   доставляется отдельным событием, чтобы не выглядеть нормальным завершением);
   interlock/fail-closed (хуки запрещают в неоднозначных случаях); checkpointing
   (сохранение состояния перед откатом; log first); graceful degradation (блокировка
   части шага паркуется); V-модель (тесты выводятся из спецификации независимо от
   реализации); PDCA (план → делать → проверять → улучшать с ограничением витков).
2. **Оговорки Астры:** пара «тесты + реализация» — не буквальный NVP (разные артефакты,
   не две реализации); recovery blocks — аналогия; fault/error/failure не соответствуют
   этапам git-процесса (различается граница наблюдения); совместный коммит журнала и
   кода улучшает прослеживаемость, но не создаёт WAL; разные модели и свежие контексты
   могут давать разные находки, но степень снижения общей ошибки надо измерять; несколько
   рубежей нельзя называть независимыми без проверки — общий неверный контракт пройдёт
   через тесты, реализацию и спек-верификатор одновременно; fail-closed полезен на
   переходе к опасной операции, но остановка всей системы не всегда безопасна — для
   каждого действия нужно определить безопасное состояние; таймаут должен иметь
   собственный статус. Учебный пример общей причины: потеряли слово «не» в требовании —
   тест-агент закрепил повторное начисление, код-агент реализовал, проверяющий прочитал
   только бриф; три роли согласны, требование нарушено; спасает сверка с первичным
   требованием и отдельно утверждённым инвариантом.
3. **Этапы:** каталог конкретных отказов (причина, ошибочное состояние, вред; неверный
   бриф, подложный PASS, потерянный возврат, гонка тестов, сбой сохранения); назначить
   рубеж обнаружения и восстановления; испытать контрольные точки (прервать и
   восстановить без потери работы и повторного внешнего эффекта); fault injection
   (остановить воркер, задержать ответ, повредить отчёт, дважды доставить завершение);
   измерить полезность каждого рубежа (какие дефекты ловят тесты, верификаторы и их
   сочетание; пересечения пропусков).

### 2.5. Глава 5. Пайплайн как конечный автомат

1. **Уровень 1 — цикл воркер/верификатор:** `CLAIM → BRIEF → DISPATCH_WORKER → VERIFY`;
   PASS → `COLLECT → COMMIT → CLAIM`; FAIL → `REWORK(iter+1) → VERIFY`; guard `iter < 3`,
   при `iter = 3` → `ESCALATE` (терминальная, дифф сохранён). Переходы охраняются:
   DISPATCH требует непустого брифа, COMMIT — записанного вердикта и pipeline-log,
   REWORK — бюджета.
2. **Уровень 2 — сам агент:** каждое действие — переход, на каждом ребре guard:
   PreToolUse — предикат перед переходом (deny запрещает переход, автомат остаётся на
   месте и получает причину); PostToolUse — пост-условие/наблюдатель (не блокирует, но
   оставляет след). Это guarded commands Дейкстры.
3. **Уровень 3 — время:** ожидание вне переходов запрещено (sleep запрещён); автомат
   событийный; единственный легальный таймер — watchdog dispatch (60 мин), ограничение
   пребывания в состоянии (clock constraint).
4. **Уровень 4 — параллелизм:** волна — N независимых копий лэйн-автомата (brief →
   worker → verify → merge → teardown), каждая в своём worktree; общий ресурс (главное
   дерево) защищён мьютексом на merge; закрытие волны — барьерная синхронизация и один
   закрывающий коммит.
5. **Уровень 5 — иерархия:** доска строк — множество параллельных автоматов с
   инвариантами (чистое дерево, чистый write-set); автомат агента вложен в автомат цикла,
   цикл — в план-цикл владельца (statechart по Харелу): ошибка не разрешается на своём
   уровне → эскалируется наверх как внешнее событие; ждущие состояния (PLAN-BLOCKED,
   ожидание решения владельца) — выход только внешним входом, сессия не блокируется, а
   переключается на другие строки.
6. **Пояснения Астры:** «почти готово» заменяется конкретным состоянием; состояние
   хранит управляющая программа, рассказ агента — входное сообщение, которое надо
   проверить. Для воспроизводимости нужны версии входов, журнал событий, сохранённое
   состояние, обработка повторов и правила возобновления. Три итерации нужно выразить
   **одним счётчиком**: первая попытка — номер 1, FAIL после 1 и 2 допускает доработку,
   после 3 — эскалацию; иначе число запусков другое. VERIFY должен уметь завершаться не
   только PASS/FAIL: отсутствие среды, таймаут, повреждённый отчёт не доказывают дефект —
   нужны отдельные `INCONCLUSIVE`, `ERROR`, `CANCELLED`, `TIMEOUT`; до выяснения они не
   разрешают выпуск, но учитываются отдельно. Worktree не отдельная машина и не БД —
   лэйны должны разделять тестовые БД, порты, каталоги, очереди; иначе текстовые
   изменения не конфликтуют, а выполнение тестов мешает соседу. Последовательный merge
   не заменяет интеграционную проверку: A и B могут проходить по отдельности, но нарушать
   общий контракт; блокировка должна охватывать создание итогового кандидата и проверку
   его состояния, а выпуск ссылаться именно на него. Запрет sleep — локальная политика,
   а не свойство событийной архитектуры; управляющая программа может использовать
   наблюдаемые, ограниченные, отменяемые таймеры/backoff.
7. **Пример таблицы переходов:** `BRIEF_READY → RUNNING` (полный бриф, свободный
   исполнитель, попытка зарезервирована); `RUNNING → VERIFYING` (верный task_id, активная
   попытка, снимок сохранён); `VERIFYING → ACCEPTED` (все обязательные проверки актуальны);
   `VERIFYING → REWORK_READY` (содержательный дефект, попытка < 3);
   `VERIFYING → ESCALATED` (три попытки); активное → `TIMED_OUT` (истёк срок, полномочия
   отозваны); `ACCEPTED → COMMITTED` (итоговый кандидат проверен, общая блокировка).
8. **Этапы:** описать состояния и запрещённые переходы (событие «коммитить» из RUNNING
   отвергается независимо от формулировки); сохранять состояние атомарно (резервирование
   попытки и запись запуска — одна операция); обрабатывать повторы и запоздалые сообщения
   (уникальный id события; запоздалый возврат сохраняется, но не даёт PASS); вынести
   watchdog; добавить очередь интеграции и барьер волны; испытать возобновление с середины
   (различать «ещё не сделано», «сделано», «результат неизвестен»; не терять блокировки;
   не повторять значимое действие без выяснения).

### 2.6. Глава 6. Сверка с рынком

1. **Совпадения:** оркестратор, который не пишет код, — orchestrator-worker у Anthropic и
   hierarchical process у CrewAI; бриф с границами — тот же вывод Anthropic после
   инцидентов с расплывчатыми инструкциями; верификатор отдельным агентом в свежем
   контексте — рекомендация Claude Code; спаренный кодген («один пишет тесты, другой —
   код») — тоже рекомендация; параллелизм через worktree и fan-out — рыночный механизм;
   бюджеты и эскалация — есть во фреймворках.
2. **Где пайплайн жёстче:** детерминированный слой контроля (матрица RULE→HOOK с
   публичными пробелами, дисциплина анти-дрейфа); протокол верификации (вердикт,
   фидбек-файл, учёт итераций, классы находок; у рынка обычно текст); двухтрековая
   маршрутизация дефектов; сохранение перед откатом и парковка блокеров.
3. **Где рынок впереди:** evals и калибровка верификатора (Anthropic ведёт статистику,
   рубричный судья 0–1, выборка реальных запросов с первого дня, оценка конечного
   состояния); трейсинг/span'ы; sandboxing на уровне ОС; fail-fast guardrails; стоимость
   и скорость.
4. **Самая спорная ставка:** Cognition прямо против параллельных агентов (конфликтующие
   неявные решения; рекомендация — однопоточный агент со сжатием контекста); наш дизайн —
   противоположный полюс. В пользу — изоляция worktree, бриф-контракт, reconciliation,
   верификатор и рекомендация вендора харнесса; но спор не закрыт, это риск, а не факт.
5. **Вердикт книги:** архитектура внутри мейнстрима, отличие — в плотности контроля;
   для соло-дева и продукта с деньгами расклад оправдан, для команды в быстрой
   разработке та же церемониальность была бы перебором.
6. **Фактчекинг Астры:** аналогии подтверждают распространённость паттерна, но не
   доказывают, что каждый менеджер лишён права писать код; последовательность «один
   пишет тесты, другой проходит» не означает одновременную разработку вслепую; Cognition
   обновила позицию (апрель 2026) — спор касается прежде всего одновременных независимых
   авторов изменений; утверждение, что guardrails обязательно остановят агента «до
   деструкции», слишком сильное — документация OpenAI предупреждает, что до завершения
   параллельной проверки агент может успеть вызвать инструменты; фразы «есть во всех
   фреймворках» и «развиты дальше рыночных» нельзя подтвердить примерами — для
   объективного превосходства нужна одинаковая выборка, сопоставимые ограничения и
   измерения; наличие sandboxing в продукте не доказывает, что операции запуска
   изолированы.
7. **Этапы:** честная база сравнения (один исполнитель с ревью vs полный пайплайн;
   одинаковые версии/задачи/критерии; отдельно расход модели и человеческое время);
   репрезентативные задачи (новый модуль, багфикс, интерфейс, интеграция, чувствительная
   операция, неполная спека); закрепить версии конфигураций (модели, параметры, промпты,
   политики, зависимости, бюджет; обновление — новая конфигурация); измерять результат
   задачи целиком (успешность независимой приёмки, пропуски, ложные отказы, число
   доработок, время, расходы, минуты человека), а не скорость токенов; выбирать режим по
   измеренному классу задач и повторять сравнение после изменений.

### 2.7. Глава 7. Разбор Астры и дорожная карта

1. **Ценное:** явный маршрут от задачи до принятия; отдельный контекст проверки;
   ограниченная доработка (предел попыток, сохраняемый между перезапусками, считаемый
   доверенным компонентом, не сбрасываемый переименованием задачи).
2. **Контроль должен принимать доказательства.** Центральный объект — не текст «готово»,
   а пакет доказательств для конкретного кандидата: задача, требования, исходная версия,
   изменения, результаты проверок, личности ролей, версия политики. Человеку — короткий
   отчёт, полный пакет — для разбора. Таблица «утверждение → чем подтверждать»:
   «тесты прошли» — команда, снимок, среда, статус процесса, число выполненных тестов,
   отчёт; «ревью выполнено» — id независимого проверяющего, критерии, находки, ссылка на
   проверенный объект; «бюджет не превышен» — счётчик и пределы в управляющем процессе;
   «работа сохранена» — id артефакта, состав, проверка восстановления; «можно выпускать» —
   совпадение кандидата с проверенным, обязательные гейты, отсутствие неразрешённых
   блокеров. Хеш файла ловит изменение, но не авторство: если воркер может переписать и
   код, и файл PASS, независимой приёмки нет. Тонкость с журналом «в одном коммите»:
   проверяем снимок продукта, финализатор добавляет журнал, контролёр проверяет, что
   прочие файлы не изменились, и сохраняет отображение «снимок → коммит»; хеш коммита
   нельзя записать внутрь него самого.
3. **Сначала ограничить возможности, затем расширять роли.** Четыре границы: неизменяемый
   снимок для проверки; ограниченная рабочая область исполнителя; отдельное место для
   доказательств; защищённый процесс интеграции. Политика, активные хуки и реестр
   полномочий не меняются воркером вместе с продуктом. Верификатору нужен read-only
   доступ к продукту, но для проверок — временные файлы, сборка, тестовая БД; это решается
   отдельным исполнителем тестов в изолированной среде, а не запуском проектного кода с
   полными полномочиями проверяющего. Внешние тексты, комментарии, ответы инструментов —
   данные, а не инструкции: фраза «пропусти проверку» внутри материала не может менять
   политику (защита от prompt injection).
4. **Независимые тесты и разумный доступ к контексту.** Абсолютная слепота — не
   универсальный режим: она полезна для проверки полноты контракта, но для ремонта
   сложного проекта нужны существующие тесты, соглашения, соседние вызовы. Рабочий
   компромисс: тест-агент выводит критерии из первичных требований; код-агент использует
   согласованные интерфейсы и разрешённый контекст; окончательная приёмка включает
   проверки, которыми исполнитель не управляет; изменение теста, чтобы узаконить неверное
   поведение, требует отдельного объяснения. Для критических алгоритмов — проверки
   свойств и мутационные испытания.
5. **Пример повторной обработки платежа:** требование «подтверждённое событие с одним
   operation_id учитывается один раз»; баланс 1000 + одно пополнение 200 = 1200, сколько
   бы раз событие ни доставлялось. Этапы и доказательства: бриф (контракт и критерии без
   неразрешённых денежных правил) → тест-агент (случаи одного события, повторов,
   одновременных повторов, разных событий) → код-агент (атомарное применение в пределах
   контракта) → спек-проверка (покрытие критериев, актуальный вердикт) → адверсальная
   проверка (конкурентная доставка, сбой между сохранением частей) → интеграция
   (повтор значимых проверок на объединённом кандидате). Если среда не позволяет
   воспроизвести конкуренцию, честный результат — «сценарий не проверен», а не PASS по
   чтению кода. Идемпотентность — свойство операции или доверенной обёртки, а не
   пожелание в промпте.
6. **Метрики верификатора и стоимости:** размеченные корректные и дефектные результаты;
   отдельно — доля пропущенных дефектов, доля ложных отказов, неполные проверки
   (`TIMEOUT`, `ERROR`, `INCONCLUSIVE`); стоимость принятой задачи (все расходы серии,
   включая неудачи и доработки / число независимо принятых задач); время до принятия
   (включая ожидание, ревью, интеграцию); человеческое участие (минуты постановки,
   уточнений, разбора отказов, ручной приёмки). Пример расчёта (не эксперимент): 80
   дефектных, 8 PASS → пропуск 10%; 20 корректных, 3 FAIL → ложный отказ 15%; если все
   случаи из одной простой функции, цифры не описывают систему. Дешёвая модель выгодна,
   когда дешевле принятая задача при сопоставимом качестве; маршрутизацию моделей надо
   пересматривать по измерениям, а не по ярлыкам.
7. **Приоритеты:** сначала запрет выпуска непроверенного/изменившегося кандидата,
   защищённые полномочия и устойчивое состояние; затем качество брифа и верификатора;
   затем наблюдаемость и восстановление; массовый параллелизм — последним. Полезен статус
   спорной находки с арбитражем: несогласие автора не отменяет FAIL, решение принимает
   независимый арбитр или человек, бюджет арбитража входит в бюджет задачи.
8. **Дорожная карта:** 1) минимальный управляемый цикл; 2) защищённая приёмка;
   3) измерение качества; 4) восстановление и наблюдаемость; 5) ограниченный
   параллелизм; 6) постоянное сопровождение контроля (владелец политик и набора evals,
   проверка изменений хуков, разбор пропусков, маршрутизация моделей по результатам).

### 2.8. Приложение А. Шаблоны артефактов

1. **Бриф:** идентичность (`task_id`, версия брифа, исходный commit, версия спецификации);
   назначение (цель, ожидаемое поведение, что входит/исключено); доступ (разрешённые файлы
   чтения/записи, инструменты, среда); контракт (имена, типы, обязательные поля, коды
   ошибок, единицы, правила границ); приёмка (критерии с id, команды проверки, ожидаемые
   результаты, обязательные сценарии); управление (попытка, лимиты времени/расходов,
   открытые вопросы, маршрут эскалации).
2. **Вердикт:** происхождение (task_id, attempt_id, reviewer_id, роль, время, версия
   политики); объект проверки (id снимка, исходная версия, версия брифа/требований);
   доказательства (критерий → проверка → артефакт → наблюдаемый результат); находки
   (finding_id, серьёзность, воспроизведение, ожидаемое/фактическое, владелец); итог
   (PASS, FAIL или причина неполной проверки, непройденные обязательные критерии).
3. **Пакет передачи на доработку:** ссылка на неизменяемый вердикт, список открытых
   finding_id, актуальная версия брифа, разрешённая область, оставшийся бюджет, способ
   повторной проверки; оркестратор передаёт идентификатор пакета, а не переписывает
   замечания.
4. **Контрольные вопросы:** что не позволяет заменить код после PASS; как отличить
   неправильный результат от несостоявшейся проверки; где хранится число попыток после
   перезапуска и смены агента; какие ресурсы общие у двух worktree; кто получает старый
   дефект, делающий выпуск неприемлемым; по каким наблюдениям видно, что ещё один агент
   улучшил результат.

### 2.9. Что учебник даёт и чего в нём нет

**Сильное:** цикл с разделением ролей и прав; бриф как контракт; независимая проверка с
вердиктом-объектом и привязкой к снимку; бюджет и эскалация; двухконтурное управление и
матрица покрытия; дисциплина доказательств; измерение верификатора; честные residual
риски; практическая дорожная карта.

**Чего нет (или что переоценено):**

* нет продуктового слоя: BA, бизнес-правил, приёмки бизнес-результата, изменения как
  единицы договорённости между ролями и репозиториями;
* нет версионирования требований и `spec_ref`: бриф ссылается на «версию спецификации»,
  но процесса согласования версии и дрейфа нет;
* нет release/deploy/PR/CI-семантики: коммит не равен выпуску;
* нет review-записи как объекта и трассировки `REQ`→`CASE`→`AC`;
* нет организационного внедрения (роли людей, очереди, метрики процесса);
* часть утверждений переоценивает механизмы (хуки ≠ песочница, «40% blocking» ≠
  безопасность, commit ≠ WAL, роли ≠ независимость ошибок) — книга сама это признаёт в
  комментариях, но формулировки легко прочитать как гарантии;
* конкретные числа (60 правил, 53 хука, 40/30/30) — описание чужой системы, не аудит.

## 3. Синтез: как два источника соединяются в один процесс

### 3.1. Два слоя, а не два конкурента

| Вопрос | Продуктовый слой (OpenSpec) | Исполнительный слой (учебник + harness) |
|---|---|---|
| На какой вопрос отвечает | Что и зачем строим, кто согласовал и в какой редакции | Как агент выполняет задачу и почему ему нельзя верить на слово |
| Единица работы | Изменение (`change`) одной возможности | Задача (`task`) с брифом и снимком |
| Артефакты | proposal, specs (дельта), design, contracts, tasks, cases, verification | бриф, снимок, вердикт, находки, evidence, pipeline-log |
| Роли | BA, SA, DEV, QA, владелец изменения, reviewers | orchestrator, briefer, worker, verifier, adversarial, human |
| Гейты | review артефактов, Ready, приёмка, закрывающий PR, archive | dispatch, submit, verdict, commit, finalize |
| Главный отказ | Построили не то / решение не задокументировано / версия разъехалась | Выпустили непроверенное / агент вышел за права / проверка не состоялась |
| Носитель истины | Git (`product-specs`, сервисные репозитории) | Управляющее состояние `harness` + `evidence/` |

Вывод: **OpenSpec без harness — это договорённость без ограждения; harness без OpenSpec —
это дисциплинированное исполнение неизвестно чего.** Целевой процесс обязан содержать оба
слоя и явные швы между ними.

### 3.2. Что каждый источник восполняет в другом

| Пробел OpenSpec | Чем закрывается из учебника/harness |
|---|---|
| Ограничение области правок — «запросом и review» | политика ролей, шлюз инструментов, `allowed_files`, write-set финализатора, guard-плагин |
| Нет ограничения автономии | бюджет 3 попыток в управляющем процессе, таймаут диспетча, watchdog |
| `verify` — отчёт, не решение | вердикт-объект: критерий → доказательство → результат, привязка к `snapshot_id` |
| Нет контракта доказательств | `evidence/`, прогон проверок в копии дерева, pipeline-log в коммите |
| Нет измерения review/QA | `evals` верификатора: пропуск, ложный отказ, неполная проверка |
| Нет защиты от injection через требования | правило «чужой текст — данные», изоляция чтения, prompt-defense |
| Нет маршрутизации находок | реестр находок, два трека, запрет закрытия без причины |
| Нет состояний и запрещённых переходов | FSM задачи, идемпотентные события, запрет «коммитить из RUNNING» |

| Пробел учебника/harness | Чем закрывается из OpenSpec |
|---|---|
| Нет BA, бизнес-правил и приёмки бизнес-результата | proposal, specs с наблюдаемым результатом, приёмка BA в опорной среде |
| Нет версионирования требований | `spec_ref` — полный SHA согласованного плана; планирующий PR; revision |
| Нет многоролевого согласования | четыре подтверждения Ready, review производителя и потребителя контракта |
| Нет design/contracts/tasks по репозиториям | design.md, contracts/, tasks.md с repo и способом проверки |
| Нет QA-кейсов и связи REQ→CASE | .feature, карта покрытия, baseline/candidate, verification.md |
| Коммит ≠ выпуск | release в опорную среду, приёмка, закрывающий PR, archive |
| Нет организационного внедрения | пилот, владелец изменения, обязательные reviewers, опорная среда |

### 3.3. Противоречия и как они разрешаются

1. **«Люди согласуют» vs «агенты работают автономно».** Решение: процессные роли и
   человеческие решения авторитетны; агентный цикл — механизм исполнения **внутри**
   уже согласованного изменения. Агент не принимает бизнес-результат и не меняет политику.
2. **«Автор не проверяет себя» vs «DEV запускает тесты и CI».** Решение: локальная
   самопроверка разрешена и полезна; запрещён **самостоятельный выпуск**. Право принять
   результат — у другого участника; вердикт верификатора и отчёт CI — разные объекты,
   оба нужны.
3. **Ready — социальный гейт vs машинный гейт.** Решение: Ready наступает только когда
   выполнены **оба** условия: есть review-записи нужных ролей (социальное) и пройдены
   машинные проверки (артефакты, трассировка, GAP=0, `spec_ref`). Инструмент не
   «одобряет», но и не пропускает без проверяемых условий.
4. **`verify` OpenSpec vs вердикт учебника.** Решение: отчёт `verify` — вход для
   change-верификации; вердикт-объект — решение по задаче; QA-отчёт — доказательство
   исполнения. Три разных объекта, не подменяют друг друга.
5. **Бюджет попыток vs отсутствие бюджета в OpenSpec.** Решение: семантика harness —
   один счётчик, три запуска всего; FAIL на третьем → `ESCALATED`; смена агента и
   переименование задачи счётчик не сбрасывают.
6. **Cases/contracts — «дополнительные файлы» vs полноценный процесс.** Решение: в
   целевом процессе это first-class артефакты со своим review, версией и продвижением
   при закрытии; стандартный `archive` их не продвигает — это делает закрывающий PR.
7. **Параллелизм OpenSpec vs риск Cognition.** Решение: параллелизм включается только
   после устойчивого последовательного цикла и только с изоляцией деревьев, контрактом
   имён и отдельными ресурсами; это риск, а не факт выигрыша.
8. **Модель по роли vs человеческое review.** Решение: маршрутизация моделей — конфиг,
   который пересматривается по измерениям; человек не «выбирает модель вручную» в цикле,
   но владеет конфигурацией и метриками.

### 3.4. Ключевые архитектурные решения (ADR-уровень)

| ID | Решение | Следствие |
|---|---|---|
| AD-1 | **Два вложенных автомата:** изменение и задача | Состояние изменения не выводится из состояния задач; агрегация — явная |
| AD-2 | **Роль — контракт прав и артефактов, а не личность** | Один и тот же агент может быть DEV в одной задаче и verifier в другой, но не в одной |
| AD-3 | **Один писатель на домен истины:** product-specs Git — требования; сервисный Git — код; harness DB — процесс; session log — след агента | Нет двойной записи; конфликты разрешаются правилом, а не «кто последний» |
| AD-4 | **Передача = артефакт + review-запись + хеш версии** | Чат не является носителем договорённости; SA не нужна история BA |
| AD-5 | **Трассировка REQ→CASE→AC→task→verdict→commit→acceptance машинно проверяема** | «Связано» становится вычисляемым свойством, а не утверждением |
| AD-6 | **Классы риска L0–L3** | Церемония пропорциональна риску; критическое — строже, документация — легче |
| AD-7 | **Человек только на необратимом и суждении; остальное — записанное решение агента** | Очередь на review не растёт линейно с числом задач |
| AD-8 | **Три класса контроля:** детерминированный / суждение / делегировано рантайму | Честная матрица; нет «правило без хука = защищено» |
| AD-9 | **Состояние процесса вне контекста агента** | Агент получает бриф и гейты, но не может «пересказать» себе PASS |
| AD-10 | **Тонкий слой над DSH-примитивами, ядро — наше** | Не дублируем sandbox/таймауты/повторы; не отдаём процесс плагину без тестов |

### 3.5. Швы: как артефакты OpenSpec становятся артефактами harness

| OpenSpec | В целевом процессе | Что добавляется |
|---|---|---|
| `change` (`chg-…`) | `change_id` + состояние изменения | change-FSM, revision, owner, risk class |
| `proposal.md` | proposal + запись review владельца продукта | схема, reviewer, hash |
| `specs/` (дельта) | `REQ-*` с наблюдаемым результатом и примерами | ID, обязательность, источник, GAP |
| `design.md` + `contracts/` | design + контракты с review производителя/потребителя | версия контракта, проверка совместимости |
| `tasks.md` | `TASK-*` → брифы | repo, зависимости, способ проверки, `AC` |
| `cases/` | `CASE-*` (Gherkin) + baseline/candidate | карта покрытия, версии, прогон |
| `spec_ref` | `spec_version` брифа = полный SHA | пиннинг, проверка дрейфа в коммите |
| Ready | состояние `READY` | машинные условия + review-записи |
| сервисный PR | коммит + PR-метаданные | change_id, spec_ref, task ids, SHA |
| `verification.md` | evidence bundle | immutable, hash-манифест, версии |
| приёмка BA | `ACCEPT`-запись | критерии, среда, SHA, кто принял |
| `archive` | закрывающий PR + archive | gate, продвижение cases/contracts, метрики |

## 4. Целевая архитектура процесса

### 4.1. Принципы

1. **Одна редакция изменения — один `spec_ref`.** Всё, что делается, ссылается на полный
   SHA плана, а не на ветку и не на «актуальную версию».
2. **Передача работы — только артефактом.** Артефакт самодостаточен, версионирован,
   прошёл review; чат — вспомогательный канал.
3. **Автор ≠ утверждающий.** Для каждого артефакта есть автор и принимающий; совпадение
   запрещено. Независимая проверка результата — обязательна.
4. **Доказательство вместо утверждения.** «Тесты прошли», «ревью выполнено», «можно
   выпускать» подтверждаются объектами: снимок, вердикт, отчёт, версия, хеш.
5. **Машинно проверяемо там, где возможно; честно там, где нет.** Семантическое суждение
   не выдаётся за механизм.
6. **Наименьшие полномочия:** роль × репозиторий × задача. Никто не пишет вне своей
   области; политику меняет только человек.
7. **Ограниченная автономия:** три попытки, бюджеты, таймауты, GAP-порог, эскалация с
   пакетом. Бесконечных циклов нет.
8. **Двухконтурное управление:** инструкция + детерминированный хук; хук — не песочница,
   review — не доказательство.
9. **Пропорциональность:** класс риска определяет набор артефактов, review и проверок.
10. **Один писатель на состояние:** переход меняет ровно один компонент; события
    идемпотентны; повторная доставка не создаёт эффекта.
11. **Параллелизм последним:** сначала устойчивый последовательный цикл, потом
    изолированные лэйны, потом волны.
12. **Процесс — продукт:** у него есть владелец, версия, метрики и регулярный разбор.

### 4.2. Двухуровневый автомат

```
                 ┌──────────────────── CHANGE (уровень изменения) ───────────────────┐
 DRAFT ─▶ EXPLORED ─▶ PROPOSED ─▶ SPECS_AGREED ─▶ DESIGN_AGREED ─▶ READY             │
   ▲           │            │              │                │            │            │
   │           │            └── revise ────┴────────────────┴────────────┘            │
   │           │                                                                     │
   │           ▼                                                                     │
   │      CANCELLED / SPLIT                                                          │
   │                                                                                 │
   │           READY ─▶ IN_PROGRESS ─▶ IMPLEMENTED ─▶ VERIFIED ─▶ RELEASED ─▶ ACCEPTED ─▶ ARCHIVED
   │                        │               │              │            │           │
   │                        └── task FAIL ──┘              │            │           │
   │                        (rework ≤ 3, иначе ESCALATED)  │            │           │
   │                                                       └─ drift ────┴─▶ новая редакция
   └────────────────────────────── superseded / rejected ────────────────────────────┘
```

Уровень задачи — существующий автомат harness (11 состояний):
`CLAIMED → BRIEF_READY → RUNNING → VERIFYING → ACCEPTED → COMMITTED`, с ветками
`REWORK_READY`, `VERIFY_BLOCKED`, `TIMED_OUT`, `ESCALATED`, `CANCELLED`.

**Правило агрегации:** состояние изменения **не** вычисляется как «все задачи
COMMITTED → изменение VERIFIED». Переходы изменения — отдельные события с guard'ами,
которые проверяют агрегаты (число задач, их вердикты, отчёты, релиз) и требуют
человеческого подтверждения там, где это решение, а не факт.

#### Состояния изменения

| Состояние | Что означает | Вход | Выход |
|---|---|---|---|
| `DRAFT` | папка изменения создана, идёт разбор | new change | explore завершён |
| `EXPLORED` | правила/границы собраны, вопросы заданы | exploration-запись, GAP-список | proposal готов к review |
| `PROPOSED` | proposal прошёл review владельца продукта | review-запись, scope | specs согласованы |
| `SPECS_AGREED` | `REQ` и примеры согласованы BA+QA | review-записи, покрытие примеров | дизайн согласован |
| `DESIGN_AGREED` | дизайн и контракты согласованы SA + владельцами сервисов | review-записи, версии контрактов | задачи и Ready |
| `READY` | план готов к реализации | все review + trace=100% + GAP=0 + `spec_ref` | первый диспетч |
| `IN_PROGRESS` | идёт реализация задач | диспетч первой задачи | все обязательные задачи COMMITTED |
| `IMPLEMENTED` | все задачи закоммичены в сервисах | агрегат задач, PR | интеграция проверена |
| `VERIFIED` | объединённый кандидат проверен | baseline+candidate, integration, `verification.md` | выпуск |
| `RELEASED` | сервисы доступны в опорной среде | release-запись, версии, флаг | приёмка BA |
| `ACCEPTED` | бизнес-результат принят | `ACCEPT`-запись BA | закрывающий PR |
| `ARCHIVED` | specs обновлены, change в архиве | closing PR, archive, метрики | терминальное |
| `BLOCKED` | ждёт внешнего решения | GAP/спор/инцидент | возврат в предыдущее |
| `CANCELLED` | отменено владельцем | причина, запись | терминальное |
| `SUPERSEDED` | заменено другим изменением | ссылка на новое | терминальное |

#### Переходы и guard'ы изменения

| Переход | Машинные условия | Человеческие условия |
|---|---|---|
| DRAFT→EXPLORED | exploration-запись со ссылками на источники; список GAP | BA подтверждает, что факты отделены от предположений |
| EXPLORED→PROPOSED | proposal валиден по схеме; scope и non-scope заполнены | владелец продукта подтверждает цель и объём |
| PROPOSED→SPECS_AGREED | каждый `REQ` имеет наблюдаемый результат и пример; нет пустых полей | BA + QA подтверждают смысл примеров |
| SPECS_AGREED→DESIGN_AGREED | design валиден; контракты имеют версию; указаны производитель/потребитель | SA + владельцы сервисов подтверждают совместимость |
| DESIGN_AGREED→READY | tasks: repo+проверка+зависимости; trace 100%; GAP=0; `spec_ref` вычислен; risk class задан | BA/SA/QA/DEV подтверждают свою часть (4 записи) |
| READY→IN_PROGRESS | все обязательные задачи имеют брифы; бюджеты заданы | владелец изменения назначает исполнителей |
| IN_PROGRESS→IMPLEMENTED | все обязательные задачи `COMMITTED`; прогресс-отметки в `tasks.md` отправлены PR | — |
| IMPLEMENTED→VERIFIED | integration-прогон на объединённом кандидате; baseline-регресс; candidate-кейсы; отчёт с версиями | QA подтверждает доказательства |
| VERIFIED→RELEASED | release-запись: среда, версии, флаг/включение | для L2 — человек подтверждает выпуск |
| RELEASED→ACCEPTED | `ACCEPT`-запись: критерии, среда, SHA, дата | BA принимает бизнес-результат |
| ACCEPTED→ARCHIVED | closing PR merged; specs синхронизированы; cases/contracts продвинуты; метрики записаны | BA/SA/QA подтверждают итоговый diff |
| любой→BLOCKED | открытый GAP/спор/инцидент | назначен ответственный и срок решения |
| любой→CANCELLED | причина | владелец изменения/продукта |

**Revision.** Любая правка planning-артефакта после `READY` увеличивает `revision`,
пересчитывает `spec_ref` и сбрасывает состояние до `SPECS_AGREED` (если менялись specs)
или `DESIGN_AGREED` (если только дизайн). Задачи, выполненные против старой ревизии,
помечаются `stale`; их вердикты не переносятся; повторный диспетч требует явного
подтверждения влияния. Это закрывает главный дефект «продолжаем по старому SHA».

**Ожидание не блокирует.** `BLOCKED` — состояние изменения, а не простой всей системы:
другие изменения и задачи продолжают работать; сессия переключается, а не висит.

### 4.3. Роли, права и решения

| Роль | Миссия | Пишет | Не пишет | Решает | Артефакты |
|---|---|---|---|---|---|
| Владелец продукта / бизнес-заказчик | Зачем и что важно | ничего в репозитории (подпись в review) | код, specs | приоритет, бизнес-правила, приёмка | review-запись, `ACCEPT` |
| BA | Сформулировать правила и границы | `product-specs` (proposal, specs, примеры) | код, дизайн | смысл требований | proposal, `REQ`, примеры |
| SA | Как сервисы обеспечат поведение | `product-specs` (design, contracts, tasks) | код сервисов | техническое решение, контракты | design, contracts, tasks |
| DEV | Реализовать свою часть | сервисный репозиторий (код, тесты), отметки задач через PR | specs, дизайн, чужие сервисы | как реализовать в рамках контракта | код, тесты, PR |
| QA | Доказать поведение | `cases/`, тестовый проект, `verification.md` | код сервисов, specs | способ и уровень проверки | `.feature`, bindings, отчёт |
| Владелец изменения (оркестратор) | Собрать план, раздать, собрать результат | планирующий PR, служебные артефакты, прогресс-отметки | продукт, код | порядок работ, эскалация | план, dispatch-записи |
| Независимый проверяющий (spec/adversarial) | Найти расхождение с планом | `evidence/` | продукт | вердикт PASS/FAIL/INCONCLUSIVE | вердикт, находки |
| QA-раннер | Выполнить проверки | `evidence/` | продукт | нет (исполняет) | отчёт прогона |
| Владелец политики (человек) | Держать правила и evals | `policies/`, `schemas/` | продукт | изменение процесса, исключения | правила, матрица |

**Разделение прав по репозиториям и артефактам** важнее разделения по «должностям»:
BA/SA физически не должны уметь писать в сервисные репозитории; DEV — в `product-specs`
(кроме своей ветки отметок задач); QA — в `src/`. Это реализуется политикой + guard'ом,
а не просьбой в промпте.

**Правило четырёх глаз** применяется к артефактам: у каждого артефакта есть
`author_id` и `approver_id`; для L2 — два независимых approver'а. Внутри одного агента
роль не переиспользуется: агент, писавший код, не может быть verifier этой же задачи.

#### Кто что утверждает

| Артефакт | Автор | Утверждает | Дополнительно |
|---|---|---|---|
| proposal | BA | владелец продукта | — |
| specs delta | BA | BA (смысл) + QA (проверяемость) | владелец продукта для L2 |
| design/contracts | SA | SA + владельцы сервисов (производитель/потребитель) | — |
| tasks | SA | DEV (реализуемость) + QA (проверяемость) | владелец изменения |
| cases | QA | BA (смысл) + SA (полнота) | — |
| brief | SA/брифёр | владелец изменения | критерии — из specs |
| вердикт задачи | verifier | — (это и есть решение) | арбитраж при споре |
| verification.md | QA | QA + владелец изменения | — |
| ACCEPT | владелец продукта/BA | — | приёмка не делегируется агенту |
| archive | владелец изменения | BA/SA/QA (итоговый diff) | — |

### 4.4. Артефакты, идентификаторы и трассировка

#### Реестр артефактов

| Артефакт | Где живёт | Владелец | Версия | Review | Продвижение |
|---|---|---|---|---|---|
| `proposal.md` | `product-specs/openspec/changes/<id>/` | BA | revision | владелец продукта | архив |
| `specs/**` (дельта) | там же | BA | revision | BA+QA | `openspec/specs` при archive |
| `design.md` | там же | SA | revision | SA+сервисы | архив (история) |
| `contracts/**` | `changes/<id>/contracts/` | SA | semver | производитель+потребитель | корневой `contracts/` при закрытии |
| `tasks.md` | там же | SA | revision | DEV+QA | архив |
| `cases/**` | `changes/<id>/cases/` | QA | revision | BA+SA | `cases/current` при закрытии |
| `verification.md` | `changes/<id>/` или `evidence/` | QA | — | владелец изменения | архив |
| бриф | `.harness/` / `briefs/` | брифёр | `brief_version` | владелец изменения | не коммитится в продукт |
| снимок | вычисляется | harness | `snapshot_id` | — | evidence |
| вердикт | `evidence/` | verifier | `attempt` | — | привязан к снимку |
| review-запись | `<change>/reviews/` | reviewer | hash артефакта | — | архив |
| `ACCEPT` | `<change>/acceptance.md` | владелец продукта | — | — | архив |
| pipeline-log | `pipeline-log/` | harness | — | — | в коммите |

#### Схема идентификаторов

```
CHG-142                 изменение (папка chg-142-cancel-order)
REV-3                   редакция плана (revision)
REQ-CANCEL-4            требование в дельте specs
CASE-CANCEL-7           сценарий/Gherkin
CON-ORDERS-2            контракт (OpenAPI/событие)
TASK-142-1.2            задача из tasks.md (repo=orders-service)
AC-142-1.2-3            критерий приёмки в брифе
FND-142-1.2-05          находка
VER-142-1.2-A1          вердикт (attempt)
EVD-142-...             пакет доказательств
ACC-142                 приёмка изменения
REL-142-...             выпуск
```

#### Цепочка трассировки

```
бизнес-цель (proposal)
   └─▶ REQ-* (specs delta: наблюдаемый результат)
         ├─▶ CASE-* (Gherkin, примеры)
         └─▶ AC-* (критерий в брифе)
                └─▶ TASK-* (repo, зависимость, проверка)
                       └─▶ VER-* (критерий→доказательство→результат)
                              └─▶ commit SHA (сервис) + spec_ref
                                     └─▶ verification.md (интеграция)
                                            └─▶ ACC-* (приёмка)
                                                   └─▶ archive
```

**Правила матрицы трассировки:**

* каждый обязательный `REQ` имеет минимум один `CASE` и один `AC`;
* каждый `AC` имеет исполняемую команду проверки (иначе `E_UNVERIFIABLE` в брифе);
* каждая `TASK` имеет repo, зависимость и способ доказательства;
* каждый `VER` ссылается на `spec_ref` и `snapshot_id`; покрытие обязательных `AC`
  полное, иначе `INCONCLUSIVE`;
* каждый `commit` содержит `change_id`, `spec_ref`, `task_id` (trailer или PR-метаданные);
* `ACCEPT` ссылается на `VERIFIED`-версии и критерии приёмки;
* `archive` невозможен при открытых обязательных `REQ`/`CASE`/находках.

Матрица **генерируется**, а не заполняется руками; расхождение — блокирующий гейт.

#### Review-запись (объект, а не «LGTM»)

```json
{
  "artifact": "openspec/changes/chg-142/specs/cancel-order/spec.md",
  "artifact_hash": "sha256:…",
  "revision": 3,
  "reviewer_id": "ba-1",
  "reviewer_role": "BA",
  "author_id": "ba-agent-2",
  "criteria": ["наблюдаемый результат", "права и состояния", "ошибки и границы"],
  "findings": [{"id": "FND-…", "severity": "major", "text": "…"}],
  "verdict": "approve | request_changes | abstain",
  "decided_at": "…",
  "policy_version": "1.0.0"
}
```

`approve` без критериев и без ссылки на проверенный hash не принимается; `abstain` не
считается подтверждением; запись автора о собственном артефакте отклоняется.

#### Пакет доказательств изменения

Один immutable-каталог (или манифест с хешами): вердикты задач, прогоны проверок,
`verification.md`, release-запись, `ACCEPT`, review-записи, `spec_ref`, SHA сервисов,
версия политики и окружения. Человеку показывается короткая сводка; полный пакет —
для разбора и аудита. Хеш-манифест защищает от подмены; для L2 — опционально подпись
(cosign/sigstore) и внешнее хранилище.

### 4.5. Сквозной маршрут (от бизнес-задачи до архива)

| Шаг | Кто | Вход | Действия | Выход | Гейт |
|---|---|---|---|---|---|
| 0. Приём задачи | владелец продукта + BA | бизнес-задача | сформулировать проблему, цель, метрику успеха, класс риска, владельца | черновик change | назначены owner и risk class |
| 1. Разбор | BA (агент-помощник) | specs/кейсы/код (read-only), экспорт wiki | извлечь правила со ссылками, отделить факты от предположений, задать GAP | exploration-запись | факты/вопросы разделены |
| 2. Proposal | BA | разбор | зачем, scope/non-scope, влияние | `proposal.md` | review владельца продукта |
| 3. Requirements | BA + QA | proposal | `REQ` с наблюдаемым результатом, примеры успех/отказ/граница | дельта specs, примеры | BA+QA подтвердили |
| 4. Design | SA + DEV | specs, текущий код | проверить архитектуру, контракты, повторы/гонки/сбои, совместимость | design, contracts | производитель+потребитель+DEV |
| 5. Tasks и Ready | SA + QA + DEV | design | разбить по repo, зависимости, проверки; покрытие REQ→CASE; `spec_ref` | tasks, trace-матрица | 4 review + trace 100% + GAP=0 |
| 6. Брифы и диспетч | владелец изменения | tasks, specs | бриф на задачу: цель, allowed_files, AC, check-команды, бюджет | брифы, dispatch | change=READY, бриф валиден |
| 7. Исполнение | DEV/QA-воркер | бриф | реализация/тесты, снимок, проверки | код, тесты, снимок | verifier PASS на снимке |
| 8. Задача принята | verifier + финализатор | снимок | критерий→доказательство, вердикт, коммит, PR | коммит, вердикт, PR | PASS + write-set + spec_ref |
| 9. Интеграция и проверка | QA + verifier изменения | все коммиты | baseline-регресс, candidate-кейсы, контрактные/интеграционные, отчёт | `verification.md`, change-verify | все задачи + отчёт + версии |
| 10. Выпуск | владелец изменения (+ человек для L2) | VERIFIED | развернуть в опорную среду, включить флаг | release-запись | среда/версии/флаг |
| 11. Приёмка | BA/владелец продукта | release | проверить бизнес-критерии в среде | `ACCEPT` | критерии + версии |
| 12. Закрытие | владелец изменения | ACCEPT | closing PR: specs sync, promote cases/contracts, archive | архив, обновлённые specs | diff проверен BA/SA/QA |
| 13. Разбор | владелец процесса | метрики | пропуски, очереди, стоимость, уроки | изменения правил/evals | запись причины (R-HOOK-1) |

#### Definition of Ready (изменение)

- [ ] proposal прошёл review; scope и non-scope явные;
- [ ] каждый обязательный `REQ` наблюдаем и имеет пример;
- [ ] design и контракты проверены производителем и потребителем;
- [ ] `tasks` разбиты по repo, с зависимостями и способом проверки;
- [ ] карта `REQ→CASE` полная; все `AC` проверяемы;
- [ ] блокирующих GAP нет; обратимые решения записаны;
- [ ] risk class назначен; reviewers назначены;
- [ ] `spec_ref` (полный SHA) вычислен и записан;
- [ ] бюджеты попыток/стоимости заданы.

#### Definition of Done (задача)

- [ ] изменения только в `allowed_files`; write-set подтверждён;
- [ ] все обязательные `AC` покрыты фактическим прогоном (не skip);
- [ ] вердикт `PASS` привязан к текущему `snapshot_id`;
- [ ] `commit` содержит `change_id`, `spec_ref`, `task_id`;
- [ ] pipeline-log в том же коммите;
- [ ] находки не закрыты формально; блокеры отсутствуют;
- [ ] PR содержит ссылки на план и требования.

#### Definition of Done (изменение)

- [ ] все обязательные задачи `COMMITTED`;
- [ ] интеграционный кандидат собран; baseline-регресс зелёный;
- [ ] candidate-кейсы выполнены; `verification.md` с версиями всех компонентов;
- [ ] открытых блокирующих находок и GAP нет;
- [ ] выпуск в опорной среде подтверждён;
- [ ] `ACCEPT` подписан владельцем продукта;
- [ ] closing PR: specs/cases/contracts продвинуты, change в архиве;
- [ ] метрики и уроки записаны.

### 4.6. Гейты и правила

Существующая матрица `policies/rules.json` (47 правил: 44 наших покрытых и 3
делегированных рантайму) остаётся ядром исполнительного
слоя. Для продуктового уровня добавляются правила; каждое обязано иметь исполняемую
проверку либо честный статус `soft`/`judgement`.

| ID | Правило | Событие | Класс | Где проверяется | Остаточный риск |
|---|---|---|---|---|---|
| R-CHG-1 | Переход состояния изменения возможен только по таблице; «готово» из `IN_PROGRESS` отвергается | change-transition | blocking | change-FSM (ядро) | состояние может быть изменено человеком в обход |
| R-REF-1 | Бриф и коммит ссылаются на полный `spec_ref`; ссылка на ветку/короткий SHA запрещена | predispatch/precommit | blocking | валидатор брифа, specgate, trailer | SHA подтверждает версию, не соответствие кода |
| R-REV-1 | Review-запись валидна только с reviewer, критериями, hash артефакта и вердиктом | gate | blocking | схема + gate | запись можно заполнить формально |
| R-REV-2 | Автор артефакта не может быть его approver'ом; для L2 — два approver'а | gate | blocking | gate по ID | подмена идентичности агента |
| R-TRACE-2 | На Ready каждый обязательный REQ покрыт CASE и AC; orphan'ы блокируют | Ready/archive | blocking | генератор матрицы | «покрытие» может быть фиктивным (CASE без проверки) |
| R-TASK-1 | Каждая задача имеет repo, зависимость и способ проверки | Ready | blocking | схема tasks | способ проверки может быть неисполним |
| R-DRIFT-1 | Задача/коммит против устаревшей редакции помечается stale и не принимается | dispatch/commit | blocking | сверка revision | ручной перенос вердикта |
| R-QA-1 | Verification содержит версии требований, runner, сервисов, среды и результаты обязательных CASE | VERIFIED | blocking | схема отчёта | версии можно записать неверно |
| R-QA-2 | Нулевой прогон/необнаруженные CASE не считаются проверкой; обязательные CASE должны быть выполнены | VERIFIED | blocking | раннер + отчёт | тест может «проходить» бессмысленно |
| R-ACCEPT-1 | Archive невозможен без ACCEPT-записи с критериями, средой и версиями | archive | blocking | closing gate | приёмка «на словах» |
| R-ACCEPT-2 | Для L2 выпуск и приёмка требуют человеческого подтверждения и release-записи | release/accept | blocking | gate | человек может подтвердить формально |
| R-GAP-2 | Вопросы про деньги, доступ, необратимое и противоречия критериев решает человек; обратимые — исполнитель с записью | predispatch | blocking/soft | brief gate | порог можно обойти формулировкой |
| R-EXIT-1 | Эскалация содержит проблему, влияние, доказательства и варианты; без этого не создаётся | escalation | soft | схема пакета | пакет может быть неполным по смыслу |
| R-REPO-1 | Запись разрешена только в репозиторий и пути, назначенные задаче; PR содержит change_id/spec_ref/task | pretooluse/precommit | blocking | policy + guard + finalize | обход через дочерний процесс |
| R-FIND-3 | Находка имеет владельца, статус и срок; закрытие без причины запрещено | postverdict | blocking/soft | реестр находок | статус может не обновляться |

**Матрица гейтов: машина vs человек**

| Гейт | Машинно | Человек/суждение |
|---|---|---|
| Ready | артефакты, схемы, trace, GAP=0, spec_ref | полнота бизнес-правил, осмысленность дизайна |
| Dispatch | бриф, allowed_files, бюджет, state | выбор исполнителя |
| Commit | PASS, snapshot, write-set, spec_ref | — |
| VERIFIED | все задачи, отчёты, версии, baseline/candidate | достаточность проверок |
| RELEASED | release-запись, среда, флаг | для L2 — разрешение |
| ACCEPTED | ACCEPT-запись, ссылки | бизнес-результат |
| ARCHIVED | closing PR, sync, продвижение | итоговый diff |

Ни одно правило не должно называться «защитой», если оно проверяет текст запроса, а не
факт. Для каждого — residual risk и владелец (см. `docs/RULES_MATRIX.md`).

### 4.7. Где что хранится и кто источник истины

| Домен | Источник истины | Что там | Кто пишет | Резерв/аудит |
|---|---|---|---|---|
| Требования и решения | `product-specs` Git | specs, changes, design, contracts, cases, reviews, acceptance | BA/SA/QA/владелец через PR | история Git + архив |
| Код | сервисные Git-репозитории | код, тесты, PR | DEV через harness | Git + PR |
| Состояние процесса | harness SQLite | change/task state, attempts, budgets, verdicts, audit | только управляющий процесс | backup + журнал событий |
| Доказательства | `evidence/` (immutable) | вердикты, прогоны, отчёты, release, ACCEPT | verifier/QA/runner | hash-манифест, вывоз |
| След агента | DSH session log | вызовы, сообщения, tool results | рантайм | экспорт/OTel |
| CI-результаты | CI | build/test artifacts | CI | retention политика |

**Правила согласованности:**

1. Git выигрывает по содержанию; harness — по состоянию процесса; session log — только
   наблюдаемость (не бизнес-истина).
2. Переход процесса фиксируется до внешнего эффекта (log first) и идемпотентен по
   `event_id`; повторная доставка не создаёт второго коммита/релиза.
3. При расхождении (например, specs изменены после Ready) побеждает процедура: изменение
   помечается, задачи stale, гейт закрывается до повторного согласования — а не «кто
   последний записал».
4. Восстановление после сбоя: состояние читается из SQLite, сверяется с Git (HEAD,
   `spec_ref`) и evidence; неизвестный результат не трактуется как успех.

### 4.8. Мультирепозиторная модель

```
product-specs (spec_ref = SHA)
  ├── openspec/changes/chg-142/...      план
  └── cases/current, contracts/          действующие артефакты
        │
        ├── orders-service  @ SHA-a ── PR-1 ─┐
        ├── refund-service  @ SHA-b ── PR-2 ─┼──▶ integration candidate (набор SHA)
        └── qa-runner       @ SHA-c ── PR-3 ─┘
```

1. **Контекст задачи:** `{change_id, spec_root, code_roots[], task_ids[], allowed_files[],
   base_commit, spec_ref}`. Один бриф — один сервис; кросс-сервисная задача дробится.
2. **Снимок** считается по каждому code-root отдельно; change-level кандидат — это
   отображение `repo → SHA`. Вердикт задачи привязан к снимку своего репозитория.
3. **`spec_ref` глобален** для изменения; каждый коммит несёт его, а отчёт — SHA каждого
   сервиса и версию runner.
4. **Прогресс `tasks.md`** обновляется отдельным PR `product-specs`; чтобы не было двух
   писателей, отметки собирает владелец изменения (или один выделенный прогресс-агент)
   под мьютексом; конфликт — не «мержим как получится», а повторная сборка прогресса.
5. **Порядок:** задачи с зависимостями выполняются по DAG; интеграция — после
   обязательных зависимостей; параллельные лэйны — только с раздельными ресурсами
   (порты, БД, каталоги).
6. **PR сервиса:** `change-id`, `spec_ref`, номера задач, связанные `REQ`, контракт,
   результаты проверок; итоговый SHA после merge фиксируется отдельно (squash).
7. **Ограничение OpenSpec** (`apply` не маршрутизирует по репозиториям) компенсируется
   harness: явные корни, `allowed_files`, guard, write-set, PR-метаданные. Это надо
   проверять отказом, а не декларацией.

### 4.9. Классы риска и пропорциональность

| Класс | Примеры | Обязательные артефакты | Дополнительно | Человеческие гейты |
|---|---|---|---|---|
| L0 | документация, конфиг без поведения, опечатки | proposal (кратко), tasks, коммит со spec_ref | — | review владельца |
| L1 | обычная функциональность | все четыре + cases + verification | verifier | Ready, приёмка |
| L2 | деньги, доступ, безопасность, PII, необратимые операции | L1 + adversarial + property/mutation + release-план | два reviewer'а, security-review | Ready, release, приёмка |
| L3 | аварийный фикс | сокращённый план + incident-запись | постфактум specs/acceptance в срок | break-glass с причиной |

Классификация — чек-лист + подтверждение владельца продукта; по умолчанию L1.
Ошибочная классификация — дефект процесса, а не «повезло». L3 не отменяет запись: после
аварии изменение обязано получить нормальную спеку и приёмку в установленный срок, иначе
следующий релиз блокируется.

### 4.10. Исключения и отказы

| Ситуация | Что происходит | Кто решает | Что записывается |
|---|---|---|---|
| Блокирующий GAP | dispatch запрещён | человек (BA/владелец) | ответ в артефакте, GAP закрыт |
| Спорный FAIL | автор предъявляет контрпример | арбитр/человек | пакет спора, решение, бюджет |
| Дрейф specs после Ready | revision++, задачи stale | владелец изменения + BA/SA | влияние, повторный Ready |
| Код нарушает согласованное | чинится код, не expected result | DEV + verifier | вердикт, повторная проверка |
| Проверка не состоялась | `INCONCLUSIVE`/`ERROR`/`TIMEOUT` | verifier/QA | отдельный статус, не FAIL |
| Таймаут диспетча | watchdog отзывает, работа сохраняется | система | `TIMED_OUT`, событие смерти |
| Конфликт слияния | откат, задача человеку | владелец изменения | конфликт, решение |
| Отказ релиза/инцидент | rollback по флагу, change открыт | владелец + on-call | инцидент, rollback-доказательство |
| Разделение объёма | новое change, ссылка на родителя | владелец продукта | `SUPERSEDED`/split-запись |
| Аварийный фикс | L3 break-glass | владелец продукта | причина, срок нормализации |
| Архив с неполными задачами | запрещён | — | исключение только через policy-owner |
| Старый дефект мешает выпуску | работа останавливается в части | владелец изменения + владелец кода | finding с владельцем и сроком |

**Принцип:** у каждой остановки есть состояние, владелец, срок и запись; «повисло» — не
состояние процесса.

## 6. Автоматизация средствами DSH: что реально можно и чего нельзя

### 6.1. Фактическое состояние установки

* DSH **0.2.2-rc.3**, профиль `desktop`, 221 Loader-строка, ни одной `failed`.
* Текущие права сессий: **`danger-full-access` + `approval: never`**. Это значит, что

### 6.3. Что строить: пять компонентов и границы

**C1. Пресеты ролей (конфиг, S). ✅** BA, SA, DEV, QA, verifier: разные инструменты,
persona, модель, доступ к скиллам. Связь с `policy.json` — по имени роли; пресет не
заменяет политику, а выбирает композицию. Проверка: `agent-preset/selected` в журнале,
`Tool.listTools` у каждого пресета.

**C2. Скиллы процесса (конфиг, S). ✅** `brief-from-change`, «Ready-чеклист», «review-
record», «формат вердикта», «приёмка», «эскалация». Скилл объясняет, но не запрещает;
все запреты — в ядре/guard'е.

**C3. Host-плагин `process-gate` (M). ✅** Расширение подхода `harness-guard`:
* роли и области из `policy.json` + `guard-scope.json` (не дублировать правила — parity);
* deny для `plugin_manager` и опасных MCP-инструментов рабочим ролям (deny-by-default
  для неизвестных инструментов, allowlist для чтения);
* проверка `spec_ref` и путей `product-specs` при записи;
* `tools/pre-execute` → `ask` для GAP (не guard);
* fail-closed при ошибке; аудит.
Плагин **читает** состояние процесса и публикует решения, но не владеет состоянием.

**C4. Python change-ядро (M/L). ✅ (Этап 1)** Change-FSM, revision, `spec_ref`, trace-матрица,
review-записи, Ready/Verified/Accepted/Archived-гейты, baseline/candidate, acceptance,
CLI (`harness change ...`). Это единственный писатель процесса. Плагин и UI — над ним.

**C5. UI-доска (M/L, опционально).** Состояния change, очередь review, гейты, evidence,
риски. Client-плагин через slots/projections; для HMR нужен `dev:web`. Без доски процесс
работает, но человек хуже видит очередь.

**C6. Оркестрация и CI (M/L).** `agent-team` для DAG задач, `workflow` для веера,
worktree на задачу, `dsh-headless --json` как точка CI, forge — для статуса PR.
Вводить после C1–C4 и только на устойчивом последовательном цикле.

**Порядок:** C1 + C2 → C4 → C3 → C6 → C5. Критерий каждого шага — воспроизводимый
отказ/разрешение, а не «плагин установился».

### 6.4. Что нельзя строить плагином

| Не в плагин | Почему |
|---|---|
| Автомат состояний и переходы | это бизнес-истина; плагин можно выгрузить/обновить, состояние останется |
| Бюджет попыток, счётчики, таймауты | должны переживать перезапуск и смену агента |
| Вердикт-объект и его приёмка | независимость и привязка к снимку — свойство ядра |
| Коммит/merge, write-set, evidence | привилегированные операции с проверкой |
| Политика и правила | их меняет человек, а не агент и не плагин рабочей роли |
| Новые типы событий сессии | запрещены; проекции/домен — да, события — нет |
| CI-гейт | CI — внешняя система; плагин только запускает/читает |
| Акцептанс бизнес-результата | решение человека, не автоматизация |

### 6.5. Жёсткие ограничения и ловушки (проверено по установке)

1. **Guard синхронный и монотонный:** только запрет, `ask` невозможен, аргументы не
   переписываются. Всё, что требует ожидания, — `tools/pre-execute`.
2. **Guard видит имя инструмента, а не смысл.** MCP-серверы (включая меняющие
   маршрутизацию), `plugin_manager`, `workflow` проходят как «непишущие». Для рабочей
   роли нужен deny-by-default и явная карта инструментов.
3. **Подагенту `ask` запрещён.** Значит, вопрос человеку из воркера возвращается
   пакетом родителю, а родитель спрашивает человека. Это надо заложить в протокол
   эскалации, иначе «спросить» из подагента невозможно.
4. **`plugin_manager` исполняет код в Host с правами пользователя.** При
   `danger-full-access` плагин равен человеку; установка только с vet/pin.
5. **Нельзя добавлять типы событий сессии; проекции — чистые.** Состояние процесса
   живёт в Python/SQLite, UI читает проекцию.
6. **Версии прибиты к `0.2.2-rc.3`.** Обновление DSH — отдельный проект с проверкой
   peerDeps и HMR; client-бандл пересобирается только при `dev:web`.
7. **`schedule` — не watchdog** (минимум ~60 с, at-least-once, отказ delegated);
   watchdog остаётся отдельным процессом ядра.
8. **Team/workflow не изолируют ФС** и не снимают владельца; `writeScopes` — совет,
   а не lock. Изоляция — worktree на задачу, а не Team.
9. **Webhook-пакета в сборке нет.** Интеграция с GitHub — через `gh`/forge/CI, не
   через webhook.
10. **Два источника истины.** DSH session log — след агента; harness DB — состояние
    процесса; Git — содержание. Нельзя выводить бизнес-состояние из журнала сессии.

### 6.6. Итог: граница «плагин / ядро / человек»

| Плагин (DSH) | Ядро (Python) | Человек |
|---|---|---|
| ограничивает инструменты роли | владеет состояниями, бюджетом, вердиктом | владеет политикой и бизнес-решениями |
| показывает гейты и очередь | вычисляет гейты и trace | принимает Ready, приёмку, исключения |
| спрашивает (`ask`) и рендерит | фиксирует решения и доказательства | решает спор и риск |
| читает состояние для UI | коммитит и архивирует | утверждает выпуск L2 |
| не хранит истину | хранит истину | отвечает за результат |

## 7. Чего нет в исходниках, но нужно для полноценного процесса

Ниже — не «список всего хорошего», а пробелы, которые проявятся на первом же реальном
изменении, и конкретное действие по каждому.

### 7.1. Продуктовый слой и требования

* **Discovery и метрика успеха.** Ни OpenSpec, ни учебник не отвечают, как понять, что
  задача вообще нужна. Добавить в `proposal.md` обязательные поля: проблема, метрика
  успеха, как измерим после выпуска, что будет считаться неудачей. Без этого приёмка
  BA превращается во вкусовое решение.
* **Доменные инварианты.** Отдельный, короткий и утверждённый владельцем список
  инвариантов продукта (идемпотентность денег, запрет расширения прав из запроса,
  сохранность суммы и т.п.). Каждый инвариант — обязательный `REQ`-кандидат и
  проверяемый сценарий; это защита от «общей ошибочной предпосылки» (Астра, гл. 3).
* **Структурированные требования.** EARS/«когда… тогда…» или пример-маппинг (three
  amigos) снижают двусмысленность лучше свободного текста; Gherkin — следствие, а не
  замена анализу. Полезно ввести правило: требование без наблюдаемого результата не
  принимается.
* **Нефункциональные требования как first-class.** Производительность, безопасность,
  доступность, наблюдаемость, стоимость эксплуатации — частый источник «скрытых
  решений». Для них нужны свои `REQ` и способ проверки, иначе они всплывают на релизе.
* **ADR и контракт-первый дизайн.** Для значимых технических решений — короткая
  Architecture Decision Record (контекст, варианты, решение, последствия); контракты —
  OpenAPI/AsyncAPI/схемы событий с проверкой совместимости, а не прозой в `design.md`.
* **Definition of Ready для задачи** (не только изменения): цель, вход, критерии,
  зависимости, риск, владелец — иначе бриф будет додумывать.

### 7.2. Тестирование и проверки

* **Уровни тестов привязаны к риску.** Unit / integration / contract / e2e / acceptance
  выбираются для каждого `REQ`, а не «всё через e2e»; QA фиксирует выбор в карте
  покрытия. Иначе e2e-пирамида переворачивается и становится медленной и хрупкой.
* **Мутационное и property-based тестирование** для критических алгоритмов (деньги,
  доступ, идемпотентность): проверяют чувствительность тестов, а не только их наличие.
  Не для всего кода — по risk class.
* **Контрактные тесты между сервисами** (Pact/OpenAPI-diff) закрывают класс «A и B
  проходят по отдельности, а вместе ломаются» — тот самый разрыв, который учебник
  называет пределом последовательного merge.
* **Политика flaky-тестов:** карантин с владельцем и сроком, запрет «перезапускать до
  зелёного», отдельная метрика нестабильности. Иначе агент выучит, что повторный прогон
  — способ пройти проверку.
* **Защита от нулевого/фиктивного прогона:** discovery должен подтверждать ожидаемые
  `CASE`; успешный запуск нуля тестов — не проверка; тест, который ничего не проверяет,
  — дефект теста (мутационная проверка помогает это поймать).
* **Escape-дефекты:** каждый дефект, дошедший до приёмки/прода, становится кейсом
  evals верификатора и QA. Это единственный способ калибровать проверяющего по реальным
  пропускам, а не по синтетике.
* **Тестовые данные и среда:** воспроизводимые фикстуры, отсутствие PII в тестах,
  управляемые версии окружения; иначе «у меня работает» не воспроизводится.

### 7.3. Безопасность и данные

* **OWASP Top 10 для LLM-приложений и NIST AI RMF** как чек-лист: prompt injection,
  небезопасная обработка вывода, чрезмерная агентность, supply chain, утечка данных,
  отравление контекста. Требования, тикеты, комментарии в коде, ответы инструментов —
  **данные, не инструкции**; правило уже есть в `docs/PROMPT-DEFENSE.md`, его надо
  распространить на все входы процесса.
* **Наименьшие полномочия на уровне инструментов, а не только путей:** allowlist
  инструментов на роль; deny-by-default для неизвестных (особенно MCP); запрет
  `plugin_manager` и опасных MCP рабочим ролям; `workspace-write` вместо
  `danger-full-access`; подтверждения на необратимых операциях.
* **Supply chain:** пиннинг версий DSH/плагинов/MCP, `scan_plugin`/`vet_label` перед
  установкой, проверка `engines.dsh`, запрет build-скриптов без явного approve, SBOM
  для зависимостей. Плагин исполняется в Host с правами пользователя — это не «ещё один
  пакет».
* **Секреты:** не попадают в промпт, бриф, вердикт, логи и сессии; маскирование,
  отдельное хранилище, ротация; проверка на секреты в коммите — уже есть в идеях
  учебника, но не в harness.
* **Классификация данных:** что можно отправлять модели/провайдеру, что нельзя; сроки
  хранения; PII; кодовая база клиента; условия провайдера. Это решение о данных, а не
  только о стоимости.
* **Лицензии и происхождение кода:** AI-сгенерированный код, копирование из корпусов
  поиска (в `xerj` есть предупреждения о copyleft), attribution; для регулируемых
  продуктов — политика допустимости.

### 7.4. Доказательства и целостность (supply chain of evidence)

* **Attestations и подписи.** Для L2 имеет смысл подписывать вердикты/приёмку
  (cosign/sigstore) и хранить хеш-манифест evidence; в перспективе — in-toto/SLSA-
  совместимые attestations. Это защищает от подмены «пакета доказательств», которую
  хеш файла не ловит.
* **Provenance.** Для каждого артефакта фиксировать: модель/версию агента, версию
  промпта/скилла, версию политики, версию инструментов и окружения, `spec_ref`, SHA
  сервисов. Без этого нельзя ответить «чем именно это сделано».
* **Воспроизводимость.** Пиннинг зависимостей и образов, фиксация версии runner и
  среды, детерминированные проверки; «повторить прогон» должно быть возможно.
* **Жизненный цикл evidence:** immutable-хранилище, retention, разграничение доступа,
  вывоз в доверенное место (в ROADMAP это остаток Этапа 4), покоммитный аудит.
* **Честная граница:** подпись подтверждает целостность, не правильность; это надо
  писать рядом с механизмом, а не вместо него.

### 7.5. Метрики и экономика

* **Метрики процесса:** lead time (бизнес-задача → приёмка), очередь на каждом гейте,
  latency review, WIP, доля доработок, first-pass yield, escape-дефекты, покрытие
  трассировки, доля изменений с полным evidence, стоимость принятого изменения, минуты
  человека. Это лучше, чем «число завершённых диспетчей».
* **Метрики верификатора:** пропуск, ложный отказ, `INCONCLUSIVE`, калибровка;
  набор — из реальных отказов, а не только синтетики.
* **Экономика:** стоимость принятой задачи (включая неудачи и ревью), стоимость
  альтернативы (человек/другая модель), бюджет по классу риска; пересмотр после смены
  модели или политики.
* **Опасность Goodhart:** нельзя оптимизировать «долю PASS» или «скорость» в отрыве от
  escape-дефектов и полной стоимости. Метрика — для решения, а не для отчёта.
* **SLO процесса:** например, «90% изменений L1 проходят Ready за 2 рабочих дня»,
  «review не дольше 1 дня», «0 изменений без trace». Нарушение SLO — предмет разбора,
  а не наказания.
* **Источник метрик:** harness DB + CI + evidence; журнал сессии — для отладки, не для
  отчётности.

### 7.6. Организация и люди

* **RACI и владельцы.** У изменения — один владелец; у артефакта — автор и утверждающий;
  у политики и evals — владелец; у процесса — человек, а не «все». Без этого гейты
  превращаются в «никто не решил».
* **Очередь и WIP.** Узкое место в такой системе — человеческое review/приёмка.
  Ограничение WIP, батчинг однотипных review, SLA, асинхронные решения; иначе агенты
  быстрее, чем люди успевают принимать, и очередь растёт.
* **Пилот и обучение.** Одно изменение, один-два сервиса, назначенные reviewers,
  опорная среда; критерий успеха — «любой участник находит правило, версию и проверку
  без переписки». После пилота — разбор очередей и автоматизация, а не расширение вслепую.
* **Процесс как продукт.** Версия регламента, changelog, владелец, регулярный разбор;
  изменения процесса — через `rule change`/policy-owner, а не «так получилось».
* **Ответственность.** Агент не владеет результатом; человек подписывает приёмку и
  исключения. Это не бюрократия, а условие доверия к процессу.
* **Team Topologies/Conway.** Платформенная команда владеет harness/процессом,
  stream-команды — изменениями; иначе процесс и продукт развиваются в разные стороны.

### 7.7. Знания и память

* **AGENTS.md и docs-as-code** как источники инструкций; процессные скиллы — тонкие,
  без дублирования политики. Иначе инструкции разъезжаются с кодом.
* **Уроки и инстинкты** (уже есть `docs/LESSONS.md`, `docs/INSTINCTS.md`): ошибка →
  правило → автоматика. Это единственный механизм, который не даёт деградировать.
* **Поиск и recall:** `xerj`, `session-query`, `recall` — для «что уже решали и почему»;
  но истина о требованиях — в Git, а не в памяти агента.
* **Гигиена контекста:** бриф самодостаточен, спека версионирована, история не является
  носителем договорённости; компакция не должна стирать критерии.
* **Глоссарий и шаблоны:** единые термины (change, revision, REQ, CASE, AC, verdict,
  acceptance) и шаблоны артефактов; иначе каждая роль понимает «готово» по-своему.

### 7.8. Юридическое и комплаенс

* **Происхождение AI-кода и лицензии:** политика допустимости генерации, проверка
  заимствований, copyleft-риски, attribution; для регулируемых доменов — отдельное
  согласование.
* **Данные и провайдер:** резидентность, условия обработки, запрет обучения на данных,
  PII, сроки хранения; это фиксируется в политике, а не в голове владельца.
* **Аудит и записи:** кто утвердил, что и на какой версии; сроки хранения evidence;
  возможность предъявить след для внутреннего/внешнего аудита.
* **Стандарты (если применимо):** ISO/IEC 42001 (менеджмент ИИ), NIST AI RMF, EU AI Act
  для рискованных сценариев; не как сертификация ради галочки, а как чек-лист пробелов.

### 7.9. Надёжность самого процесса

* **Два источника истины** (Git и harness DB) требуют явной процедуры сверки при
  старте, восстановлении и конфликте; «кто последний» — не процедура.
* **Идемпотентность и повторы:** события с `event_id`, повторная доставка не создаёт
  второго коммита/релиза; неизвестный результат не трактуется как успех.
* **Deadlock/ожидание:** `BLOCKED` — состояние с владельцем и сроком; система не
  останавливается целиком; отмена и таймауты предусмотрены.
* **Отказ/восстановление:** backup SQLite, восстановление evidence, миграции схемы
  (`SCHEMA_VERSION = 4`, ALTER-миграции идемпотентны; миграции формата evidence —
  Этап 3).
* **Версии и обновления:** OpenSpec CLI, DSH, модели, плагины — пиннинг и процедура
  обновления с прогоном evals; обновление модели = новая конфигурация, а не «то же самое».
* **Break-glass:** аварийный путь с причиной, сроком нормализации и последующей спекой;
  без него люди будут обходить процесс молча.
* **Ёмкость и стоимость:** параллельные изменения ограничены не агентами, а review и
  бюджетами; лимиты задаются заранее.

### 7.10. Чего не копировать из источников

* Число хуков (53) и «40% blocking» как цель: количество не равно безопасности.
* Абсолютную слепоту пары «тест/код» как универсальный режим: она нужна для проверки
  полноты контракта, но мешает ремонту сложного проекта.
* Аналогии NVP / recovery blocks / WAL как гарантии: это язык, а не свойства.
* «Ready» как одобрение инструмента и «validate» как доказательство правильности.
* Многолетнюю церемонию для всех задач: без классов риска процесс умрёт от стоимости.
* Параллелизм по умолчанию: Cognition-предупреждение остаётся в силе, пока нет измерений.

**Минимальный набор для пилота** (не больше): Git/PR + `product-specs`, OpenSpec CLI,

для поиска, каталог `evidence/`, один CI-job. Всё остальное — после того, как пилот
покажет очередь и узкое место. Инструмент, который не влияет на гейт или доказательство,
в пилот не берём.

## 8. План внедрения

Оценки — ориентировочные, для одного опытного разработчика с агентами; зависят от
числа сервисов и строгости L2. Каждый этап закрывается не «код написан», а
**воспроизводимым отказом**: запрещённый сценарий действительно запрещён, разрешённый —
работает, и оба записаны в тесты.

### Этап 0. Стабилизация и решения (≈1 неделя) ✅

Сделано: падающий тест исправлен, ключевые числа в README/AGENTS/ROADMAP/FACTS
синхронизированы, классы риска и DoR/DoD зафиксированы в этом документе, пилот
назван (`add-change-layer`). Переключение на `workspace-write` остаётся за человеком
(сессия — `danger-full-access`).

* Починить падающий `test_browser_mcp`; синхронизировать числа в README/AGENTS/ROADMAP/
  FACTS; убрать `.harness/status.json` из описания или начать его генерировать.
* Зафиксировать: классы риска L0–L3, DoR/DoD, схему review-записи, порог GAP,
  обязательных reviewers, опорную среду.
* Переключить рабочие сессии на `workspace-write` + подтверждения; проверить, что

* Выбрать пилотное изменение (одна возможность, 1–2 сервиса), владельца, reviewers,

### Этап 1. Change-ядро (2–3 недели) ✅ (v1)

`change_reviews` и `tasks.change_id` (схема v4), CLI `harness change`, review-записи
файлами и в БД, trace-матрица с ID, `Ready`-гейт, полный `spec_ref`, ужесточённый

* Запись change в SQLite (`changes`: id, revision, risk_class, owner, spec_ref; шаблон

### Этап 5. Мультирепозиторий и параллелизм (3–4 недели) ✅ (v1)

Запись в явно открытый сервис (`--service-write`) разрешена worker'у через

**Не сделано:** push/PR сервисных репозиториев; merge order как очередь;
shell-запись в сервис.

* `spec_root` отдельно от `code_root`; снимок на репозиторий; change-кандидат как набор
  SHA; PR-метаданные.
* Лэйны на задачу по репозиториям; DAG задач с зависимостями; волна с барьером;
  раздельные ресурсы (БД/порты/каталоги).
* Выход: две задачи в разных сервисах не смешивают write-set; интеграция проверяется

* Владельцы политики и evals; проверка изменений хуков отдельным агентом.
* Выход: процесс деградирует видимо, а не молча; каждое изменение правила имеет

### Чего не делать на старте

* Не строить 53 хука и не гнаться за «40% blocking».
* Не начинать с параллелизма и UI.
* Не переносить FSM/бюджет/вердикт в плагин.
* Не автоматизировать приёмку бизнес-результата.
* Не включать `danger-full-access` как рабочий режим.
* Не требовать полной церемонии для L0-задач.

### Пилот на этом репозитории (если отдельного продукта пока нет)

Процесс можно проверить на самом `harness`, не дожидаясь большого проекта. Это честный
пилот: изменение реальное, код реальный, роли можно раздать агентам, а человек остаётся
владельцем продукта и политики.

* **Change:** `add-change-fsm` — реализация уровня изменения, описанного в этом документе.
  Продуктовые артефакты живут в `openspec/changes/add-change-fsm/`, код — в `harness/`.
* **Роли:** человек — владелец продукта/политики; BA-агент — proposal и дельта specs;
  SA-агент — design (таблица состояний, guard'ы, запись change) и tasks; DEV-агент —
  код и тесты; QA-агент — кейсы переходов и baseline/candidate; verifier — отдельный агент
  с read-only доступом к продукту.
* **Гейты:** Ready — четыре review-записи + trace 100% + GAP=0 + `spec_ref`; диспетч
  задач — только после Ready; коммит — только с PASS и `spec_ref`; приёмка — человек;
  archive — после приёмки.
* **Что проверяем на пилоте:** работает ли передача «артефакт + review» без чата; ловит ли
  trace-матрица разрыв; отказывает ли `specgate` на чужом/архивном change; сколько времени
  занимает review; где очередь; сколько стоит принятое изменение.
* **Чего не делаем:** не строим в пилоте весь будущий фреймворк (UI, параллелизм, CI) —
  только один change и минимальный набор артефактов. Иначе пилот сам станет проектом
  на квартал.

Критерий успеха пилота: любой участник находит правило, версию реализации и проверку
результата без переписки; все гейты пройдены или явно объяснены; метрики lead time и
review latency сняты.

## 9. Решения, которые нужны от вас

Эти вопросы меняют архитектуру, поэтому их лучше закрыть до Этапа 1.

1. **Кто исполняет роли.** Один человек + агенты или реальная команда с людьми? От этого
   зависит, где заканчивается автоматизация и начинается очередь review.
2. **Топология репозиториев.** Есть ли отдельный `product-specs` и сколько сервисов?
   Можно ли завести его как пилотный, не мигрируя всю wiki?
3. **OpenSpec и CI.** Какая версия CLI, какой Git-хостинг (GitHub/GitLab), есть ли CI
   и опорная среда (staging/production с флагом)?
4. **Классы риска.** Какие изменения считать L2 (деньги, доступ, PII, необратимое) и
   кто подписывает выпуск?
5. **Данные и провайдер.** Что можно отправлять модели, есть ли ограничения на код
   клиента/PII, допустимы ли внешние MCP-серверы?
6. **Пилот.** Какую одну возможность взять первой (1–2 сервиса) и кто её владелец?
7. **Стартовый объём.** Начинаем с Этапа 0–1 (change-ядро) или сразу с пресетов и
   guard'а? Рекомендация: 0 → 1 → 2.
8. **Где живёт реализация.** Продолжаем в этом репозитории (`harness`) или разделяем:
   ядро здесь, процессные артефакты — в `product-specs` пилота?
9. **Формат отчётности.** Нужна ли UI-доска сразу или достаточно CLI/JSON и Markdown?
10. **Бюджет и срок.** Ориентир по человеко-неделям и допустимая стоимость прогонов.

## Приложение C. Глоссарий

| Термин | Значение |
|---|---|
| change | Изменение одной возможности: папка `openspec/changes/<id>/` |
| revision | Редакция плана; увеличивается при любой правке артефактов после Ready |
| spec_ref | Полный Git SHA согласованного плана |
| REQ | Требование в дельте specs с наблюдаемым результатом |
| CASE | Проверочный сценарий (Gherkin/тест), связанный с REQ |
| AC | Критерий приёмки в брифе, связанный с REQ/CASE |
| TASK | Задача из `tasks.md` (repo, зависимости, способ проверки) |
| brief | Самодостаточный пакет задачи для исполнителя |
| snapshot | Хеш состояния кандидата; привязка вердикта |
| verdict | Объект независимой проверки: критерий → доказательство → результат |
| evidence | Пакет доказательств: вердикты, прогоны, отчёты, версии |
| ACCEPT | Запись приёмки бизнес-результата владельцем продукта |
| L0–L3 | Классы риска и соответствующие уровни церемонии |

## Приложение D. Новые правила: пары проверок

Для каждого правила — положительный и отрицательный сценарий; без пары правило не
включается (принцип `harness coverage`).

| Правило | Разрешённый случай | Запрещённый случай |
|---|---|---|
| R-CHG-1 | `IN_PROGRESS→IMPLEMENTED` при всех COMMITTED | `commit change` из `IN_PROGRESS` отвергается |
| R-REF-1 | бриф с полным `spec_ref`, коммит с trailer | бриф с именем ветки → отказ |
| R-REV-1 | review с hash, критериями, вердиктом | review без hash/критериев → отказ |
| R-REV-2 | автор и approver разные | автор утверждает свой артефакт → отказ |
| R-TRACE-2 | 100% обязательных REQ покрыты | REQ без CASE → Ready заблокирован |
| R-TASK-1 | задача с repo и check | задача без repo/check → Ready заблокирован |
| R-DRIFT-1 | задача на текущей revision | задача на старой revision → stale/отказ |
| R-QA-1 | отчёт со всеми версиями | отчёт без версий → VERIFIED заблокирован |
| R-QA-2 | discovery подтвердил CASE | нулевой прогон → отказ |
| R-ACCEPT-1 | ACCEPT с критериями и SHA | archive без ACCEPT → отказ |
| R-ACCEPT-2 | L2: release-запись + человек | L2 без подтверждения → отказ |
| R-GAP-2 | обратимое решение записано | денежный GAP без человека → dispatch запрещён |
| R-EXIT-1 | пакет с проблемой/влиянием/вариантами | эскалация без вариантов → soft-отказ |
| R-REPO-1 | запись в назначенный repo/путь | запись в чужой repo → deny |
| R-FIND-3 | закрытие с причиной и владельцем | закрытие без причины → deny |
