# Архитектура контрольного слоя

Задача: сделать так, чтобы выпуск непроверенного или изменившегося после проверки
результата был **невозможен обычным разрешённым путём**, а не «не рекомендован».

```
                    ┌──────────────────────────────────────────┐
   задача ─────────▶│  управляющий процесс (harness)           │
                    │  состояние · бюджет · вердикты · журнал  │
                    └───────┬──────────────┬───────────────────┘
                            │ политика      │ guard'ы переходов
                    ┌───────▼───────┐  ┌───▼──────────────┐
                    │ хуки событий  │  │ автомат состояний │
                    │ deny/advise   │  │ 11 состояний      │
                    └───────┬───────┘  └───┬──────────────┘
                            │              │
              ┌─────────────▼───┐   ┌──────▼────────┐
              │ роли (права)    │   │ артефакты      │
              │ orchestrator    │   │ бриф · снимок  │
              │ worker          │   │ вердикт · лог  │
              │ verifier        │   │ находки        │
              └─────────────────┘   └────────────────┘
```

## Слои

| Слой | Модуль | Что решает | Можно ли обойти |
|---|---|---|---|
| Политика ролей | `harness/policy.py`, `policies/policy.json` | кому что можно читать/писать | да, если роль может менять политику — поэтому политика защищена |
| Шлюз инструментов | `harness/gateway.py` | что агент вообще может сделать | да, если агент пишет напрямую — ловится на коммите |
| Хуки инструментов | `harness/hooks.py` | допустимость конкретного действия | да, через обходные пути (см. residual риски) |
| Автомат | `harness/fsm.py` | допустимость перехода и порядок работ | нет: переход либо есть в таблице, либо отказ |
| Прогон проверок | `harness/checks.py` | чем подтверждён критерий | нет: вердикт собирается из кодов возврата |
| Финализатор | `harness/finalize.py` | что попадёт в коммит | нет: write-set и снимок сверяются до коммита |
| Состояние | `harness/state.py` (SQLite) | бюджет, снимки, вердикты, журнал, коммиты | нет без доступа к файлу БД |
| Контракты | `harness/brief.py`, `harness/verdict.py` | полнота и непротиворечивость артефактов | нет: проверка структурная |
| Измерение | `harness/evals.py` | качество проверяющего | — (это метрика, не гейт) |
| Сторож | `harness/watchdog.py` | отзыв просроченных полномочий | нет, если запущен отдельным процессом |
| Лейны | `harness/lanes.py` | изоляция дерева и порядок слияния | нет: мьютекс и откат конфликта |
| Бюджет | `harness/cost.py` | расход до запуска | нет, если бюджет задан в брифе |
| Дисциплина правил | `harness/rulechange.py` | причина и тесты изменения | нет: дрейф виден по отпечатку |
| Драйвер | `harness/run.py` | весь маршрут одной командой | переходы всё равно идут через автомат |

Ключевое разделение: **шлюз и хуки** отвечают на вопрос «можно ли это действие»,
**автомат** — «можно ли этот переход», **финализатор** — «можно ли это выпустить».
Первое эвристично, второе и третье — нет.

## Состояния и переходы

```
CLAIMED ──attach_brief──▶ BRIEF_READY ──dispatch──▶ RUNNING ──submit──▶ VERIFYING
   │                          │                        │                  │
   │ dispatch                 │ cancel/escalate        │ timeout          ├─PASS──▶ ACCEPTED ──commit──▶ COMMITTED
   ▼ (deny R-BRIEF-1)         ▼                        ▼                  ├─FAIL & iter<3 ─▶ REWORK_READY ──dispatch──┐
  ...                     CANCELLED                TIMED_OUT              ├─FAIL & iter=3 ─▶ ESCALATED (терминальное)  │
                                                        │                  └─INCONCLUSIVE ──▶ VERIFY_BLOCKED        │
                                                        ├─requeue──▶ REWORK_READY ◀───────────────────────────────────┘
                                                        └─escalate─▶ ESCALATED

ACCEPTED ──invalidate──▶ REWORK_READY      ACCEPTED ──commit(snapshot≠accepted)──▶ deny R-SNAPSHOT-1
VERIFY_BLOCKED ──submit/recheck──▶ VERIFYING ──escalate──▶ ESCALATED
```

Терминальные: `COMMITTED`, `ESCALATED`, `CANCELLED`.

### Охранные условия (guard'ы)

| Переход | Условие | Правило при отказе |
|---|---|---|
| `attach_brief` | бриф валиден, `task_id` совпадает | `R-BRIEF-1` |
| `dispatch` | бриф есть и валиден, нет блокирующих вопросов, `attempt < max` | `R-BRIEF-1`, `R-GAP-1`, `R-BUDGET-1` |
| `submit` | `attempt` совпадает с активной, снимок передан, срок не истёк | `R-TIMEOUT-1`, `R-SNAPSHOT-1` |
| `verdict` | контракт вердикта, совпадение задачи/попытки/снимка, роль ≠ worker | `R-VERIFY-1`, `R-TIMEOUT-1`, `R-SNAPSHOT-1` |
| `commit` | последний вердикт — PASS, не устарел, снимок совпадает с принятым, есть pipeline-log | `R-VERIFY-1`, `R-SNAPSHOT-1`, `R-COMMIT-1`, `R-COMMIT-2` |
| `invalidate` / `requeue` | `attempt < max` | `R-BUDGET-2` |

### Инварианты

1. `attempt` только растёт и никогда не сбрасывается сменой агента или переименованием задачи.
2. Вердикт, сохранённый для снимка `S`, не действует для снимка `S' ≠ S` (`stale`).
3. `PASS` без покрытия обязательных критериев превращается в `INCONCLUSIVE` до сохранения.
4. Повторная доставка события (`event_id`) не создаёт второго эффекта.
5. Каждый переход оставляет запись в `events` и `pipeline_log`.
6. Состояние меняется только через таблицу переходов: «коммитить» из `RUNNING` отвергается
   независимо от формулировки сообщения агента.
7. Коммит содержит только пути из `allowed_files` и `pipeline-log/<task>.jsonl`.
8. Принятый снимок и закоммиченное состояние совпадают: `accepted_snapshot` сверяется
   непосредственно перед `git commit`.

## Уровень изменения (`changefsm.py`)

Задача отвечает на вопрос «сделай этот кусок», изменение — «что и зачем делаем, кто
согласовал и на какой редакции». Уровень включается, когда change зарегистрирован
(`harness change new`); брифы без `change_id` работают по-старому.

```
DRAFT ─▶ EXPLORED ─▶ PROPOSED ─▶ SPECS_AGREED ─▶ DESIGN_AGREED ─▶ READY
  │                                                                 │
  └─ revise: revision+1, назад в SPECS_AGREED                       ▼
READY ─▶ IN_PROGRESS ─▶ IMPLEMENTED ─▶ VERIFIED ─▶ RELEASED ─▶ ACCEPTED ─▶ ARCHIVED
```

| Слой | Где | Что проверяет |
|---|---|---|
| Автомат изменения | `changefsm.TRANSITIONS`, `transition()` | переход есть в таблице; запрещённый отклоняется с `R-CHG-1` |
| Review-записи | `changefsm.review()`, таблица `change_reviews`, файлы `changes/<id>/reviews/` | артефакт, его sha256, редакция, автор ≠ проверяющий, критерии (`R-REV-1`, `R-REV-2`) |
| Ready-гейт | `changefsm.ready_check()` | review всех ролей по текущим хешам, trace, GAP=0, полный `spec_ref` |
| Трассировка | `changefsm.check_trace()` | каждое `REQ` имеет `CASE`, каждая задача — файл и проверку (`R-TRACE-2`) |
| Привязка задач | `fsm._guard_dispatch` → `changefsm.gate_dispatch()` | диспетч только из `READY`/`IN_PROGRESS`, `spec_ref` совпадает (`R-CHG-1`, `R-REF-1`) |
| Коммит | `specgate.check()` | живой change (не архив) и совпадающий digest спеки (`R-SPEC-1`) |

Состояние — SQLite (`changes`, `change_events`, `change_reviews`, `tasks.change_id`,
схема v4); review-записи дополнительно пишутся файлами в каталог change, чтобы их
видел Git. Ready не хранится флагом: он пересчитывается перед переходом, поэтому
правка плана после Ready снова закрывает гейт (ревизия увеличивается, `spec_ref`
сбрасывается).

## Проверка, приёмка и evidence

`VERIFIED` не выводится из «тесты прошли» и не считается по состоянию задач:

| Объект | Где | Что проверяется |
|---|---|---|
| `verification.json` | каталог change | baseline и candidate: command, ref, runner, environment, tests_ran, failures, exit_code; diff новых падений |
| `release.json` | каталог change | `spec_ref`, среда, сервисы (полный SHA), кто выпустил, флаг |
| `acceptance.json` | каталог change | принимающий, критерии, среда, сервисы, остаточные риски |
| `closing.json` | каталог change | `specs_synced`, `cases_promoted`, `contracts_promoted`, кто закрыл |
| `evidence/change-<id>/manifest.json` | evidence | sha256 и размер каждого файла пакета |

Гейты: `IMPLEMENTED → VERIFIED` требует отчёт с версиями и ненулевыми прогонами;
`VERIFIED → RELEASED` — release-запись; `RELEASED → ACCEPTED` — acceptance; `ACCEPTED →
ARCHIVED` — closing + манифест evidence с verification и acceptance. Для L0 приёмка
без release допустима; для L2 `by_role`/`accepted_by_role` обязаны быть `human`.

Baseline может выполняться в отдельном git-worktree на `--ref` (принятая версия),
candidate — в рабочем дереве. Парсер понимает unittest и pytest; нестандартный runner
обязан назвать число тестов, иначе отчёт не проходит — «ноль тестов» не считается
проверкой. Записи и evidence — файлы, а не строки БД: их видит Git и закрывающий PR.
Подпись/вывоз evidence — остаток Этапа 4.

## Мультисервисные изменения (v1)

`change.payload.services` хранит список `{name, path, base_commit}`; сервисы
объявляются `change new --service name=PATH[@SHA]`, попадают в бриф и валидируются
(непустые имя и путь, полный SHA). Путь — ссылка для чтения и verification, не граница
записи. Verification пишет прогоны по ключам
`service:baseline`/`service:candidate`; сервис `repo` сохраняет старые ключи
`baseline`/`candidate`. `check_report` требует оба режима для каждого сервиса,
объявленного в change, и считает новые падения отдельно по сервисам. Baseline может
идти в git-worktree сервиса на `--ref`, candidate — в его рабочем дереве.

Release/acceptance принимают несколько `--service name=SHA` и обязаны сохранять порядок
объявления сервисов: это merge order, он фиксируется в `release.json`,
`acceptance.json` и evidence-манифесте; другой порядок отклоняется.

Запись в сервис — явная: `change new --service-write NAME` ставит `write=true`, в
брифе появляются ключи `service:<name>/<relative>`. Policy резолвит абсолютный путь
под сервисный корень (`resolve_target`), требует `role.can_write_services` и
`service.write`, а `allowed_files` проверяются по ключу; gateway и guard делают
realpath-проверку, чтобы симлинк/junction не вывел из корня. Если target лежит внутри
главного корня (сервис внутри проекта или сервис-предок), те же protected/spec/product
правила проверяются по главному относительному пути; корень-предок и корень-сервис
`change new` отклоняет. Shell-запись в сервис не открывается. Snapshot задачи
включает деревья writable-сервисов, `finalize` коммитит каждый сервис отдельно и
пишет SHA в `commits`/evidence; push и merge order остаются вне процесса.

## Метрики, доска и CI (`metrics.py`, `ci.py`)

Метрики — проекция состояния, а не отдельное хранилище. `collect` читает
`changes/change_events/change_reviews/tasks/attempts/verdicts/findings/costs` и файлы
`verification.json`, считает очередь, lead time Ready → Accept, rework rate, состояние
verification и evidence, открытые находки. Улучшить цифры отдельно от процесса нельзя.

Доска (`harness board --out`) — самодостаточный HTML без сети и JS: изменения, review,
trace/verify/release/accept, очередь и риски. Все поля экранируются. `board --serve`
поднимает локальный HTTP-сервер (`HTTPServer`, своё SQLite-соединение на запрос) и
отдаёт `/`, `/metrics.json`, `/healthz`; HTML автообновляется каждые 15 секунд. Это
снимок/локальная доска, а не встроенная панель DSH GUI.

`harness otel` строит OTLP/HTTP JSON (`resourceMetrics` → `scopeMetrics` → gauge) с
метриками процесса и ресурсом `service.name`/`service.version`/`vcs.revision`;
отправка — POST на endpoint или файл. Protobuf/gRPC не реализованы сознательно.
Агентские трейсы DSH экспортирует сам.

`harness ci` собирает selftest, покрытие правил, метрики и (опционально) unittest в
`evidence/ci-<ts>/report.json` с Git HEAD и версией Python. CI-отчёт отвечает на вопрос
«здоров ли harness», но не заменяет release/accept/archive: зелёный CI и принятый
change — разные вещи. Для headless-пути есть `tools/headless_smoke.py`: он запускает
`dsh headless --json` и пишет evidence; в этой установке прогон дошёл до `final`, но
упёрся в `MISSING_CREDENTIAL` — у headless-профиля нет `DEEPSEEK_API_KEY`. Это
ограничение окружения, а не скрытая неработоспособность.

## Шлюз инструментов (`gateway.py`)

Единственный путь, которым агент трогает файлы и команды. Рантайм не получает
прямого доступа: он шлёт запрос, шлюз спрашивает политику и хуки, исполняет и
пишет аудит.

```json
{"tool": "write_file", "args": {"path": "src/fee.py", "content": "..."}}
```

Порядок проверок на каждый вызов:

1. роль из `HARNESS_ROLE` (нет роли — `R-ROLE-1`);
2. инструмент входит в закрытый список (`R-WORK-2`);
3. задача в состоянии `RUNNING` и срок не истёк (`R-STATE-1`, `R-TIMEOUT-1`);
4. хуки: политика записи, защищённые пути, sleep, git, обходы через shell;
5. путь нормализуется и проверяется через `realpath` (ссылка не должна выводить
   из корня);
6. исполнение: атомарная запись через временный файл, урезанное окружение для
   `run_command` (`PATH`, `HOME`, `TMPDIR`, без `HARNESS_*` и без токенов);
7. запись в `tools_audit`: решение, правило, путь, краткое описание.

`allowed_files` берутся из брифа в состоянии задачи. Если агент передаст свой
список прав в запросе, он будет проигнорирован — это и есть `R-TOOL-1`.

## Процессные роли, пресеты и guard

Процессная роль (`actor_role` брифа: BA/SA/DEV/QA/verifier) переводится в роль
политики и публикуется в `guard-scope.json` при диспетче:

| actor_role | роль политики | что может писать |
|---|---|---|
| BA, SA | `analyst` | `openspec/**`, `docs/**`, `journal/**`; код — нет |
| DEV | `worker` | только `allowed_files`; спеку — нет |
| QA | `qa` | `tests/**`, `openspec/changes/*/cases/**`, `evidence/**` |
| verifier | `verifier` | только `evidence/**`; продукт читает |
| — (нет поля) | `worker` | прежнее поведение |

Guard (`plugins/harness-guard`) держит три класса запретов, которых нет в тексте
брифа: `R-WORK-3` (каталог спеки не пишет рабочий код), `R-TOOL-2`
(`plugin_manager`, marketplace и MCP-префиксы с побочными эффектами закрыты всем,
кроме human/system; читающие `xerj`/`trendshift` разрешены явно) и `R-GAP-2`
(открытый `.harness/gap.json` превращает пишущий вызов в `ask` человеку; чтение
проходит). `ask` не может вернуть синхронный `ctx.tools.guard()`, поэтому это
отдельный listener `tools/pre-execute`.

Пресеты DSH (`plugins/process-presets`) дают каждой роли свою композицию
инструментов и скиллов (`skills/process-*`), но не являются источником прав: путь и
инструмент всё равно проверяет guard по `policy.json`. Пресет без `plugin_manager` и
`workflow` — defence in depth, а не замена политике.

## Изолированный прогон проверок (`checks.py`)

`harness checks run` копирует дерево во временный каталог, выполняет команды из
брифа с таймаутом и сохранением вывода в `evidence/checks-<task>-<ts>/NN/`,
затем собирает вердикт из фактических кодов возврата:

| Что было | Что записывается |
|---|---|
| команда завершилась с кодом 0 | `pass` + путь к артефакту |
| код ≠ 0 или таймаут | `fail` |
| критерий без выполненной команды | `skip` → вердикт `INCONCLUSIVE` |

Продукт при этом не меняется: копия одноразовая. Это не ОС-песочница (нет
изоляции сети и прав пользователя), но «мои тесты прошли» превращается в файл.

## Доверенный финализатор (`finalize.py`)

Коммит делает не агент. Порядок:

1. состояние задачи — `ACCEPTED` (иначе `R-VERIFY-1`);
2. снимок пересчитывается в объявленной области и сверяется с принятым (`R-SNAPSHOT-1`);
3. `git status` → набор изменённых путей; всё вне `allowed_files` блокирует коммит
   (`R-WRITESET-1`) — так виден обход шлюза;
4. пишется `pipeline-log/<task>.jsonl` и добавляется в тот же коммит (log first);
5. коммитятся только разрешённые пути и журнал;
6. после коммита проверяется, что в разрешённой области не осталось грязных файлов;
7. записывается связь «проверенный снимок → sha коммита» в таблицу `commits`
   и событие `commit` переводит задачу в `COMMITTED`.

Хеш коммита нельзя записать внутрь самого коммита, поэтому связь живёт отдельно —
это и есть та тонкость из §7.2 книги, которую нельзя «исправить» требованием к коммиту.

## Watchdog как отдельный процесс (`watchdog.py`)

Таймер живёт вне цикла агента, потому что иначе падение управляющего слоя означает,
что полномочия никто не отзовёт:

```powershell
python -m harness watchdog sweep                 # один проход (cron, CI, таймер)
python -m harness watchdog serve --interval 15   # отдельный процесс
```

Проход ищет задачи, формально ещё `RUNNING`, но с истёкшим `deadline_ts`, и для
каждой: закрывает попытку как `timed_out`, переводит задачу в `TIMED_OUT`, пишет
событие `dispatch_death` с пометкой `synthetic: true` и запись в журнал.

Смерть доставляется отдельным событием намеренно: «исполнитель завершился сам» и
«мы отозвали у него полномочия» не должны выглядеть одинаково. Повторный проход
ничего не отзывает — событие имеет детерминированный идентификатор
`death-<task>-<attempt>`.

## Лейны и слияние (`lanes.py`)

Мутирующая задача работает в собственном `git worktree`; общий ресурс — главное
дерево — защищён мьютексом на слияние.

```powershell
python -m harness lane create --task FEE-101          # worktree + ветка harness/FEE-101
python -m harness lane merge  --task FEE-101          # только для COMMITTED
python -m harness lane list
python -m harness lane remove --task FEE-101
```

Правила слияния:

1. сливается только задача в состоянии `COMMITTED`, и только её зафиксированный коммит;
2. главное дерево должно быть чистым (служебные `.harness/` и `evidence/` не считаются);
3. мьютекс `merge.lock` — один слиятель; ожидание ограничено, протухшая блокировка
   (старше 15 минут) снимается, а не блокирует работу навсегда;
4. при конфликте выполняется `git merge --abort`, а задача помечается для человека:
   координатор продукт не правит;
5. после слияния фиксируется новый `HEAD` как коммит задачи (finalizer = `merge-queue`).

Чего лейны **не** разделяют: тестовые БД, порты, очереди и внешние ресурсы. Это
настраивается в проекте и остаётся в residual риске `R-WAVE-1`.

## Бюджет стоимости (`cost.py`)

Бюджет, который считается после факта, — отчёт, а не ограничение. Гейт стоит перед
диспетчем:

```json
"control": {"budget": {"max_cost": 12, "estimate_per_attempt": 4, "unit": "cost_units"}}
```

```
остаток = max_cost − израсходовано
остаток < estimate_per_attempt  →  запуск отклонён (R-COST-1), решение за человеком
```

Фактический расход записывается явно (`harness cost record`) или из вердикта, если
проверяющий предъявил поле `cost`. Единица — условные единицы: подставлять тарифы
провайдера догадкой нельзя.

**Остаточный риск:** бюджет действует только там, где задан в брифе; оценка попытки —
допущение, а не измерение, и её нужно пересматривать по факту.

## Дисциплина изменения правил (`rulechange.py`)

```powershell
python -m harness rule verify                    # дрейфует ли файл правил без записи
python -m harness rule change --id R-COST-1 --reason "бюджет проверяется до запуска"
```

`rule change` сначала прогоняет исполняемые проверки правила и только потом пишет
запись: причина, отпечаток `rules.json`, число пройденных тестов. `rule verify`
сравнивает текущий отпечаток с последней записью и различает три состояния:

| Состояние | Значение |
|---|---|
| `no_history` | записей ещё нет: это не нарушение, а отсутствие базовой линии |
| `current` | правила не менялись после последней записи |
| `drift` | файл правил менялся без записи причины и прогона тестов |

**Остаточный риск:** сравнение идёт по файлу правил; правка кода хука без правки
`rules.json` этим механизмом не ловится (для неё есть `harness selftest`).

## Драйвер цикла (`run.py`)

Собирает слои в один прогон: `harness run` проходит маршрут бриф → диспетч →
воркер → снимок → проверка → вердикт → (доработка ≤ 3) → PASS → финализатор → коммит.

Исполнитель и проверяющий — **внешние команды**: харнесс не знает, LLM внутри или
скрипт, и задаёт только контракт (окружение на входе, код возврата, формат вердикта).

```
попытка N: dispatch → worker (exit 0?) → submit(snapshot) → verifier → verdict
                                                    │ FAIL → feedback-пакет → попытка N+1
                                                    │ ERROR/TIMEOUT → VERIFY_BLOCKED
                                                    └ PASS → ACCEPTED → finalize → COMMITTED
```

Отдельно учтены три вещи, которые обычно и ломают такие драйверы:

* **сбой воркера ≠ дефект кода**: exit ≠ 0 фиксируется как `ERROR` и уводит задачу в
  `VERIFY_BLOCKED`, а не в доработку;
* **в лейне разделены два корня**: `HARNESS_ROOT` (файлы в worktree) и
  `HARNESS_CONTROL_ROOT`/`HARNESS_STATE` (политика и состояние в главном дереве);
* **область снимка считается от корня работы**, а не от главного дерева — иначе путь
  лейна удваивается и снимок получается пустым.

## Артефакты

### Бриф (`schemas/brief.schema.json`)
Группы полей: идентичность (`task_id`, `brief_version`, `base_commit`, `spec_version`),
назначение (`goal`, `expected_behavior`, `scope`), доступ (`allowed_read`,
`allowed_files`), контракт (`names`, `types`, `required_fields`, `error_codes`, `units`,
`boundary_rules`), приёмка (`criteria[{id, statement, mandatory, check}]`,
`check_commands`), управление (`attempt_limit`, `open_questions`, `escalation_route`).

Валидатор различает: **пустое поле** (`E_EMPTY_FIELD`), **отсутствующее**
(`E_MISSING_FIELD`), **противоречивое** (`E_CONTRADICTION`), **непроверяемое**
(`E_UNVERIFIABLE` — обязательный критерий без команды проверки). Это разные адресаты
исправления, поэтому разные коды.

### Снимок (`snapshot.py`)
`sha256` по каноническому манифесту «путь + хеш файла» дерева кандидата. Ловит изменение,
но не подтверждает авторство — усиление требует доверенного источника записи.

### Вердикт (`schemas/verdict.schema.json`)
`PASS | FAIL | INCONCLUSIVE | ERROR | TIMEOUT | CANCELLED`; критерии с обязательным
доказательством для `pass`; находки с серьёзностью; `scenario` для адверсального.
Понижение вердикта — штатное поведение, а не ошибка:
* нет покрытия обязательных критериев → `INCONCLUSIVE`;
* открытая находка `blocker/major` при `PASS` → `INCONCLUSIVE`;
* адверсальный `PASS` без выполненного сценария → `INCONCLUSIVE`;
* `FAIL` только по косметике → `INCONCLUSIVE`.

### Вердикт → решение автомата
`PASS` → `ACCEPTED`; `FAIL` → `REWORK_READY` при остатке бюджета, иначе `ESCALATED`;
`INCONCLUSIVE/ERROR/TIMEOUT` → `VERIFY_BLOCKED` (ни выпуска, ни ложного дефекта).

## Протокол хука

Событие `pretooluse`, контекст на stdin:

```json
{
  "event": "pretooluse",
  "tool": "write_file",
  "role": "worker",
  "claimed_role": "worker",
  "task_id": "FEE-101",
  "path": "src/fee.py",
  "allowed_files": ["src/fee.py"]
}
```

Ответ:

```json
{ "decision": "deny", "rule": "R-WORK-1", "reason": "src/billing.py вне allowed_files брифа" }
```

`deny` доминирует над `advise`; ошибка внутри хука даёт `deny` (`R-HOOK-ERR`), а не
молчаливое разрешение. Роль берётся из окружения запускающего процесса; расхождение с
`claimed_role` — отказ `R-ROLE-1`.

Точка интеграции с реальным рантаймом:

```powershell
"$ctx" | python -m harness --root . hook pretooluse --stdin
# exit 0 = allow/advise, exit 2 = deny
```

## Что эта система НЕ защищает

Честный список; он же — разделы «Пробелы» и «Делегировано» в `docs/RULES_MATRIX.md`.

Часть прежних пробелов закрыта не нами, а рантаймом DSH и плагинами: песочница
(`dsh-sandbox`), наблюдённое состояние файлов (`fs-observation-policy`), таймауты
инструментов, повторные вызовы, одобрения (`ctx.approval`). Такие правила имеют
статус `delegated`. Это значит: механизм существует, но его исправность — не наша
заслуга, и её надо проверять отдельно (`harness doctor`, `docs/PLUGINS.md`).

1. **Обход шлюза прямой записью.** Ловится на коммите через write-set (R-WRITESET-1),
   но до коммита дерево уже изменено — «не попало в продукт» ≠ «не произошло».
2. **Эффекты `run_command`.** Шлюз видит команду, а не то, что она сделала с файлами
   вне разрешённой области; частично прикрыто write-set и обязательной проверкой.
3. **Права процесса.** Верификатор и исполнитель работают под одним пользователем:
   `checks run` даёт копию и таймаут, но не отдельного пользователя и не сеть.
4. **Смысловой дефект, который проверяющий не заметил.** Измеряется evals, не хуком.
5. **Общие ресурсы лейнов.** Worktree разделяет файлы, но не тестовые БД, порты и
   очереди: два лейна могут мешать друг другу на уровне выполнения.
6. **Остановка самого управляющего процесса.** Watchdog теперь отдельный процесс,
   но если не запущен и он, отзыв не произойдёт.
7. **Грязные файлы, существовавшие до задачи.** Финализатор видит их как
   нарушение write-set и требует решения, а не молча коммитит.
8. **Сеть для исполнителя.** `run_command` не изолирует сеть; изоляция есть только
   у прогона проверок, и только при доступном docker.
9. **Оценка бюджета.** Запуск останавливается по оценке, а оценка — допущение:
   дешёвая модель с плохим результатом может обойтись дороже расчётной.
10. **Правка кода хука без правки правил.** `rule verify` видит только файл правил;
    расхождение «текст правила ↔ код хука» ловится прогоном `selftest`, а не отпечатком.

```
harness/            пакет: cli, changefsm, fsm, state, policy, hooks, gateway, checks, finalize,
                    brief, verdict, snapshot, findings, rules, evals, selftest, demo
policies/           policy.json (полномочия), rules.json (матрица правил)
schemas/            JSON-схемы брифа и вердикта
templates/          примеры артефактов для людей
examples/           учебные верификаторы и размеченный набор evals
tests/              unittest: свойства, а не счастливые пути
tools/              вспомогательное: lessons.py, recall.py, pdf_extract.py,
                    trendshift.py, browser_mcp.py, mcp_stdio.py
plugins/            host-плагины DSH: harness-guard, voice-ru
docs/               ANALYSIS, ARCHITECTURE, ROADMAP, RUNNING, PLUGIN, PLUGINS,
                    LESSONS, RECALL, TRENDSHIFT, BROWSER, XERJ, RULES_MATRIX
bin/                обёртки harness / harness.cmd
```

Зависимостей нет: только стандартная библиотека Python 3.10+. Контрольный слой должен
запускаться там, где нет ничего, кроме интерпретатора.
