# Архитектура контрольного слоя

Задача: сделать так, чтобы выпуск непроверенного или изменившегося после проверки
результата был **невозможен обычным разрешённым путём**, а не «не рекомендован».

```
                    ┌──────────────────────────────────────────┐
   задача ─────────▶│  управляющий процесс (harness)           │
                    │  состояние · бюджет · вердикты · журнал  │
                    └───────┬──────────────┬───────────────────┘
                            │ политика      │ guard'ы переходов
                    ┌───────▼───────┐  ┌───▼──────────────┐
                    │ хуки событий  │  │ автомат состояний │
                    │ deny/advise   │  │ 11 состояний      │
                    └───────┬───────┘  └───┬──────────────┘
                            │              │
              ┌─────────────▼───┐   ┌──────▼────────┐
              │ роли (права)    │   │ артефакты      │
              │ orchestrator    │   │ бриф · снимок  │
              │ worker          │   │ вердикт · лог  │
              │ verifier        │   │ находки        │
              └─────────────────┘   └────────────────┘
```

## Слои

| Слой | Модуль | Что решает | Можно ли обойти |
|---|---|---|---|
| Политика ролей | `harness/policy.py`, `policies/policy.json` | кому что можно читать/писать | да, если роль может менять политику — поэтому политика защищена |
| Хуки инструментов | `harness/hooks.py` | допустимость конкретного действия | да, через обходные пути (см. residual риски) |
| Автомат | `harness/fsm.py` | допустимость перехода и порядок работ | нет: переход либо есть в таблице, либо отказ |
| Состояние | `harness/state.py` (SQLite) | бюджет, снимки, вердикты, журнал | нет без доступа к файлу БД |
| Контракты | `harness/brief.py`, `harness/verdict.py` | полнота и непротиворечивость артефактов | нет: проверка структурная |
| Измерение | `harness/evals.py` | качество проверяющего | — (это метрика, не гейт) |

Ключевое разделение: **хуки** отвечают на вопрос «можно ли это действие», **автомат** —
«можно ли этот переход». Первое эвристично, второе — нет.

## Состояния и переходы

```
CLAIMED ──attach_brief──▶ BRIEF_READY ──dispatch──▶ RUNNING ──submit──▶ VERIFYING
   │                          │                        │                  │
   │ dispatch                 │ cancel/escalate        │ timeout          ├─PASS──▶ ACCEPTED ──commit──▶ COMMITTED
   ▼ (deny R-BRIEF-1)         ▼                        ▼                  ├─FAIL & iter<3 ─▶ REWORK_READY ──dispatch──┐
  ...                     CANCELLED                TIMED_OUT              ├─FAIL & iter=3 ─▶ ESCALATED (терминальное)  │
                                                        │                  └─INCONCLUSIVE ──▶ VERIFY_BLOCKED        │
                                                        ├─requeue──▶ REWORK_READY ◀───────────────────────────────────┘
                                                        └─escalate─▶ ESCALATED

ACCEPTED ──invalidate──▶ REWORK_READY      ACCEPTED ──commit(snapshot≠accepted)──▶ deny R-SNAPSHOT-1
VERIFY_BLOCKED ──submit/recheck──▶ VERIFYING ──escalate──▶ ESCALATED
```

Терминальные: `COMMITTED`, `ESCALATED`, `CANCELLED`.

### Охранные условия (guard'ы)

| Переход | Условие | Правило при отказе |
|---|---|---|
| `attach_brief` | бриф валиден, `task_id` совпадает | `R-BRIEF-1` |
| `dispatch` | бриф есть и валиден, нет блокирующих вопросов, `attempt < max` | `R-BRIEF-1`, `R-GAP-1`, `R-BUDGET-1` |
| `submit` | `attempt` совпадает с активной, снимок передан, срок не истёк | `R-TIMEOUT-1`, `R-SNAPSHOT-1` |
| `verdict` | контракт вердикта, совпадение задачи/попытки/снимка, роль ≠ worker | `R-VERIFY-1`, `R-TIMEOUT-1`, `R-SNAPSHOT-1` |
| `commit` | последний вердикт — PASS, не устарел, снимок совпадает с принятым, есть pipeline-log | `R-VERIFY-1`, `R-SNAPSHOT-1`, `R-COMMIT-1`, `R-COMMIT-2` |
| `invalidate` / `requeue` | `attempt < max` | `R-BUDGET-2` |

### Инварианты

1. `attempt` только растёт и никогда не сбрасывается сменой агента или переименованием задачи.
2. Вердикт, сохранённый для снимка `S`, не действует для снимка `S' ≠ S` (`stale`).
3. `PASS` без покрытия обязательных критериев превращается в `INCONCLUSIVE` до сохранения.
4. Повторная доставка события (`event_id`) не создаёт второго эффекта.
5. Каждый переход оставляет запись в `events` и `pipeline_log`.
6. Состояние меняется только через таблицу переходов: «коммитить» из `RUNNING` отвергается
   независимо от формулировки сообщения агента.

## Артефакты

### Бриф (`schemas/brief.schema.json`)
Группы полей: идентичность (`task_id`, `brief_version`, `base_commit`, `spec_version`),
назначение (`goal`, `expected_behavior`, `scope`), доступ (`allowed_read`,
`allowed_files`), контракт (`names`, `types`, `required_fields`, `error_codes`, `units`,
`boundary_rules`), приёмка (`criteria[{id, statement, mandatory, check}]`,
`check_commands`), управление (`attempt_limit`, `open_questions`, `escalation_route`).

Валидатор различает: **пустое поле** (`E_EMPTY_FIELD`), **отсутствующее**
(`E_MISSING_FIELD`), **противоречивое** (`E_CONTRADICTION`), **непроверяемое**
(`E_UNVERIFIABLE` — обязательный критерий без команды проверки). Это разные адресаты
исправления, поэтому разные коды.

### Снимок (`snapshot.py`)
`sha256` по каноническому манифесту «путь + хеш файла» дерева кандидата. Ловит изменение,
но не подтверждает авторство — усиление требует доверенного источника записи.

### Вердикт (`schemas/verdict.schema.json`)
`PASS | FAIL | INCONCLUSIVE | ERROR | TIMEOUT | CANCELLED`; критерии с обязательным
доказательством для `pass`; находки с серьёзностью; `scenario` для адверсального.
Понижение вердикта — штатное поведение, а не ошибка:
* нет покрытия обязательных критериев → `INCONCLUSIVE`;
* открытая находка `blocker/major` при `PASS` → `INCONCLUSIVE`;
* адверсальный `PASS` без выполненного сценария → `INCONCLUSIVE`;
* `FAIL` только по косметике → `INCONCLUSIVE`.

### Вердикт → решение автомата
`PASS` → `ACCEPTED`; `FAIL` → `REWORK_READY` при остатке бюджета, иначе `ESCALATED`;
`INCONCLUSIVE/ERROR/TIMEOUT` → `VERIFY_BLOCKED` (ни выпуска, ни ложного дефекта).

## Протокол хука

Событие `pretooluse`, контекст на stdin:

```json
{
  "event": "pretooluse",
  "tool": "write_file",
  "role": "worker",
  "claimed_role": "worker",
  "task_id": "FEE-101",
  "path": "src/fee.py",
  "allowed_files": ["src/fee.py"]
}
```

Ответ:

```json
{ "decision": "deny", "rule": "R-WORK-1", "reason": "src/billing.py вне allowed_files брифа" }
```

`deny` доминирует над `advise`; ошибка внутри хука даёт `deny` (`R-HOOK-ERR`), а не
молчаливое разрешение. Роль берётся из окружения запускающего процесса; расхождение с
`claimed_role` — отказ `R-ROLE-1`.

Точка интеграции с реальным рантаймом:

```powershell
"$ctx" | python -m harness --root . hook pretooluse --stdin
# exit 0 = allow/advise, exit 2 = deny
```

## Что эта система НЕ защищает

Честный список; он же — раздел «Пробелы» в `docs/RULES_MATRIX.md`.

1. **Прямой вызов исполнителя в обход управляющего процесса.** Счётчик попыток и
   запрет коммита действуют только для тех, кто ходит через `harness`.
2. **Запись дочерним процессом интерпретатора.** Хук видит команду, но не то, что
   делает запущенная программа.
3. **Запуск проектного кода с полными правами проверяющего.** Нужен отдельный
   изолированный тест-раннер (следующий этап).
4. **Смысловой дефект, который проверяющий не заметил.** Измеряется evals, не хуком.
5. **Параллельная запись.** В v0 её просто нет: одна задача — один исполнитель.
6. **Остановка самого управляющего процесса.** Watchdog живёт в нём же; при падении
   процесса полномочия не отзываются автоматически (состояние при этом сохраняется).

## Структура репозитория

```
harness/            пакет: cli, fsm, state, policy, hooks, brief, verdict, snapshot,
                    findings, rules, evals, selftest, demo
policies/           policy.json (полномочия), rules.json (матрица правил)
schemas/            JSON-схемы брифа и вердикта
templates/          примеры артефактов для людей
examples/           учебные верификаторы и размеченный набор evals
tests/              unittest: свойства, а не счастливые пути
docs/               ANALYSIS, ARCHITECTURE, ROADMAP, RULES_MATRIX (генерируется)
bin/                обёртки harness / harness.cmd
```

Зависимостей нет: только стандартная библиотека Python 3.10+. Контрольный слой должен
запускаться там, где нет ничего, кроме интерпретатора.
