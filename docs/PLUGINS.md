# Что уже есть в экосистеме и что из этого брать

Проверено 25.10.2026: по поставляемому коду DSH (`app.asar`), реестру npm и
GitHub-топику `dsh-plugin`. Ниже — не список «интересных плагинов», а разбор
наших пробелов и того, чем их закрывать: своим, чужим или уже включённым.

---

## 1. Что уже активно в профиле (base bundle)

Профиль `desktop` собирается из `@deepseek-ai/dsh-base` и `dsh-web-app`. В базовом
патче уже стоят — то есть работает без установки:

| Плагин | Что делает | Наше правило/пробел |
|---|---|---|
| `dsh-sandbox` + `dsh-sandbox-local` + `dsh-pwsh-sandbox` / `dsh-bash-sandbox` | ОС-изоляция процесса: `read-only` / `workspace-write` / `danger-full-access`; на Windows активен pwsh-backend, bash выключен | **R-SANDBOX-1** (мы держали его пробелом) |
| `dsh-sandbox-policy` | режим по умолчанию: `DSH_PERMISSION_MODE ?? workspace-write`, корень = `process.cwd()` | задаёт границу записи |
| `dsh-permission-presets` | пресеты «песочница + правило подтверждений» одной ручкой | наш «человек на границе» |
| `dsh-user-approval` + `dsh-client-ui-approval` | seam подтверждений: `ask` вместо отказа | наш **GAP** умел только deny |
| `dsh-fs-observation-policy` | наблюдённое состояние, read-before-edit, version-guarded write | не пересекается: наш **R-READ-1** теперь `can_read`, а не счётчик чтений |
| `dsh-tool-call-timeout-policy` | дедлайн на каждый инструмент → `TOOL_TIMEOUT` | дополняет наш watchdog (**R-TIMEOUT-1**) |
| `dsh-session-checkpoint-policy` | семантические чекпойнты перед запросами и побочными эффектами | аналог **WAL** из гл. 4 (мы честно писали «это не WAL») |
| `dsh-plan-mode` | план → ревью человеком → выход из режима | родственник нашего брифа (**R-BRIEF-1/GAP-1**) |
| `dsh-repeat-tool-reminder` | предупреждения при зацикливании на одинаковых вызовах | мягче нашего старого счётчика; R-READ-1 больше не про это |
| `dsh-session-query-sqlite` + `otel`/`session-telemetry-otel` | поиск по журналу сессии, телеметрия | наш `pipeline-log` (остаток Этапа 4) |
| `dsh-tool-subagent`, `dsh-subagent-spawn/fork` | воркеры и форки агентов | наш «воркер» в драйвере |
| `dsh-tool-workflow` | JS-оркестрация с фазами | «волна» из гл. 5 |
| `dsh-mcp-client` | MCP-серверы как инструменты | проверяющий как внешний процесс |
| `dsh-spill-policy`, `dsh-compaction-basic` | экономия контекста | стоимость/скорость |

**Вывод:** половина «наших» механизмов — дубли того, что уже стоит. Их надо не
развивать, а выключать или связывать.

## 4. Что это меняет в нашем слое

### Убрать как дубль

| Наше | Почему |
|---|---|
| `R-SLEEP-1`, `R-GIT-1` (эвристики по строкам команд) | `dsh-jev-guard` делает это на `tools/pre-execute` с четырьмя состояниями и аудитом; наши regex-эвристики слабее |
| `lanes.py` (worktree) | есть экспериментальный worktree-bundle; наш остаётся для CI/headless |
| `R-SANDBOX-1` как «пробел» | sandbox есть в рантайме; пробел теперь не в механизме, а в **режиме сессии** |

### Связать

1. **Режим сессии.** В этой сессии `danger-full-access` — то есть песочница
   выключена, и наш guard остаётся единственной границей. Для рабочих задач нужен
   `workspace-write`: тогда запись ограничена деревом на уровне ОС, а `allowed_files`
   — на уровне брифа. Две границы вместо одной.
2. **GAP → `ask`.** Наш guard умеет только `deny`; `tools/pre-execute` умеет
   возвращать `ask` через `ctx.approval`. Спорный вопрос брифа должен спрашивать,
   а не блокировать молча.
3. **Timeout.** `dsh-tool-call-timeout-policy` даёт дедлайн на инструмент; наш
   watchdog — дедлайн на весь диспатч. Это разные уровни, оба нужны.
4. **Чекпойнты.** `session-checkpoint-policy` уже стоит; наш `pipeline-log`
   остаётся бизнес-журналом, а не заменой WAL.
5. **Трассировка.** `otel` уже есть; наш след — только доменный (задача, попытка,
   вердикт).

### Оставить своим (в экосистеме этого нет)

| Наш механизм | Почему уникален |
|---|---|
| Бриф и его валидатор | контракт задачи с `allowed_files`, критериями и GAP-вопросами |
| Вердикт-объект + привязка к снимку | «PASS только для этого дерева»; ни плагины, ни рантайм такого не дают |
| Инвалидация вердикта после правки | `R-SNAPSHOT-1` — наша |
| Бюджет попыток и стоимости | у рантайма есть таймауты, но не «три попытки и эскалация» |
| Финализатор + write-set | коммит как привилегированная операция с проверкой набора файлов |
| Evals верификатора | измерение самого контроля — этого нет ни в рантайме, ни в маркете |

## 5. Порядок действий

1. **Переключить рабочие сессии на `workspace-write`** (`/permission`), вернуть
   `danger-full-access` только для разовых операций. Это закрывает `R-SANDBOX-1`
   по существу, а не отчётом.
2. **Поставить `dsh-jev-guard`** и снять наши bash-эвристики (`R-SLEEP-1`,
   `R-GIT-1`) — иначе два слоя спорят о том, кто отказывает, и непонятно, чей отказ
   видит модель.
3. **Не отключать `R-READ-1`:** это теперь `can_read`, а не счётчик чтений;
   повторные чтения остаются за `fs-observation-policy`.
4. **Сделать GAP→`ask`** через `tools/pre-execute` + `ctx.approval`.
5. **Перед установкой любого стороннего плагина — `@jieai/dsh-plugin-vet`.**
   Маркетплейс говорит «популярно», а не «безопасно».

### Что уже сделано

| Шаг | Состояние |
|---|---|
| 2, 3 | `R-SLEEP-1` остался `delegated`; `R-READ-1` переведён в blocking `can_read`; `R-GIT-1` возвращён своим хуком `bash.git_destructive` после удаления `dsh-jev-guard` |
| — | `R-SANDBOX-1` тоже `delegated` (наши `checks.sandbox` остались запасным путём для headless) |
| — | `harness doctor` показывает, если песочница не подтверждена или права висят |
| 2 | `dsh-jev-guard` поставлен и удалён: платный бэкенд, без ключа работал только L0 |
| 1 | **Осталось за вами:** `/permission` → `workspace-write` |
| 4 | Не начато |
| 5 | Не начато |

Важное следствие: после удаления `dsh-jev-guard` разрушительный git закрыт нашим
хуком `bash.git_destructive` (force-push, reset --hard, clean -f, checkout -- .,
restore ., branch -D без явно названного дерева → отказ). `sleep` не запрещён: его
ограничивает дедлайн инструмента, и это осознанно — запрет ожидания мешал законным
паузам.

## 7. dsh-jev-guard: что поставили и на каких условиях

Проверено на установленном пакете `dsh-jev-guard@0.5.7` (25.10.2026).

**Это не бесплатный плагин.** Судья — сервис TypeSafe Jev (`https://api.typesafe.ai/v1/systemone`,
ключ `apikey_...`, кредиты, в конфиге есть `pricePerMTok`). Мой первоначальный вердикт
«брать» был основан на описании в npm и не учитывал этого — урок ровно тот, ради
которого написан `vet-audit-protocol`.

### Что уходит наружу при наличии ключа

`buildState()` (gate.js) отправляет в сервис:

* текст команды;
* при `inlineScripts` (по умолчанию включено) — содержимое inline-скрипта;
* тело `package.json`-скрипта, который команда запускает.

То есть с ключом ваши команды и фрагменты скриптов покидают машину. Это решение о
данных, а не только о деньгах. Плюс риск HTTP 451 по региону.

### Что работает без ключа (проверено)

L0 — 24 локальных статических правила, офлайн:

```
$ node bin/guard.mjs judge "git push --force origin main"
block  -  static-rule  git-force-push   ...   (exit 3)

$ node bin/guard.mjs judge "python -m pytest -q"
allow  -  error  ...  Jev 安全阀门已降级: нет ключа; работает L0 + предфильтр   (exit 0)
```

Покрывает: запись в блочные устройства, `mkfs`, `rm --no-preserve-root`, fork-бомбу,
drop/truncate БД, `git push --force`, перезапись истории, shred ключей, `chmod` корня,
удаление теневых копий/бэкапов, `diskpart`, `wsl --unregister`, kubectl-ns, дисковые
команды PowerShell.

Не покрывает: «серые» случаи (то, для чего нужен платный судья), обфускацию
(`eval`, base64), команды, собранные из переменных.

### Рекомендация

1. **Ключ не вводить.** Платный слой нам не нужен: необратимое уже отсекается L0,
   спорное — человеком (`approval: ask`), область записи — нашей политикой и guard'ом.
2. Если ключ всё же появится — сначала `inlineScripts: false`, чтобы тела скриптов
   не уходили.
3. `lang: "en"` (или `zh-CN`) — по умолчанию сообщения китайские; ставится на странице
   конфигурации плагина в **Plugins**.
4. Деградация — штатное состояние, а не поломка: L0 продолжает работать.

### Что показал статический скан

`scan_plugin` даёт `critical`, но по существу: `process.exit` в dev-скриптах пакета
(`tools/selftest-*.mjs`), «hardcoded keys» — синтетические фикстуры (в самом файле
написано, что настоящие ключи когда-то попали в тесты и были заменены). Реальный
сигнал один: `R15` — динамический `fetch` на endpoint из конфига; он подтверждает
сетевую возможность, описанную выше.

## 8. Чего в экосистеме нет и не будет

Бриф, контракт вердикта, привязка к снимку, бюджет попыток, финализатор с
write-set, evals. Это не «плагины», а **протокол работы**; его либо пишешь, либо
живёшь на промптах. Поэтому наш слой остаётся, но становится тоньше: он отвечает
за маршрут и доказательства, а не за песочницу, таймауты и защиту от повторов.

## 9. Что подключили сами

`dsh-mcp-client` оказался самым дешёвым способом дать агенту внешние инструменты:
один сервер — одна запись в профиле, код проекта не меняется.

| Сервер | Что даёт | Где документация |
|---|---|---|
| `browser` | moli: чтение JS-страниц, скриншоты, CDP-сессия | [`BROWSER.md`](BROWSER.md) |
| `xerj` | поиск по коду/докам, определения, память-неймспейс | [`XERJ.md`](XERJ.md) |
| `trendshift` | тренды GitHub за сутки/неделю/месяц/год | [`TRENDSHIFT.md`](TRENDSHIFT.md) |

Запись живёт в `~/.dsh/profiles/<profile>/cordis.patch.yml` **внутри `- insert:`** —
верхнеуровневый `- id:` адресует только существующую строку и молча игнорируется
(урок `L-20261026-07`). Каждый сервер объявляется отдельным инстансом
`@deepseek-ai/dsh-mcp-client` со своим `serverName`.

Два из трёх (`browser`, `trendshift`) — наши обёртки на stdlib
(`tools/browser_mcp.py`, `tools/trendshift_mcp.py`, общий протокол в
`tools/mcp_stdio.py`); `xerj` подключается как есть, своим бинарником.
