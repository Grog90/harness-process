# Плагин: почему ограждение должно жить здесь

CLI-версия harness — sidecar: агент **может** ходить через шлюз, но не обязан.
Это выполняет урок главы 3 книги лишь наполовину: «инструкция — рекомендация,
хук — ограждение» работает, только если хук стоит на пути, которым агент
физически не может не пройти.

В DSH такой путь — `ctx.tools.guard()`. Это синхронная проверка внутри сервиса
инструментов: другой плагин может только добавить запрет, но не отменить чужой
(`guard` возвращает причину отказа, и первая причина останавливает вызов).

## Что подтверждено по поставляемому коду

Прочитано в `app.asar` (`@deepseek-ai/dsh-tools/lib/index.js`,
`@deepseek-ai/dsh-agent-preset/.../cordis-plugin-development/`):

| Факт | Значение |
|---|---|
| Регистрация | `ctx.tools.guard(fn)` → возвращает disposer, регистрируется как эффект контекста |
| Сигнатура | `fn(exec)` → `string` (отказ) или `undefined` (пропустить) |
| Синхронность | да; асинхронные решения — через `tools/pre-execute`, который умеет `ask` |
| Поля `exec` | `name`, `arguments`, `agent`, `callId`, `parent`, `rootCallId`, `signal`, `token` |
| Порядок | глобальные guard'ы → цепочка контекстов агента; `deny` нельзя переопределить на `allow` |
| Установка | bundle с `dsh.bundle.patch` → `plugin_manager` → `install_bundle` |

## Что делает плагин

```
вызов инструмента
      │
      ▼
ctx.tools.guard ──► guard-core.mjs (JS)  ──► deny? → строка "R-WORK-1: ..."
      │                     │
      │                     └─ читает policies/policy.json (тот же файл, что ядро)
      │                     └─ читает .harness/guard-scope.json (роль + allowed_files)
      ▼
исполнение инструмента (если разрешено)
```

Соответствие правилам:

| Правило | Где проверяется |
|---|---|
| `R-ROLE-1` | роль из scope-файла; расхождение с заявленной — отказ |
| `R-WORK-2` | список инструментов роли |
| `R-PROT-1` | защищённые пути и выход из корня |
| `R-ORCH-1`, `R-VER-1` | продуктовые пути для не-продуктовых ролей |
| `R-WORK-1` | `allowed_files` активного брифа |
| `R-SLEEP-1`, `R-GIT-1` | эвристики команд |
| `R-HOOK-ERR` | сбой самой проверки (fail-closed) |

Состоятельные правила (`R-BRIEF-1`, `R-GAP-1`, `R-BUDGET-*`, `R-VERIFY-1`,
`R-SNAPSHOT-1`, `R-COMMIT-*`, `R-WRITESET-1`, `R-TIMEOUT-1`) остаются в Python:
это работа управляющего процесса, а не предикат одного вызова.

## Дрейф между копиями

Логика продублирована (JS для синхронного guard'а, Python для ядра), поэтому
копии проверяются машинно: `tests/test_parity.py` прогоняет одну матрицу случаев
через оба решателя и требует совпадения решения и правила. Проверено и обратное:
намеренная поломка JS-решателя валит тест.

## Установка

Плагин ставится в профиль (`desktop` в этой установке) и действует на все сессии
профиля. Путь к пакету:

```
C:\Users\ownag\OneDrive\Документы\deepseek-harness\default-workspace\plugins\harness-guard
```

### Через Web UI (обычный путь)

1. Открыть Web UI и выбрать **Plugins** в боковой панели.
2. Кнопка **Add plugin** (или стрелка рядом → **Install a third-party plugin**).
3. В поле пакета вставить **абсолютный путь** к каталогу выше и нажать Enter.
4. Дождаться экрана установки: Host сначала читает пакет, затем ставит его.
   Для локального каталога пакет линкуется, а не копируется.
5. На готовом экране — **Enable now**, либо позже переключатель на карточке
   **Installed plugins**.

### Чья роль применяется

| Ситуация | Роль | Что разрешено |
|---|---|---|
| активная задача (есть `.harness/guard-scope.json`) | `worker` + `allowed_files` брифа | только файлы задачи |
| `config.role` в патче | указанная | по политике |
| `HARNESS_ROLE` в окружении | указанная | по политике |
| ничего из перечисленного | **`human`** | как у человека: продуктовые пути и документация |

Дефолт `human` — осознанное решение: между задачами агент работает как руки
человека, а рабочие ограничения включаются только активной задачей. Иначе профиль
превращается в кирпич: любая запись вне задачи отклоняется как «воркер без
allowed_files».

### Где ищется корень проекта

`config.root` → `HARNESS_ROOT` → указатель `~/.dsh/harness-root` (`$DSH_HOME/harness-root`)
→ текущий каталог → до четырёх уровней вверх. Указатель пишется одной командой:

```powershell
python -m harness --root . plugin prepare
```

```
корень проекта: C:\...\default-workspace
  [ok] policies/policy.json на месте
  [ok] манифест bundle корректен
  [ok] файлы пакета на месте
  [ok] указатель C:\Users\ownag\.dsh\harness-root ведёт на этот корень
ИТОГ: готов к включению
```

### Если политика не найдена

Осматривать можно, менять — нет: чтение разрешено, запись и команды получают
`R-HOOK-ERR` с перечнем проверенных путей. Так сессия не превращается в
кирпич, но и не даёт менять файлы по неизвестным правилам.

### Порядок действий

1. python -m harness --root . plugin prepare — записать указатель на корень.
2. Установить bundle (шаги выше) и включить.
3. Проверить ограждение (ниже).

### Проверка, что ограждение работает

1. Создайте задачу и запустите цикл, чтобы появился активный бриф:

   ```powershell
   python -m harness run --task CHECK-1 --brief briefs/check.json `
     --worker "python examples/agents/demo_worker.py" `
     --verifier "python examples/verifiers/behavior_verifier.py"
   ```

   На время диспетча существует `.harness/guard-scope.json` — без него guard
   работает по роли из окружения и без `allowed_files`.

2. Попросите агента записать файл вне области. Ожидаемый результат:

   ```
   Error: R-WORK-1: src/other.py вне allowed_files брифа
   ```

   Файл при этом не появляется. Если файл создан — guard не активен: смотрите
   статус строки плагина (**failed** / **disabled**) и `HARNESS_ROOT`.

3. Уберите задачу действием вердикта или дождитесь таймаута — файл области
   снимается, и запись снова идёт по роли из окружения.

### Отключение и удаление

* **Выключить:** переключатель строки на карточке плагина (пакет остаётся).
* **Удалить:** страница bundle → **Remove** (с подтверждением).

### Если установка не удалась

Сообщение об ошибке на экране называет причину; вывод pnpm — за **Show install
details**. Частые случаи для локального каталога:

| Симптом | Причина |
|---|---|
| «не найдено» / не читается спецификация | указан относительный путь или путь с опечаткой — нужен абсолютный |
| профиль не writable | DSH установлен в защищённый каталог |
| после установки строка **failed** | плагин упал при активации; для v1 это обычно битый `package.json` или синтаксис `index.js` |

## Проверено вживую (25.10.2026)

Плагин установлен в профиль `desktop` и включён. Наблюдённые результаты на
рабочем профиле:

| Действие | Результат |
|---|---|
| запись вне задачи (роль `human`) | разрешена |
| политика не найдена (до настройки указателя) | отказ только на запись и команды, чтение доступно |
| активная задача `LIVE-1`, `allowed_files = ["docs/_plugin_live_check.md"]` | `guard-scope.json` опубликован с ролью `worker` |
| запись в `src/other_live.py` во время задачи | `Error: R-WORK-1: src/other_live.py вне allowed_files брифа`, файл не создан |
| запись в файл из `allowed_files` | разрешена |
| отмена задачи | область прав снимается, роль снова `human` |

Это и есть доказательство: отказ наблюдался на реальном вызове инструмента, а не
выведен из факта установки. По итогам проверки исправлены три ошибки: поиск
корня (указатель `~/.dsh/harness-root`), дефолтная роль (`human` вместо `worker`)
и снятие области прав при отмене задачи.

## Как проверить, что ограждение работает

Установленный плагин не виден из тестов, но его решения воспроизводимы без
установки — тем же кодом:

```powershell
$payload = '{"root":".","calls":[{"name":"write","arguments":{"path":"src/b.py"}}]}'
$payload | node plugins/harness-guard/guard-probe.mjs
# [{"name":"write","args":{"path":"src/b.py"},"deny":"R-WORK-1: src/b.py вне allowed_files брифа"}]
```

Что остаётся непроверенным до установки: фактическая регистрация в вашем профиле
и порядок относительно других guard'ов. Установка и регистрация сами по себе не
доказывают поведение — доказательство даёт только наблюдённый отказ.

## Ограничения v1

1. **Один корень и одна роль на профиль.** Перизменное переключение возможно через
   `.harness/guard-scope.json` (публикуется диспетчем), но привязка роли к
   конкретному агенту через `agent.ctx` + `restrict()` ещё не сделана.
2. **Только запись и команды.** Правила чтения (лимит повторных чтений) в guard не
   перенесены: это состояние, ему место в управляющем процессе.
3. **Нет `ask`.** GAP-вопросы остаются в Python-гейте; guard умеет только отказ.
4. **`HARNESS_*` из окружения читаются один раз** при активации плагина; scope-файл
   перечитывается на каждый вызов по mtime.
