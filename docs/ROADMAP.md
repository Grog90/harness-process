# Дорожная карта внедрения

Порядок этапов — из главы 7.7 книги: сначала необратимое (выпуск непроверенного),
потом качество, потом наблюдаемость, параллелизм — последним. Критерий закрытия этапа —
не «код написан», а **отказ воспроизводится** и записан в `harness selftest`.

Статусы: ✅ сделано · 🟡 частично · ⬜ не начато

---

## Этап 1. Минимальный управляемый цикл ✅

**Цель:** один последовательный маршрут бриф → исполнитель → независимая проверка →
принятие или эскалация, с сохранением версий и трёх попыток в управляющем процессе.

Сделано:
* `harness task/brief/dispatch/submit/verdict/commit` — весь маршрут;
* состояние в SQLite, резервирование попытки одной транзакцией;
* `attach_brief` → `dispatch` → `submit` → `verdict` → `commit` с guard'ами;
* бюджет: 3 запуска всего, FAIL на 3-м → `ESCALATED`;
* идемпотентность по `event_id`; журнал событий и `pipeline-log`.

Критерий готовности: учебные случаи PASS, FAIL и исчерпания бюджета проходят.
Подтверждение: `harness selftest` (46 проверок), сценарии 4, 8, 9 в `harness demo`.

**Что осталось до полной готовности:** подключение реального рантайма агентов —
сейчас роли исполняют скрипты. Это следующий практический шаг (см. «Этап 1.5»).

---

## Этап 1.5. Подключение к живому рантайму ✅

Нужно, чтобы `harness` стоял между агентом и инструментами, а не рядом с ними.

Сделано:
* `harness/gateway.py` — закрытый список инструментов (`read_file`, `list_dir`,
  `write_file`, `run_command`, `snapshot`), роль из окружения, `allowed_files`
  из брифа задачи, проверка состояния и срока, аудит каждого решения в `tools_audit`;
* попытка агента расширить права через аргументы игнорируется (`R-TOOL-1`);
* вне `RUNNING` инструменты закрыты (`R-STATE-1`);
* `run_command` — с урезанным окружением, таймаутом и без наследования `HARNESS_*`;
* атомарная запись через временный файл: недописанный файл не попадает в снимок.

Критерий готовности: агент с ролью `worker` не может записать файл вне
`allowed_files` и не может закоммитить; попытка видна в журнале как `deny` с правилом.
Подтверждение: `selftest` (R-STATE-1, R-TOOL-1), сценарий 13 демо.

**Остаток:** обёртка конкретного рантайма (сейчас протокол есть, интеграции с
конкретным фреймворком нет).

## Этап 2. Защищённая приёмка ✅

**Цель:** нельзя выпустить изменённый после ревью код или принять поддельный отчёт
обычным разрешённым путём.

Сделано:
* вердикт привязан к `snapshot_id` (хеш дерева), правка инвалидирует PASS;
* `commit` перепроверяет контракт вердикта и снимок;
* политика и схемы — защищённые пути, рабочая роль их не пишет;
* роль берётся из окружения, подмена заявленной роли — отказ;
* `PASS` без покрытия критериев понижается до `INCONCLUSIVE`;
* адверсальный `PASS` без выполненного сценария невозможен.

Критерий готовности: после `PASS` изменена одна строка продукта → выпуск отклоняется
(`R-SNAPSHOT-1`). Подтверждение: `selftest` «правка после PASS инвалидирует вердикт».

**Доверенный финализатор (добавлено):** `harness finalize` сверяет снимок, проверяет
write-set ⊆ `allowed_files` (`R-WRITESET-1`), пишет `pipeline-log` в тот же коммит
(`R-FINAL-1`) и записывает связь «снимок → sha». Подтверждение: `selftest` R-WRITESET-1,
R-FINAL-1, сценарий 15 демо.

**Остаток:** подпись коммита и защищённый от подмены финализатор (сейчас — процесс в
том же дереве, который может запустить человек).

## Этап 3. Измерение качества ✅ (механика) / 🟡 (набор)

**Цель:** понимать, что именно пропускает проверяющий, а не только как часто он говорит PASS.

Сделано:
* `harness evals run` — прогон размеченного набора, метрики: пропуск дефекта, ложный
  отказ, неполная проверка, согласие с разметкой;
* учебный набор из 10 случаев (4 корректных, 6 дефектных, включая скрытые);
* два учебных верификатора: маркерный (пропускает 50%) и поведенческий (0%);
* предупреждения о грубости метрик при малом или однородном наборе;
* `harness checks run` — проверки из брифа выполняются в копии дерева, вердикт
  собирается из кодов возврата, критерий без запуска даёт `INCONCLUSIVE`. Это
  закрывает добрую часть остатка R-COMMIT-1 («доверяем отчёту о выполнении команд»).

Критерий готовности: каждый тип ошибки объясним, регрессия после изменения
конфигурации видна.

**Набор собран (27.10.2026):** 35 размеченных случаев в трёх предметах —
`examples/evals/fee` (21: деньги, округление, типы, границы),
`examples/evals/access` (6: матрица доступа, fail-open, тихий отказ) и
`examples/evals/duration` (8: разбор строки, пустая строка, неизвестная единица, тип).
Разметка — 22 дефектных и 13 корректных; формат и правила пополнения —
`examples/evals/README.md`, целостность корпуса проверяет `tests/test_eval_cases.py`.

**Текущий режим:** деньги — пропуск 0/13, ложный отказ 0/8; доступы — 0/4 и 0/2;
длительности — 0/5 и 0/3. Согласие с разметкой 1.0 во всех трёх наборах.

Первая версия набора давала пропуск 1/12: `bad_8` (банковское округление) проходил,
потому что проверка била по 20000 и 12345, где `round()` и «половина вверх» совпадают.
Слепая зона закрыта не подкруткой метрики, а ужесточением контракта: в брифе появилось
правило «ровная половина округляется вверх» и критерий `AC-3` с входом `fee(20) = 1`.
После этого три «хороших» кандидата, округлявших по-банковски, перестали соответствовать
спеке и были исправлены — это и есть нормальный эффект ужесточения спеки.

**Остаток, который нельзя закрыть без данных:** добавить случаи из реальных прогонов,
где проверяющий что-то пропустил (сейчас классы дефектов известны, а сами кандидаты
синтетические), и стоимость принятой задачи.

## Этап 4. Восстановление и наблюдаемость ✅

**Цель:** прерывание и возобновление на каждом значимом переходе без потери
доказательств и без повторного внешнего эффекта.

Сделано:
* устойчивое состояние (SQLite WAL), переживает перезапуск;
* `event_id` → повторная доставка не создаёт эффекта;
* **watchdog вынесен из процесса** (`harness/watchdog.py`): `sweep` для cron/CI и
  `serve` для отдельного процесса; просрочка отзывается, смерть доставляется
  отдельным событием `dispatch_death`, повторный результат отклоняется по номеру
  попытки;
* четыре отдельных статуса неполной проверки.

Критерий готовности: прерывание и возобновление на каждом значимом переходе.
Подтверждение: `selftest` R-TIMEOUT-1, сценарий 10 демо.

**Остаток:** вывоз журнала в доверенное хранилище, `trace_id`/span'ы, процедура
«результат неизвестен» (сейчас различаются «не сделано» и «сделано»).

## Этап 5. Ограниченный параллелизм ✅ (v1)

**Цель:** выигрыш времени до принятия без роста значимых пропусков.

Сделано:
* `harness/lane create` — изолированный `git worktree` и ветка на задачу;
* `harness/lane merge` — слияние только `COMMITTED`-задачи, только в чистое главное
  дерево, под мьютексом `merge.lock` с ограниченным ожиданием и снятием протухшей
  блокировки;
* конфликт → `git merge --abort` и задача человеку: координатор продукт не правит;
* после слияния фиксируется merge-коммит (finalizer = `merge-queue`).

Критерий готовности: параллельная работа не смешивает write-set'ы.
Подтверждение: `selftest` R-WAVE-1, сценарий 16 демо, 5 unit-тестов на конфликт,
грязное дерево и мьютекс.

**Остаток:** раздельные тестовые БД/порты/очереди для лейнов, очередь интеграции
и барьер волны (закрытие волны одним коммитом).

## Этап 6. Постоянное сопровождение контроля 🟡

Нужно, чтобы система не деградировала молча.

Сделано:
* **измерение** (`evals`): пропуск, ложный отказ, неполная проверка — с предупреждением
  о малой и однородной выборке;
* **бюджет стоимости** (`R-COST-1`): гейт до запуска, запись факта, отчёт по задачам;
* **дисциплина изменения правил** (`R-HOOK-1`): причина + прогон проверок правила,
  затем запись причины и отпечатка файла правил; `rule verify` показывает дрейф;
* матрица различает «есть хук» и «есть исполняемый тест» (сейчас 32/32 и 32/32).

**Остаток:**
* владелец набора evals и регулярный разбор пропусков (это процесс, не код);
* пересмотр маршрутизации моделей по измерениям, а не по ярлыкам;
* проверка изменений самих хуков отдельным агентом.

## Этап 7. Продуктовый уровень изменения ✅ (v1)

**Цель:** задача перестаёт быть самостоятельной единицей: у неё появляется изменение
с согласованным планом, редакцией и доказательствами согласования.

Сделано:
* `harness/changefsm.py` — автомат изменения (15 состояний), таблица переходов,
  `Ready`-гейт, review-записи, trace-матрица;
* SQLite: `changes`, `change_events`, `change_reviews`, `tasks.change_id` (схема v4,
  миграция идемпотентная); review-записи дублируются файлами в `changes/<id>/reviews/`;
* `harness change new|list|show|review|trace|ready|advance`; `task new --change`;
* бриф: `change_id` и полный `spec_ref` (40 hex), критерии несут `req_id`/`case_id`;
  `brief from-change` заполняет их и берёт полный SHA вместо короткого;
* `specgate`: архивный change больше не считается связью, digest спеки сверяется;
  диспетч задачи по change разрешён только из `READY`/`IN_PROGRESS`;
* правила `R-CHG-1`, `R-REF-1`, `R-REV-1`, `R-REV-2`, `R-TRACE-2` и ужесточённый
  `R-SPEC-1`: 6 исполняемых пар в `selftest`.

Критерий готовности: нельзя диспетчить задачу по change до Ready; правка плана после
Ready сбрасывает состояние; review без критериев/хеша и самопроверка отклоняются;
trace-разрыв блокирует Ready. Подтверждение: `tests/test_changefsm.py`,
`tests/test_specgate.py`, `selftest` (61 проверка).

**Остаток:** приёмка/архив как гейты с evidence, baseline/candidate, мультирепозиторность,
пресеты ролей и UI. Это Этапы 2–5.

## Этап 9. Проверка, приёмка и закрытие ✅ (v1)

**Цель:** изменение нельзя объявить готовым, выпущенным и принятым без объектов,
которые это подтверждают.

Сделано:
* `harness/verification.py` — baseline/candidate-прогоны с `ref`, runner, окружением,
  версиями сервисов, числом тестов и diff падений; `verification.json`/`.md`;
* гейты `verify/release/accept/archive`: отчёт с версиями, `release.json`,
  `acceptance.json`, `closing.json`;
* `write_evidence` — пакет `evidence/change-<id>/` с sha256-манифестом;
* CLI `verification run|show`, `change release|accept|close|evidence`;
* правила R-QA-1, R-QA-2, R-ACCEPT-1, R-ACCEPT-2 и 4 исполняемые пары в selftest.

Критерий готовности: verify без отчёта/версий/нулевого прогона отклоняется; release и
accept без записей отклоняются; archive без acceptance и evidence отклоняется; L2 с
`by_role=agent` отклоняется. Подтверждение: `tests/test_verification.py`,
`tests/test_changefsm.py`, selftest (61), `harness coverage` (47 правил, 94%).

**Остаток:** подпись evidence (cosign/sigstore), вывоз в доверенное хранилище и
реальная интеграция с CI/средой (Этап 4); мультирепозиторность (Этап 5).

## Этап 11. Мультисервисность ✅ (v1)

**Цель:** change может опираться на несколько сервисов, а приёмка — собрать их версии.

Сделано:
* `change new --service name=PATH[@SHA]` и `change services`;
* сервисы в брифе (`services`) и валидация (относительный путь, полный SHA);
* verification по сервисам: ключи `service:mode`, `--cwd`, требование baseline и
  candidate для каждого объявленного сервиса;
* release/acceptance/evidence уже принимают несколько `--service name=SHA`;
* merge order: порядок объявления сервисов фиксируется в release/acceptance
  (`merge_order`), запись с другим порядком отклоняется.

Критерий готовности: change объявляет два сервиса; verification требует оба прогона;
приёмка содержит несколько SHA и merge order. Подтверждение: `tests/test_verification.py`,
`tests/test_changefsm.py`, trace мультисервисной спеки.

**Остаток:** push/PR сервисных репозиториев, откат частичного коммита и исполнение
merge order; snapshot/commit закрыты `add-service-commit` (Этап 12).

## Этап 12. Мультикорневая запись ✅ (v1)

**Цель:** worker может писать в явно открытый сервисный репозиторий, не ослабляя
однокорневую защиту.

Сделано:
* `change new --service-write NAME` открывает сервис; по умолчанию read-only;
* `allowed_files` понимает ключи `service:<name>/<relative>`, бриф валидирует сервис
  и `write=true`;
* policy/guard/gateway резолвят путь под сервисный корень с realpath, требуют
  `can_write_services` (только worker) и `allowed_files`;
* parity-тесты JS↔Python, gateway пишет в сервис и отклоняет чужой файл/корень;
* `snapshot_for_task` включает деревья writable-сервисов, `finalize` коммитит каждый
  сервис отдельно и пишет SHA в `commits`/evidence (`add-service-commit`);
* shell-запись в сервис не открыта; push/PR сервисов и merge order — нет.

Критерий готовности: запись в открытый сервис проходит, в чужой корень/чужой файл/
read-only сервис — отказ; verifier не пишет сервис. Подтверждение:
`tests/test_parity.py`, `tests/test_harness.py` (GatewayTests).

**Остаток:** push/PR сервисных репозиториев, откат при частичном коммите и merge order
как исполнение.

## Как проверять, что этап закрыт

```powershell
python -m unittest discover -s tests -v      # 434 проверок свойств
python -m harness selftest                   # 61 исполняемая проверка
python -m harness demo                       # 50 сквозных проверок
python -m harness coverage                   # покрытие и наличие тестов
python -m harness rule verify                # правила менялись с записью?
python -m harness evals run --cases examples/evals/fee --verifier "..."
```

Этап закрыт, если все пять команд зелёные **и** новый отказ добавлен в `selftest`
в виде пары «разрешённый случай / запрещённый случай».
