# Набор evals

Здесь лежат размеченные случаи для `harness evals run`: кандидат (работа исполнителя)
и метка, что проверяющий обязан с ним сделать.

## Формат

```
<набор>/
  <кейс>/
    case.json          # метка и ссылка на бриф
    candidate/src/*.py # то, что «принёс» исполнитель
```

`case.json`:

| Поле | Смысл |
|---|---|
| `case_id` | имя кейса; должно совпадать с каталогом |
| `expected` | `PASS` — корректная работа, `FAIL` — дефект, который обязан быть найден |
| `candidate_dir` | каталог кандидата относительно кейса |
| `brief_file` | путь к брифу относительно кейса |
| `note` | класс дефекта: по нему метрика предупреждает об однородности набора |

Бриф — общий на набор (`examples/evals/<набор>-brief.json`): в нём контракт и критерии,
по которым проверяющий обязан судить.

## Запуск

```powershell
python -m harness evals run --cases examples/evals/fee      --verifier "python examples/verifiers/behavior_verifier.py"
python -m harness evals run --cases examples/evals/access   --verifier "python examples/verifiers/access_verifier.py"
python -m harness evals run --cases examples/evals/duration --verifier "python examples/verifiers/duration_verifier.py"
```

## Как добавить кейс

1. Скопируйте соседний кейс с тем же набором.
2. Положите кандидата в `candidate/src/<модуль>.py`.
3. Поставьте `expected` и опишите класс дефекта в `note` — одной фразой.
4. Прогоните набор: новый кейс должен либо совпасть с меткой, либо показать
   расхождение, которое вы готовы объяснить.

Разметка — это утверждение о поведении, а не о коде. Если проверяющий расходится с
меткой, сначала проверьте спеку: возможно, прав он, а не вы.

## Чего здесь нет

Кейсы синтетические: классы дефектов взяты из отказов, которые проект уже ловил, но
сами кандидаты написаны руками. Настоящее пополнение — из реальных прогонов, когда
проверяющий что-то пропустил. Пока таких записей нет, метрики описывают известные
классы ошибок, а не частоту отказов в работе.
